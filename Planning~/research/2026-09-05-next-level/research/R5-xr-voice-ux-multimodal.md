# R5 — XR voice UX and multimodal interaction

Research report, 2026-09-05. Scope: HCI/systems work 2018–2026 (emphasis 2021+) on voice interaction in VR/XR and games — multimodal fusion with gaze/hand pointing, feedback and error-recovery design, activation modes, latency perception, LLM/NLU intent parsing, and developer tooling — evaluated against VoXR v2.0.0 as described in `00-brief.md`.

Pipeline stage numbers (§2.1 capture … §2.8 verification) refer to the brief.

## Executive summary

- **Deixis is the single largest UX win available, and it is cheap.** Nothing in the literature asks VoXR to get better at recognising "hotel one". It asks VoXR to let the player say *"fire at that"* and resolve the referent from gaze/pointing. Bovo et al. (2025) measure **+26.5% coreference-resolution accuracy** from adding gaze + laser-pointer + scene metadata to a VR speech transcript versus speech alone; AssistVR (Chen et al., 2024) measures **30.5%/86.4% faster** multi-object selection at 4 targets and **lower NASA-TLX on 4 of 6 subscales** for speech+raycast vs a spatial-UI baseline. This maps onto the maintainer's own `{ship*}` slot-time-hook plan in `anaphora-resolution-analysis.md` almost exactly, and it *reduces* grammar size rather than growing it.
- **Multimodal fusion is a substitution-error fix as well as a UX feature.** Two semantically rich inputs mutually disambiguate: the classical result is 19–41% error suppression (Oviatt; `UNVERIFIED`, see §3.13). For VoXR this is concrete — if gaze says the only in-view hostile is `hotel one`, the parser can prefer that slot value over an acoustically closer wrong one, which directly attacks the documented in-grammar-substitution failure mode without touching the decoder.
- **Fusion timing is short and mostly simultaneous.** 95% of multimodal constructions are delivered with gesture overlapping speech rather than sequentially, with observed intermodal lags around 0.3–0.8 s and ~1 s as a sufficient fusion threshold (Chen et al., OZCHI 2004; `UNVERIFIED`). Practical VoXR rule: buffer a ring of gaze/pointing samples and resolve a deictic slot against the window **[word_start − 1.0 s, word_end + 1.0 s]**, using VOSK's existing per-word `start`/`end` timings (§2.3 already sets `vosk_recognizer_set_words(1)`), not against "gaze at the moment the command fired".
- **Latency: acknowledge early, execute later.** In VR specifically, Maslych et al. (CUI 2025, n=54) find quality of experience degrades significantly at every step of 1.5 s → 4.0 s → 6.5 s, and that *natural* fillers (thinking gesture + voice line) significantly improve perceived response time at 4.0 s and 6.5 s while a spinner does not (65% preferred natural fillers). VoXR's real problem is not the decoder; it is that the 0.5–2 s `bufferWindow` is silent. A ~200 ms "heard you" earcon/HUD tick at first partial converts dead time into acknowledged waiting for free.
- **Push-to-talk is the right default and the docs are already correct**, but it should not be the only option. Meta's own platform guidance says implement PTT *or* a wake word so the mic is not always live, always signal mic state via earcon or visual, and show transcription as light guidance. The missing third mode is gaze-gated listening: Google's Look and Talk shows a shipped design where **attention gating is strict before speech onset and relaxed once the user starts speaking** — exactly the shape a VR bridge-officer game wants (look at the tactical console, speak, then look at the target).
- **Repair should be a two-strike protocol, not an open loop.** Meta's conversation-design standard is *two* repair attempts then hand off to another modality. VoXR has the machinery (`OnCommandPending`, `PendingAmbiguity`, `pendingTimeout`) but no attempt counter and no hand-off contract, so a bad audio environment produces an unbounded ask-loop.
- **Confidence display beats confidence thresholds.** Nowrin & Vertanen (PETRA 2025, n=48) got a **12% relative increase in error detection** and **11% faster decisions** by *marking low-confidence output differently* rather than by raising a rejection threshold. VoXR's `minConfidence` is stuck at 0.4 because VOSK confidence is flat/uncalibrated — but the same uncalibrated number is still usable as a *display* signal (render the low-confidence word dimmer/italic in the HUD transcript) where it costs nothing to be wrong.
- **Ambiguity should be shown, not only asked.** Uncertain Pointer (Tsai et al., CHI 2026, n=60 + n=40) systematically studies *feedforward* visualisation of multiple candidate targets before confirmation, with opacity encoding system uncertainty. VoXR's `disambiguateSiblingTies` currently ships a data structure and no presentation; the package should ship a reference prompt prefab, because the docs themselves note the flag is worse than useless without a subscriber.
- **Do not put an LLM in the hot path on Quest.** Meta's own Unity Inference Engine guidance says the NPU is not used, inference runs on the Unity main thread, and large generative models "do not perform well" on Quest 3. VR Mover's LLM path costs ~2 s to first API call. An LLM tier is viable only off-device or as a design-time/offline tool — which is where it is genuinely valuable (see DX below).
- **The developer story that is missing is linting and evaluation, and both have prior art.** Microsoft's Grammar Confusability Metric (US7844456B2) computes a 0–1 confusability score per grammar term pair from the acoustic model; Amazon ships Utterance Conflict Detection on every model build plus an NLU Evaluation Tool driven by annotation sets. VoXR already has *six* authoring warnings, `InjectText`, a WAV fixture corpus and a 699-utterance A/B rig — it has the parts of both tools and has not assembled either.

## Detailed findings

### 3.1 Gaze + pointing + scene context resolves deixis in VR — `VERIFIED`
**Citation.** Bovo, R., Brudy, F., Fitzmaurice, G., Anderson, F. (2025). *Augmenting speech transcripts of VR recordings with gaze, pointing, and visual context for multimodal coreference resolution.* arXiv:2509.08689. https://arxiv.org/abs/2509.08689

**Study.** 12 participants (6 pairs) held an open-ended design critique of a 3D apartment in VR while gaze, laser pointing and voice were captured. Gaze/pointing streams plus scene metadata were converted to textual descriptions of non-verbal behaviour and interleaved into the transcript.

**Evidence.** **26.5% improvement in coreference-resolution accuracy** by a GPT model on the multimodal transcript versus a speech-only baseline. No timing-window figures are reported.

**VoXR mapping.** This is the empirical backing for the maintainer's own Phase-2/3 plan in `Planning~/anaphora-resolution-analysis.md`. Take the **slot-time hook** option (already the document's recommendation): a `{target*}` pattern suffix opts a slot position into deixis; when the matcher sees a pronoun/demonstrative token there it calls an `IVoxrDeixisResolver` delegate. §2.4 grammar gains ~10 closed-class words (`it, them, that, this, those, these, one, him, her, they`) — a trivial addition beside the existing per-value entries, and in exchange the *slot value list can shrink*, which shrinks the grammar. §2.6 keeps its invariant that a delivered slot value is a registered value, because the resolver substitutes before delivery.

**Feasibility on Quest.** High. Head-gaze ray is available on Quest 2/3 with no eye tracking; Quest Pro/3 eye tracking improves it. Resolution is O(small N) over a per-category salience ring buffer, main-thread, allocation-free — consistent with the parser's existing style.

**Risk.** A wrong referent is a *silent* wrong action, the same class of failure the leading-required-miss bar was shipped to stop. Mitigation: require the resolver to return a confidence and route ties into the existing pending/ambiguity path rather than picking.

### 3.2 Speech + pointing beats a spatial UI once there is more than one target — `VERIFIED`
**Citation.** Chen, J., Grubert, J., Kristensson, P.O. (2024). *Large Language Model-assisted Speech and Pointing Benefits Multiple 3D Object Selection in Virtual Reality.* arXiv:2410.21091. https://arxiv.org/abs/2410.21091

**Study.** AssistVR (speech + raycast + LLM) vs DiscPIM (mini-map). 24 participants, 1/2/4 targets × three scene-perplexity levels × search and repeat tasks; 2,592 trials.

**Evidence.** Search task at 4 targets: **19.8 s vs 35.9 s** (p<.001). Repeat at 4 targets: **12.5 s vs 23.3 s** (p<.001). At **1 target the baseline won** (9.34 s vs 14.5 s, p<.05). NASA-TLX overall **4.06 vs 4.94**, with physical, temporal and effort subscales all lower (p<.05). SUS 71.0 vs 68.0 (n.s.). Preference split 13/11. Named dislikes: limited command vocabulary, speech-recognition failures, accent sensitivity, difficulty remembering object names.

**VoXR mapping.** Two things. (a) Sequential extraction (§2.6) already lets one utterance carry several commands; this is the evidence that *plural targets in one command* ("fire on hotel one and hotel three") is where voice earns its keep, and argues for a set-valued slot rather than n repeated utterances. (b) The dislikes are a verbatim list of VoXR's `KNOWN_LIMITATIONS.md`, which is why finding 3.13 (confusability linting) and 3.1 (deixis, so players need not remember names) matter more than raw decoder work.

**Feasibility.** Set-valued slots are a parser change only; no decoder or grammar change beyond adding `and`.

**Risk.** The 1-target regression is a real warning: do not make voice the *only* path to a single-target action.

### 3.3 Voice for mode-switching, not for repetition — `VERIFIED` (abstract-level)
**Citation.** Bashar, M.R., Mutasim, A.K., Pfeuffer, K., Batmaz, A.U. (2026). *Eyes on Many: Evaluating Gaze, Hand, and Voice for Multi-Object Selection in Extended Reality.* CHI '26. arXiv:2602.12406. https://arxiv.org/abs/2602.12406

**Evidence.** Mode-switching techniques (SemiPinch, FullPinch, DoublePinch, Voice) crossed with subselection (Gaze+Dwell, Gaze+Pinch, Gaze+Voice). DoublePinch + Gaze+Pinch was best overall; SemiPinch worst. **Voice-based mode-switching showed benefits; Gaze+Voice subselection was less favoured because the repetitive vocal commands were perceived as tedious.** Participant counts and per-condition times are in the full PDF, not the abstract.

**VoXR mapping.** Doctrine for `Documentation~/command-sets.md` and the sample content: voice belongs on *mode and intent* (`switch to navigation`, `cease fire`, `orient heading two seven zero`) and on batch/one-shot orders, and does not belong on per-object iteration. It also argues that the **audio gap on set switching (§2.4)** is more damaging than its 50 ms suggests, because mode-switching is precisely the job the literature assigns to voice.

**Feasibility / risk.** Documentation and sample change only. Risk: abstract-level evidence.

### 3.4 Show the ambiguity before asking about it — `VERIFIED`
**Citation.** Tsai, C., Tacconi, N., Wilson, A.D., Abtahi, P. (2026). *Uncertain Pointer: Situated Feedforward Visualizations for Ambiguity-Aware AR Target Selection.* CHI '26. https://doi.org/10.1145/3772318.3790329 (arXiv:2602.13433)

**Evidence.** 25 pointer designs across two online studies (**n=60**, **n=40**) varying object distance and density; measures preference, confidence, mental ease, target visibility, identifiability. Two design levers: distinct visual identities (e.g. colour) per candidate to *support* disambiguation, and visual intensity (e.g. opacity) to *convey system uncertainty*.

**VoXR mapping.** VoXR already computes everything this needs: `PendingAmbiguity` carries the competing commands plus the one discriminating word, and `IsTruncated` says when the list is incomplete. What the package ships is a struct and a documentation paragraph that says the flag is *worse than the coin flip* without a subscriber. Ship a reference prompt (world-space canvas prefab + sample) that renders the candidates with per-candidate colour and uncertainty opacity, wired to `OnCommandPending` + `PendingAmbiguity`, and gate the truncated case behind "…or say the whole command again", which the docs already prescribe.

**Feasibility.** Pure §2.7/sample work. No runtime risk.

**Risk.** The studies measure perception, not task error; and they are AR *selection*, not command disambiguation. The transfer is the visual-encoding vocabulary, not the effect size.

### 3.5 Latency in VR: <4 s, and fill the gap with something diegetic — `VERIFIED`
**Citation.** Maslych, M., Katebi, M., Lee, C., Hmaiti, Y., Ghasemaghaei, A., Pumarada, C., Palmer, J., Martinez, E.S., Emporio, M., Snipes, W., McMahan, R.P., LaViola Jr., J.J. (2025). *Mitigating Response Delays in Free-Form Conversations with LLM-powered Intelligent Virtual Agents.* CUI '25, Article 49. https://doi.org/10.1145/3719160.3736636 (arXiv:2507.22352)

**Study.** n=54 (23F/31M, 18–56, mean 22.07). Delays **1.5 s / 4.0 s / 6.5 s** × fillers **none / artificial (spinner + processing sound) / natural (thinking gesture + "Hmm, let's see…")**.

**Evidence.** Perceived response time degrades at every delay level (p<.0001). **Natural fillers significantly improved perceived response time at Medium (p<.01) and High (p<.0001); artificial fillers did not.** Engagement, impression, competence and willingness to re-engage all fell with latency (p<.0001); discomfort rose (p<.05). 57.4% named the fastest agents favourite, 61.1% named the slowest as disliked, **64.8% preferred natural fillers**. Recommendation: target **<4 s** turn-taking delay.

**VoXR mapping.** VoXR's user-visible latency is dominated by `bufferWindow` (0.5 s default, up to ~2 s in the field) plus VOSK's ~0.8 s endpointing — comfortably under 4 s, but *entirely silent*. Two additions to §2.7: (1) an acknowledgement signal at the **first partial result** (`OnPartialResult` already exists — it just isn't documented as the acknowledgement hook); (2) a documented pattern for a *diegetic* filler, because the study says the diegetic one is what works — in a bridge-command game the filler is the officer answering "Aye, captain…" before the order resolves, not a spinner.

**Feasibility.** Documentation + one sample; optionally a `OnSpeechDetected` event so games do not have to subscribe to raw partials.

**Risk.** Acknowledging then rejecting is a new failure shape. Pair the early ack with a distinct rejection earcon so the two are never confused (see 3.6, 3.8).

### 3.6 Mark low confidence in the display rather than raising the threshold — `VERIFIED`
**Citation.** Nowrin, S., Vertanen, K. (2025). *Using Confidence Scores to Improve Eyes-free Detection of Speech Recognition Errors.* PETRA '25. https://doi.org/10.1145/3733155.3734896 (arXiv:2410.20564)

**Study.** n=48. Four conditions: AllNormal (200 wpm), AllSlow (140 wpm), UncertainSlow (low-confidence output at 140 wpm), UncertainBeep (one-second beep before low-confidence output). Confidence threshold 0.93. Underlying recogniser WER 15%.

**Evidence.** Error-detection accuracy **85% (UncertainSlow) vs 80% (AllNormal), 79% (UncertainBeep), 76% (AllSlow)**. Detection time **1.86 s vs 1.98 / 2.26 / 2.03 s**. Total listen+respond time rose only 7% for UncertainSlow (4.85 s vs 4.52 s). Participants located only 49% of errors overall — insertions were nearly undetectable (2%).

**VoXR mapping.** VoXR's `minConfidence` is pinned at 0.4 because VOSK confidence is flat (documented: "two" ≈ 0.50 regardless of clarity), so it cannot be raised without killing number sequences. This finding sidesteps that entirely: use the same uncalibrated number as a **presentation** signal. Surface per-word confidence on the recognised-command event and in `OnPartialResult`, and document a HUD pattern that dims/italicises words below a developer-set display threshold. Also note the 2% insertion-detection figure: it is direct evidence for why VoXR's *phantom command* class (stranded tails, noise decoded as short in-grammar words) needs a machine-side bar — humans do not catch insertions — which retrospectively justifies the 2.0.0 leading-required-miss bar.

**Feasibility.** Event-payload change (additive) plus docs; a minor public-API addition with a clean migration path.

**Risk.** If VOSK confidence is *too* flat, the marking is noise. Cheap check: replay the 699-utterance A/B corpus and compute AUC of per-word confidence against known substitutions before shipping any UI.

### 3.7 Gaze-gated activation as a third listening mode — `VERIFIED`
**Citation.** Google Research Blog (2022). *Look and Talk: Natural Conversations with Google Assistant.* https://research.google/blog/look-and-talk-natural-conversations-with-google-assistant/

**System.** Three phases. Phase 1 (engagement): face detection with proximity filtering via face-box size, Face Match, a multi-tower CNN gaze model over whole face + eye patches, multimodal active-speaker detection. Phase 2 (intent validation): Voice Match, **on-device** ASR, intent understanding that combines non-lexical audio (pitch, speed, hesitation) with text classification over **partial** utterances. Phase 3: fulfilment. All processing local; no audio to servers. End-to-end latency stated as comparable to hotword systems.

**Key design rule.** Attention requirements are **strict before the system signals readiness** (so a passing glance does not trigger), then **relaxed once the user starts speaking** so gaze can wander naturally.

**VoXR mapping.** Add `VoxrListeningMode.GazeGated` beside `Continuous` and `PushToTalk`. The controller drives `StartRecognition` when a developer-supplied attention predicate (head-gaze ray hitting a designated console/NPC collider, dwell ≥ T) fires, and — crucially — does **not** stop the moment gaze leaves; it holds while speech is in progress (first partial received) and stops on end-of-utterance or a timeout. This is a `VoxrPushToTalkController` change only; the predicate stays game-side, which matches VoXR's existing separation (the package ships no UI).

**Feasibility.** High on Quest 2/3 with head gaze; better with Quest Pro/3 eye tracking. No decoder change.

**Risk.** VOSK grammar mode has no silence output, so any hands-free mode inherits the false-trigger problem the PTT doc names. Gaze gating narrows *when* the mic is open; it does not fix in-grammar noise decoding. Pair with a wake word (3.9) or a rejection model, and keep PTT the default.

### 3.8 The platform's own voice-design standard — `VERIFIED`
**Citations.** Meta Horizon OS Developers, *Voice Best Practices* (https://developers.meta.com/horizon/design/voice-best-practices/); *Voice Technology* design guidance; *Voice SDK Best Practices* (https://developers.meta.com/horizon/documentation/unity/voice-sdk-improving-results/).

**Evidence (normative).** Do not activate the microphone without consent or by default. Ensure transparent activation — mic-state awareness via earcons or conversational cues. Warn the user when background noise is high and suggest moving. Displaying the text transcription doubles as mic-state feedback *and* as light guidance about how commands are heard, so the user can adjust. **"Conversation Design standards expect two attempts at repair and then a handoff."** Triage soft vs hard errors; offer explanations and alternatives. Announce available options; provide shortcuts for frequent actions. Separately, community/vendor guidance: implement push-to-talk or a wake word so the mic is not always active; use voice for high-level commands, not precise adjustments; voice should augment, not replace, other input. Wit.ai's own tooling advice is to review logged utterances and add synonyms to bias recognition.

**VoXR mapping.** Four concrete gaps: (1) **no repair-attempt counter** — `pendingTimeout` bounds *time*, not *attempts*, so a noisy room can loop; add an attempt count to the pending state and an `OnRepairExhausted` hand-off event. (2) **No noise signal** — VoXR's AGC (§2.2) already tracks level; exposing a noise-floor estimate would let a game show Meta's "move somewhere quieter" cue. (3) **Mic-state feedback is optional** — `OnTalkStarted`/`OnTalkEnded` exist but the docs treat the indicator as a tip; make it a documented requirement with a sample. (4) **Discoverability** — VoXR has the complete active command set in memory at all times and no API to enumerate it for a "what can I say?" panel.

**Feasibility.** All additive; (1) and (4) are small parser/recogniser API additions.

**Risk.** Vendor guidance, not measured. Treat as convention alignment.

### 3.9 Offline wake word: feasible, but the licence is the trap — `VERIFIED`
**Citations.** dscripka/openWakeWord, https://github.com/dscripka/openWakeWord ; Picovoice Porcupine, https://picovoice.ai/products/voice/wake-word/ and https://github.com/Picovoice/porcupine (product pages `VERIFIED` via search result content, repository page not fetched → treat Porcupine's numbers as vendor claims).

**Evidence.** openWakeWord: **code Apache-2.0**; **pre-trained models CC-BY-NC-SA 4.0** because of training-data provenance. Documented operating target: **false-reject <5% at false-accepts <0.5/hour** with threshold tuning, evaluated on the Dinner Party Corpus (~5.5 h far-field speech and noise). One Raspberry Pi 3 core runs **15–20 models simultaneously in real time**. Input contract: **16-bit 16 kHz PCM in 80 ms frames**. Custom wake words trainable from **100% synthetic TTS speech**, via a Colab notebook, in under an hour, with no proprietary data. Porcupine (vendor claims): 97%+ detection, <1 false alarm per 10 h, <200 KB, 11.0× more accurate and 6.5× faster than the best of PocketSphinx/Snowboy on RPi 3 — but commercial licensing (reported entry ~$6,000/yr for 100 monthly active devices), i.e. **not Apache-2.0-compatible**.

**VoXR mapping.** A wake-word stage slots in *before* §2.3 and consumes exactly what §2.2 already produces (16 kHz int16). It gives a hands-free mode whose false-trigger cost is bounded and measurable, unlike Continuous mode under a VOSK grammar with no silence output. The licence path is clear and cheap for this project specifically: VoXR already generates TTS corpora for its fixtures and A/B rig, so training an Apache-2.0-clean custom wake word ("computer", "helm") from synthetic speech is an existing capability, not a new one.

**Feasibility.** openWakeWord is a Python/ONNX stack; on Quest it would need the ONNX graph re-hosted (Unity Inference Engine, or ONNX Runtime in the native bridge). Note 3.11: Inference Engine on Quest runs on the Unity main thread and does not use the NPU — for a ~few-hundred-KB KWS model at 80 ms cadence that is probably acceptable, but it must be measured, and layer-per-frame scheduling may be required.

**Risk.** Shipping openWakeWord's *pre-trained* models would put a non-commercial licence into an Apache-2.0 package. This is the finding's headline hazard.

### 3.10 Incremental hypotheses: VoXR's eager flush is a known curve — `VERIFIED` (citations); numbers `UNVERIFIED`
**Citations.** Baumann, T., Atterer, M., Schlangen, D. (2009). *Assessing and Improving the Performance of Speech Recognition for Incremental Systems.* NAACL-HLT 2009, 380–388. https://aclanthology.org/N09-1043/ · Skantze, G., Schlangen, D. (2009). *Incremental Dialogue Processing in a Micro-Domain.* EACL 2009, 745–753. https://aclanthology.org/E09-1085/

**Evidence.** Both citations verified against the ACL Anthology (venue, pages, authors). Content, from secondary summaries only (`UNVERIFIED`): incremental ASR hypotheses are unstable and constantly revised; simple incremental post-processing improves stability dramatically at the cost of timeliness — **from ~90% of hypothesis edits being spurious down to ~10% at a lag of 320 ms**. Skantze & Schlangen report that naive users preferred a fully incremental number-dictation system over a non-incremental version and perceived it as more human-like.

**VoXR mapping.** This names VoXR's §2.5 machinery. `eagerFlushOnCompleteMatch` is exactly "act on an incremental hypothesis"; **prefix hold** is exactly "add right-context lag to buy stability". The literature's contribution is (a) the framing that lag→stability is a tunable curve to be *measured*, not a constant to be guessed, and (b) the user-preference result that justifies keeping the eager path at all. Concrete action: instrument the A/B rig (§2.8) to plot, for the 699-utterance corpus, eager-flush error rate against prefix-hold duration in 40–80 ms steps, and publish the curve in `Documentation~/scoring.md` so a developer picks a hold from data instead of from the default.

**Feasibility.** Pure §2.8 tooling; no runtime change.

**Risk.** The 320 ms number is from a 2009 German-language system with a different endpointer; it is a shape, not a setting. Do not copy it.

### 3.11 On-device LLM/NLU on Quest: not in the hot path — `VERIFIED`
**Citations.** Meta Horizon OS Developers, *Unity Inference Engine For On-Device ML/CV Models*, https://developers.meta.com/horizon/documentation/unity/unity-pca-sentis/ · Wang, X.E., Sin, Z.P.T., Jia, Y., Archer, D., Fong, W.H.Y., Li, Q., Li, C. (2025). *Can You Move These Over There? An LLM-based VR Mover for Supporting Object Manipulation.* arXiv:2502.02201 · Coucke, A. et al. (2018). *Snips Voice Platform: an embedded Spoken Language Understanding system for private-by-design voice interfaces.* arXiv:1805.10190.

**Evidence.** Meta on Quest: backends are CPU and GPUCompute; **"Inference Engine doesn't use NPU or hardware acceleration"**; inference **runs on the Unity main thread and impacts the render pipeline**, mitigated by splitting inference layer-per-frame; use the smallest model (their sample contrast is YOLO-8 at 8 MB vs YOLO-medium at 146 MB); quantise to uint8 to cut load times; **"large generative models and LLMs do not perform well on devices like Meta Quest 3."** VR Mover (n=24) measures the *value* of an LLM tier — TLX **3.88 vs 4.73 (structured voice) vs 5.97 (controller)**; Borg CR10 arm fatigue **2.52 / 3.52 / 4.79**; multi-object coarse task **29.9 s / 50.5 s / 72.1 s**; SUS 6.52 / 6.04 / 5.44 — and its *cost*: **~2 s** from request to first API execution. Snips shows the classical alternative: embedded SLU with logistic-regression intent classification plus a linear-chain CRF for slots, small enough for a Raspberry Pi, with no significant gain from deep learning at this task size.

**VoXR mapping.** Three conclusions. (a) An LLM intent parser cannot replace §2.6 on Quest today: no NPU access, main-thread inference, ~2 s latency, and a 40 MB acoustic model already competing for APK budget. (b) The **structured-voice** column of VR Mover is VoXR's actual competitor set, and it already beats controllers on workload and fatigue — VoXR's pattern grammar is on the right side of that comparison. (c) The LLM belongs **offline**, at authoring time (see 3.14) and in an optional cloud/PC tier the game — not the package — owns, exactly as `anaphora-resolution-analysis.md` concludes ("hold the line: ship rule-based, keep the door open for an LLM tier later").

**Feasibility / risk.** The risk here is doing this at all on-device; the finding is mostly a stop sign with a measured price tag on it.

### 3.12 Speech as a proxy for manipulation — `VERIFIED`
**Citation.** Liang, C., Liu, Y., Mott, M., Guo, A. (2025). *HandProxy: Expanding the Affordances of Speech Interfaces in Immersive Environments with a Virtual Proxy Hand.* Proc. ACM IMWUT 9(3), Article 107.

**Evidence.** n=20. Speech describes an intended interaction; the system translates it into a sequence of virtual-hand controls. **100% task completion**, **1.09 average attempts per command**, **91.8% command execution accuracy**.

**VoXR mapping.** The 1.09-attempts figure is the useful number: it is a benchmark for "how many times did the player have to say it". VoXR should log exactly this (utterances per successfully-executed intent) in its per-session JSON debug log (§2.7) and surface it in the Editor debug window — it is a single scalar that captures the whole player-side experience and can be compared across builds and across grammar edits.

**Feasibility.** Debug-log field + Editor window column. Trivial.

**Risk.** None material; it is instrumentation.

### 3.13 Mutual disambiguation and fusion timing — `UNVERIFIED`
**Citations.** Oviatt, S. (1999). *Mutual disambiguation of recognition errors in a multimodal architecture.* CHI '99 (paper PDF fetched but not text-extractable). · Chen, F. et al. (2004). *Integration of Speech and Gesture Inputs during Multimodal Interaction.* OZCHI 2004, https://maestro.ee.unsw.edu.au/~julien/ozchi04.pdf (fetch failed: TLS hostname mismatch).

**Evidence (from secondary summaries — treat as leads, not as measured facts).** Oviatt: a multimodal architecture with two semantically rich input modes supports **mutual disambiguation and error suppression of 19–41%**, over 2,000 multimodal utterances, with *higher* gains for accented speakers. Chen et al.: gesture overlapped speech in **95% of 80 multimodal constructions** (only 5% sequential); observed intermodal lags around **0.3 s and 0.8 s**; a **~1 s threshold** is argued sufficient for fusing normal speech+gesture input; 16 of 17 multimodal users were 100% consistent in their integration style, with one habitual sequential integrator.

**VoXR mapping (the actionable part).** VOSK already emits per-word `start`/`end` timings and §2.3 enables `set_words(1)`, but the parser (§2.6) discards them for anything except confidence. Keep them, and resolve a deictic slot against a gaze/pointing ring buffer over the window **[word.start − 1.0 s, word.end + 1.0 s]**, weighting by proximity to the word rather than taking the sample at command-fire time (which can be 2 s late because of `bufferWindow`). The "consistent integrator" finding argues for making the window a per-player calibratable value rather than a constant.

**Feasibility.** Requires threading word timings through §2.5→§2.6 into the resolver — a real but contained change. Note the documented hazard that a *dropped* in-grammar word leaves no timing hole, so timings can only be trusted for words that were actually emitted.

**Risk.** Both numbers are unverified; the 1 s window should be confirmed against VoXR's own field logs before being hardcoded. Verification path: re-attempt the OZCHI PDF from an alternate mirror, and fetch the CHI '99 paper via a text-extractable source.

### 3.14 Grammar confusability linting and batch NLU evaluation — `VERIFIED`
**Citations.** Cai, Q., Hamaker, J. *Grammar confusability metric for speech recognition.* US7844456B2, Microsoft, filed 2007, granted 2010, https://patents.google.com/patent/US7844456B2/en · Amazon (2019). *Build, Test, and Tune Your Skills with Three New Tools*, https://developer.amazon.com/en-US/blogs/alexa/alexa-skills-kit/2019/10/build-test-and-tune-your-skills-with-three-new-tools1 · Amazon, *NLU Evaluation Tool API*, https://developer.amazon.com/en-US/docs/alexa/smapi/nlu-evaluation-tool-api.html · Zhu, P., Wang, Q., Agarwal, D., Partridge, K. (2025). *LLM-Synth4KWS: Scalable Automatic Generation and Synthesis of Confusable Data for Custom Keyword Spotting.* Interspeech 2025, 2675–2679, arXiv:2505.22995.

**Evidence.** *Confusability metric*: a 0–1 Grammar Confusability Metric per term, computed by generating feature vectors that approximate the acoustic properties of an input term from the built-in acoustic model, perturbing them temporally and spatially, re-running each variant through the recogniser, and aggregating; the developer gets a per-term-pair score identifying "terms with different meanings that sound too alike", to be fixed by revising vocabulary or adding prompts. *Alexa tooling*: **Utterance Conflict Detection runs automatically on every model build** and flags utterances accidentally mapped to multiple intents, with an alert in the developer console; the **NLU Evaluation Tool** batch-tests an *annotation set* (utterances → expected intents and slots) for regression testing, accuracy measurement, and detecting overtraining; a Get Metrics API feeds CloudWatch dashboards. *LLM-Synth4KWS*: LLMs generate and group confusable keywords, TTS synthesises them in varied styles; **+3.7% AUC on Speech Commands and +11.3% confusable-AUC**, with no manual data creation.

**VoXR mapping.** These are three distinct DX products VoXR is one step away from:
1. **Confusability warning** — extend the existing authoring-warning pass (§2.4 grammar build, already six warnings, already runs in player builds for three of them). The cheap version is not the patent's acoustic simulation: it is a G2P dictionary (CMUdict, BSD-style licence) plus a weighted phone-edit distance across every pair of *pattern literal runs and slot values* in the active grammar, warning when two entries with different intents fall under a threshold. This catches `switch to weapons`/`switch two weapons`, `all modes`/`fall modes` and `cease fire`/`safe five` at author time — the three named field failures none of the current warnings can see.
2. **Annotation sets** — a `VoxrAnnotationSet` ScriptableObject (utterance string → expected intent + expected slot values) run through `InjectText` (§2.8) as an EditMode test and as an Editor button. VoXR has the injection path and the fixtures; it lacks the asset and the report.
3. **Confusion analytics** — the per-session JSON debug log already records attempts; aggregate it into a "most-confused pairs" table (intent fired vs intent expected, plus unrecognised-transcript frequency) in the Editor debug window. This is the offline place where an LLM *is* appropriate (LLM-Synth4KWS's pattern): use one at author time to propose confusable variants and phonetic aliases for OOV abbreviations like `cqb`/`pdc`, which the docs currently say developers must spell by hand.

**Feasibility.** (1) and (2) are Editor/asset work with no runtime cost; (3) is a report over data already written. G2P adds a dictionary file — check licence and size, and keep it Editor-only so it never ships in the APK.

**Risk.** A confusability warning that fires on half of a real grammar is noise and will be ignored; it needs a threshold tuned against the 699-utterance corpus, where ground truth already exists.

## Interaction patterns to adopt

**Activation.**
- *Keep push-to-talk as the default and say why.* Meta's platform guidance: never open the mic without consent; implement PTT or a wake word so the mic is not always active. VoXR's docs already argue this from the VOSK-no-silence property; the platform guidance corroborates it. (Meta, *Voice Best Practices*.)
- *Add gaze-gated listening as a third mode, with the asymmetric rule.* Strict attention to open, relaxed attention once speech has begun — the player looks at the console to start an order and may look at the target while giving it. (Google, *Look and Talk*, 2022.)
- *Offer an offline wake word for genuinely hands-free games, trained from synthetic speech.* Budget it against a published operating point of <5% false rejects at <0.5 false accepts/hour. (openWakeWord.)
- *Keep commands coarse.* Voice for mode-switch and one-shot orders; never make the player repeat a vocal command per object. (Bashar et al., CHI 2026.)

**Feedback.**
- *Always show mic state* — earcon plus a visual, both. (Meta.)
- *Acknowledge at the first partial result, within a few hundred ms*, and make the acknowledgement diegetic (an officer's "Aye"), because artificial fillers measurably did not help and natural ones did. (Maslych et al., CUI 2025.)
- *Display the running transcript* as both mic-state feedback and as instruction in how the system hears the player. (Meta.)
- *Mark low-confidence words differently rather than rejecting them* — measured +12% relative error detection, 11% faster decisions. (Nowrin & Vertanen, PETRA 2025.)
- *Signal high background noise and suggest a fix.* (Meta.)

**Disambiguation.**
- *Ask instead of guessing* — VoXR already does this via `disambiguateSiblingTies`; the literature's addition is to **render the candidates** with distinct identities and uncertainty-encoded opacity, as feedforward before the answer. (Tsai et al., CHI 2026.)
- *A one-word answer must be enough.* VoXR's design (answer with the discriminating literal) matches; keep it.
- *Say when the candidate list is truncated* and offer "say the whole command again" — already in `PendingAmbiguity.IsTruncated`; make the shipped prompt honour it.

**Deixis fusion.**
- *Add a deictic slot form (`{target*}`) resolved by a game-supplied provider* covering ellipsis ("fire"), pronouns ("fire at it") and demonstratives ("fire at that"). (Bovo et al., 2025: +26.5% coreference accuracy from gaze+pointing context.)
- *Fuse on word timing, not on command-fire time*, over roughly ±1 s around the deictic word, using VOSK's per-word `start`/`end`. (Chen et al., OZCHI 2004 — `UNVERIFIED`.)
- *Let gaze/pointing bias slot-value scoring even when no pronoun is spoken* — this is the mutual-disambiguation mechanism, and it attacks in-grammar substitution errors directly. (Oviatt — `UNVERIFIED`.)
- *Prefer plural/batch reference over per-object repetition*: the measured win is at 4 targets, and there was a measured *loss* at 1. (Chen et al., 2024.)

**Confirmation and undo.**
- *Reserve explicit confirmation for destructive, non-undoable actions* (`requiresConfirmation` already exists); for everything else prefer **implicit confirmation** — restate the parse as the action happens ("Firing on hotel one") so a wrong parse is visible without adding a turn. This is standard VUI practice and is what the two-stage "which? then are-you-sure?" flow in VoXR's own docs is trying to avoid over-using.
- *Two repair attempts, then hand off* to another modality — a hard rule VoXR currently lacks (it bounds time, not attempts). (Meta, *Voice Best Practices*.)
- *Prefer undo over confirmation where the action is reversible* — a confirmation costs every correct utterance a turn; an undo costs only the wrong ones.

**Error repair.**
- *Distinguish "not heard", "not understood", and "not valid here".* VoXR's §2.4 grammar restriction currently collapses out-of-set speech into `[unk]`, so a game cannot say "that's a navigation command; you're in weapons mode". A cheap fix without leaving grammar mode: keep a *shadow* index of all registered commands across all sets and, on an `[unk]`-heavy or unrecognised transcript, check whether the transcript would have matched an inactive set — then fire a distinct `OnCommandOutOfContext` event.
- *Offer the alternative rather than only rejecting* (Meta: "offer explanations and alternatives"). VoXR's `OnUnrecognisedSpeech` carries the transcript and nothing else; carrying the best sub-threshold candidate and its score would let a game say "did you mean *cease fire*?" — the n-best repair pattern, which users prefer over respeaking the whole utterance.
- *Never silently retarget a vanished referent* — cancel and say so. (`anaphora-resolution-analysis.md`'s own failure policy; consistent with the repair literature's misunderstanding/non-understanding split.)

## Developer-experience patterns to adopt

**Authoring.**
- Keep the ScriptableObject authoring surface; add two token forms that the research justifies: `{slot*}` (deixis-enabled slot) and a set-valued slot for plural targets. Both are parser-level and preserve existing assets.
- Ship a **"what can I say?"** enumeration API over the active command set. VoXR holds the full active grammar at all times; discoverability is the second-biggest voice-UI complaint after accuracy, and the package makes games solve it from scratch.
- Follow Wit.ai's authoring loop shape: log real utterances, then add synonyms/aliases to bias recognition. VoXR's alias mechanism already exists; what is missing is the loop that *proposes* aliases from logs.

**Linting for confusability.**
- Add a seventh authoring warning: pairwise phonetic confusability across pattern literal runs and slot values, via a G2P dictionary and weighted phone-edit distance, thresholded against the existing 699-utterance corpus. Prior art: Microsoft's Grammar Confusability Metric (US7844456B2) for the concept; LLM-Synth4KWS (Interspeech 2025, +11.3% confusable-AUC) for the author-time LLM+TTS generation of confusable variants.
- Model the *reporting* on Alexa's Utterance Conflict Detection: run it automatically on every grammar build, surface it as an alert, never block.
- Extend it to propose phonetic aliases for OOV abbreviations (`cqb`, `pdc`) rather than leaving developers to guess spellings.

**Analytics.**
- Aggregate the existing per-session JSON debug logs into a **most-confused-pairs** table (expected vs fired intent; unrecognised-transcript frequency; per-slot fill failure rate) in the Editor debug window.
- Adopt **utterances-per-successful-intent** as the headline player-experience metric; HandProxy's 1.09 is a usable external reference point.
- Add per-round outcome counters (fired / barred by the leading-required-miss bar / below `minScore` / below `minConfidence` / debounced / diverted to pending) so the documented gate table in `scoring.md` becomes a measurable dashboard rather than prose.

**Testing.**
- Add a `VoxrAnnotationSet` asset (utterance → expected intent + slots) run through `InjectText` in EditMode and from an Editor button, modelled on Alexa's NLU Evaluation Tool: regression testing, accuracy measurement, and overtraining detection.
- Extend the A/B rig (§2.8) to plot the eager-flush / prefix-hold **stability-vs-lag curve** and publish it, rather than shipping a default hold nobody can justify. (Baumann et al., NAACL 2009.)
- Keep on-device Quest verification human-only; nothing in this area changes that.

## What this area cannot fix

- **It cannot make VOSK's small model hear better.** Every finding here is about what to *do* with a hypothesis, not about producing a better one. In-grammar substitutions, dropped function words, and the absence of a silence/garbage output in grammar mode are decoder problems (§2.3/§2.4) and belong to the accuracy research track.
- **It cannot calibrate confidence.** Displaying uncalibrated confidence is useful (3.6); *thresholding* on it is not, and no UX pattern changes that. `minConfidence` stays where it is until the decoder produces something better.
- **It cannot close the ~50 ms grammar-rebuild audio gap** or remove VOSK's ~0.8 s endpointing. Fillers and early acknowledgement make latency *feel* shorter; they do not make it shorter, and a diegetic filler played over lost audio is a lie.
- **Deixis cannot resolve what the game does not tell it.** Gaze/pointing fusion needs the game to publish targetable entities and their categories. VoXR can define the contract; it cannot supply the data, and a game that ignores the contract gets nothing.
- **Multimodal fusion adds a new silent-failure class.** Mutual disambiguation reduces the *rate* of wrong actions but produces wrong actions that no transcript reveals — a wrong referent looks like a correct parse. The leading-required-miss bar was earned by exactly this failure shape; deixis reintroduces a version of it on a different axis.
- **It cannot make free-form natural language work offline on Quest today.** Meta's own guidance says the NPU is unavailable to Unity inference, inference runs on the main thread, and LLMs do not perform well on Quest 3; VR Mover's LLM tier costs ~2 s. The pattern grammar stays.
- **Confirmation and repair cost turns.** Every added question is latency and vocal effort. The evidence (Bashar et al.) is that repetitive vocal interaction is quickly judged tedious, so more dialogue is not automatically better UX.
- **None of this is validated on VoXR's own field data.** The evidence base here is 73 utterances from one speaker; every number in this report comes from a different population, task and recogniser.

## Ranked recommendations for VoXR

**1. Deictic slots with gaze/pointing fusion (`{target*}` + `IVoxrDeixisResolver`).**
*Rationale.* Largest measured effect available (+26.5% coreference accuracy, Bovo et al.; 30.5–86.4% faster multi-target selection, Chen et al.), it shortens utterances so fewer words can be misheard, it *shrinks* the grammar rather than growing it, it exploits per-word timings VoXR already has, and the maintainer's own analysis has already chosen the integration point (slot-time hook in the parser, between parse and accept). Stage the delivery as that document does: ellipsis first (no grammar change at all), then pronouns/demonstratives (+~10 grammar words), then gaze.
*Cheapest validating experiment.* Phase 1 only, offline: extend the A/B rig to replay the existing 699-utterance corpus with the last-target auto-fill enabled and disabled, and count how many previously-unfilled required slots resolve correctly. Zero device time, zero new fixtures. Then a single in-headset session logging utterances-per-successful-intent with and without ellipsis.

**2. Acknowledge early, and say what state the recogniser is in.**
*Rationale.* Cheapest change with a measured VR-specific effect (Maslych et al., n=54: natural fillers significantly improve perceived response time at 4.0 s and 6.5 s; 64.8% preferred them), and it repairs the one thing VoXR's own pipeline description admits is unavoidable — a silent 0.5–2 s buffer window. Meta's platform guidance independently requires mic-state feedback and transcript display.
*Cheapest validating experiment.* In-game telemetry, no study: log time-from-first-partial-to-command-event across a play session, and count *re-utterances within 2 s of a prior utterance* (the player's "did it hear me?" behaviour) before and after adding the acknowledgement earcon. A drop in premature re-utterances is the effect.

**3. A confusability linter in the authoring pass.**
*Rationale.* Attacks the substitution failures that cost this project the most (`switch two weapons`, `fall modes`, `safe five`) at the only point where they are cheap to fix — author time — and it needs no decoder change, no device, and no runtime cost. Prior art exists for both the metric (US7844456B2) and the delivery model (Alexa's build-time Utterance Conflict Detection). VoXR already ships six authoring warnings, so the surface, the tone and the "warn, never reject" convention are established.
*Cheapest validating experiment.* Retrospective: run the candidate metric over the *existing* sample command sets and check that the three known field substitutions rank in the top confusable pairs, and that the false-positive count on the shipped sample grammar is small enough to be actionable. This is a pure offline scoring job against ground truth that already exists.

**4. Ship the ambiguity prompt, and bound repair at two attempts.**
*Rationale.* `disambiguateSiblingTies` is documented as *worse than the coin flip it replaces* without a subscriber, which means the feature is currently shipped in a state its own docs warn against. Uncertain Pointer (CHI 2026, n=60/40) supplies the visual vocabulary (per-candidate identity colour, uncertainty opacity) and Meta supplies the protocol (two repair attempts, then hand off). Adding an attempt counter also closes a real hole: `pendingTimeout` bounds time, not attempts, so a noisy room loops.
*Cheapest validating experiment.* Telemetry from one play session: count disambiguation rounds, answers received, timeouts, and repeat-asks per round, with the reference prompt enabled. Success criterion is that ≥1 answer arrives for most raised questions and that no round exceeds two asks. No user study needed to detect an unbounded loop.

**5. Gaze-gated listening mode, plus an out-of-context rejection event.**
*Rationale.* Together these fix the two activation complaints the current design cannot answer: hands-free listening without always-on false triggers (Look and Talk's strict-then-relaxed attention rule, shipped and on-device), and the documented inability to explain a wrong-mode rejection ("that's a navigation command; you're in weapons mode"), which is a shadow-index lookup, not a decoder change. Both live in §2.7 and neither touches the native bridge.
*Cheapest validating experiment.* For gaze gating: one in-headset session in a quiet room and one with game audio playing, logging false starts per minute in `GazeGated` versus `Continuous`. For the out-of-context event: pure offline — replay the existing corpus against a *restricted* active set and count how many utterances the shadow index correctly attributes to an inactive set instead of reporting them as unrecognised.
