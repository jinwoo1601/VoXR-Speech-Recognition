## Verification results

### a. Is the partial-result path really Editor-only on device?

**Checked.** `NativeBridge~/src/vosk_bridge.cpp:136-139`; `Runtime/VoxrSpeechRecogniser.cs:563`, `:578`, `:580`, `:584-589`, `:595`; `Runtime/Commands/VoxrCommandRecogniser.cs:409-410`, `:422-423`, `:501`, `:502-504`, `:520-522`, `:1328-1334`.

**Found.** The claim is **half right, and the half that is wrong matters for the API design.**

- The bridge pushes partials in every build: `vosk_recognizer_partial_result` at `vosk_bridge.cpp:136`, de-duplicated against `g_last_partial` at `:137-138`, queued non-final at `:139`. No `#if` anywhere near it.
- `VoxrSpeechRecogniser.DispatchJsonResult` (`:563`) parses the text (`:578`) and, in the non-final branch, raises `OnPartialResult?.Invoke(text)` at **`:595` — unconditionally, in players too**. Partial payloads carry no word array and none is requested (`ParseWordsFromJson` is called only inside `if (isFinal)`, `:588-589`).
- What *is* Editor-only is the command layer's subscription and its handler: `speechRecogniser.OnPartialResult += HandlePartialResult;` sits inside `#if UNITY_EDITOR` at `VoxrCommandRecogniser.cs:502-504` (and the mirrors at `:409-410`, `:422-423`, `:520-522`), and `HandlePartialResult` itself is inside `#if UNITY_EDITOR` at `:1328-1334`, where it does exactly one thing: `LastPartialResult = text;` (`:1333`).

**Exactly what reaches `VoxrCommandRecogniser` on Android today: nothing from a partial.** Only `OnResult` (finals) is subscribed (`:501`), and only finals append to `UtteranceBuffer` or run `ProbeEagerCommit` (`HandleResult`, `:566`, buffer append `:581`, eager probe `:592-599`). Because `VoxrCommandRecogniser` subscribes to `OnResult`, `needFullParse` at `VoxrSpeechRecogniser.cs:584` is true in a player, so per-word data *is* parsed for finals on device — the "Editor parses words, a player may not" divergence the audit flags (`01-code-audit.md:196`) does not bite while the command layer is attached.

**Who was right.** R3 finding 3, I1 P10, I2 M5, I3 P1 are all correct that the eager path never sees a partial. I1's phrasing "the partial handler is compiled out of players entirely" (`I1:222`) is precise. I3's P6 assumption that game code can already receive partials (`I3:49`) is also correct.

**What it changes.** The work in R17 (merged register) is smaller than I2/I3 imply on the C# side — `OnPartialResult` already flows to a player — and larger on the payload side: partials carry *text only*, so `set_partial_words` is not an optimisation but a precondition for eager condition 7 to be anything but bypassed.

### d. Re-derivation of R4's decimation-filter measurement

**Checked.** `NativeBridge~/src/downsampler.h:14-15` (`kDecimationFactor = 3`, `kFilterTaps = 15`), `:25-49` (`Process`), `:58-68` (comment + coefficient table); `Runtime/Dsp/Downsampler.cs:13-14`, `:22-27`, `:33-61`. **Found — R4 is confirmed to three significant figures:**

| f (Hz) | 1000 | 2000 | 3000 | **4000** | 5000 | 6000 | **7000** | 7500 | 7600 |
|---|---|---|---|---|---|---|---|---|---|
| dB re DC (mine) | −0.349 | −1.419 | −3.282 | **−6.083** | −10.103 | −15.975 | **−25.902** | −36.676 | −41.081 |
| dB (R4 D1 table) | −0.35 | −1.42 | −3.28 | **−6.08** | −10.10 | −15.97 | **−25.90** | −36.68 | — |

`Σh = 1.335800` → **DC gain +2.5148 dB, un-normalised** (R4: 1.3358 / +2.51 dB). Worst alias image rejection into the 0–7 kHz output band: **−29.16 dB**, at input 9440 Hz folding to 6560 Hz (R4: −29.2 dB at 9450 → 6550 Hz; the 10 Hz difference is my sweep step).

**"+2.51 dB DC, −6.1 dB @4 kHz" is CONFIRMED**, independently, from the shipped coefficients. The header comment at `downsampler.h:58-63` ("cutoff at 1/6 of sample rate (8 kHz)… ~7.5 kHz passband. **Who was right.** R4 D1/A1. The brief's §2.2 "48→16 kHz decimation-by-3 downsampler" understates it (there *is* an anti-alias filter); I1 P1 restates R4 correctly.

**What it changes.** This is the only defect in the whole research pass whose *magnitude* is measured rather than asserted, and it is now measured twice by two independent methods. The link from the response to `cease fire → safe five` remains a hypothesis with a mechanism (R4 D1 says so explicitly), so the *fix's benefit* is still unmeasured.

### e. AGC constants, and the C#/C++ divergence

**Checked.** `NativeBridge~/src/agc.h:17` (`kDefaultTargetDb = -18.0f`), `:25-26` (level attack 5 ms / release 200 ms), `:31-32` (gain attack 10 ms / release 300 ms), `:53` (gate), `:56-58` (`desired_gain`, clamps), `:77` (`kNoiseFloor = 1e-5f`), `:78-79` (`kMinGain = 0.5f`, `kMaxGain = 20.0f`), `:93-98` (`fast_tanh`). `Runtime/Dsp/Agc.cs:13`, `:17-18`, `:23-24`, `:26-29`, `:66`, `:72-74`, `:106-112`.

**Found. Every constant matches: `1e-5` noise floor, `0.5`/`20` gain clamps, −18 dBFS target, 5/200/10/300 ms time constants — identical in both files.** The divergence the audit reports is confirmed exactly where it says:

- `agc.h:53` — `if (smoothed_level_ < kNoiseFloor)` → gate on the **envelope**.
- `Agc.cs:66` — `if (absX < NoiseFloor)` → gate on the **instantaneous sample**.
- `Agc.cs:61-64` says "See divergence note in the class summary." **The class summary is `Agc.cs:1-6` and contains no such note** (`01-code-audit.md:497` says the same; I1 P2 cites `Agc.cs:1-6`, the audit cites `:1-13` — the summary block ends at line 6, so I1 is the more precise citation).

**Arithmetic check of R4 A2's "+26 dB in a pause" (C++ path).** With real room noise the envelope settles above `1e-5`, so `desired_gain = 0.1259 / level` saturates at `kMaxGain = 20` (+26.0 dB). The gain smoother is a one-pole with the 300 ms release coefficient, so `g(t) = 20 − 19·e^(−t/0.3)`: g = 10× at **t = 0.3·ln(1.9) = 193 ms**, g = 19× at **t = 0.3·ln 19 = 883 ms**. R4's "~10× within ~190 ms and ~19× within ~0.9 s" is **CONFIRMED by derivation**.

**One consequence neither R4 nor any ideation report states, and it bites the experiments they propose.** Under *digital* silence (`x == 0`), the two implementations behave **oppositely**: C# freezes the gain immediately (`absX < 1e-5` is true at once), while C++ keeps adapting until the 200 ms-release envelope decays from 0.1259 below `1e-5`, i.e. for `0.2·ln(12590) ≈ 1.9 s`, during which the gain ramps toward 20×. The fixture corpus is built from digital silence — `Tests~/Fixtures/generate.py:28-29` (`LEAD_SILENCE_S = 0.3`, `TAIL_SILENCE_S = 1.0`) and a 3.0 s `silence_negative` case (`Tests~/Fixtures/audio/manifest.json:183-189`). **So the WSL harness (C++) and the Editor WAV-replay tests (C#) present materially different signals to the decoder on exactly the silence-then-event fixtures R4's recommendation 2 and I1's P2 propose building.** Unifying the two implementations is not cosmetic; it is a precondition for that experiment meaning anything.

## Contradictions between reports

**C1 — Does `set_grm` remove the audio gap?** R1 rec. 1 (`R1:269`, `R1:11`) says the gap is "an implementation artefact of `vosk_bridge_set_grammar`'s free-and-recreate, not a property of VOSK" and can go "→ ~0". I3 P5 (`I3:159`) picks R2 and calls R1 unsupported.
**Resolution: R2/R4/I3 are right, and R1 is refuted by local code alone, independent of what `SetGrm` does upstream.** VoXR's gap is a composite whose *first* term is `vosk_bridge_stop` stopping the capture device (`vosk_bridge.cpp:285`) and joining the recognition thread (`:287-288`), driven from `GrammarManager.ForceApply`'s stop→set→start (`GrammarManager.cs:43-52`). No decoder API can shorten a term that lives in VoXR's own bridge. Evidence: `vosk_bridge.cpp:283-294`, `:346-353`, `GrammarManager.cs:38-53`.

**C2 — Are the endpointer setters callable at runtime?** R3 finding 2 and rec. 1 (`R3:77`, `R3:264`) build a recommendation on `vosk_recognizer_set_endpointer_delays`. R1 (`R1:12`, `R1:65`) and `02-verified-facts.md` say the symbols are not exported.

Evidence: export table of `Runtime/Plugins/Android/arm64-v8a/libvosk.so`; `NativeBridge~/include/vosk_api.h:33-35` declares them anyway, which is a latent link-time trap.

**C3 — Is the 699-row A/B corpus decoder-in-the-loop?** R6 (`R6:9`, `R6:271`) says no. Project memory `grammar_ab_rig` says a `GenerateGrammarJson` change was measured "against the real decoder in WSL". I1 flags the conflict as open question 1 (`I1:407`); I2 M0 and I3 P12.1 assume R6.

That makes the ordering *AGC gate before VAD* — the cheap fix removes the amplification, the expensive one removes the audio. Neither I2 nor I3 could see this.

**Resolution: half right.** The doc paragraph (`Documentation~/command-recognition.md:282`, `:286`) does read as prose. But the Inspector tooltip at `VoxrCommandRecogniser.cs:66-71` asserts something stronger and more specific — "the **measured** gap between results runs ~1.9–2.1s". So the number is not baseless; its provenance is undocumented and unreproducible. The correct complaint is provenance, not absence.

**C7 — Does the fixture corpus contain a negative?** R6 gap 4 (`R6:262`) says "Not one fixture is 'audio that must produce nothing'" and then, in the same sentence, describes `silenceSeconds` producing digital silence.
**Resolution: internally inconsistent; the literal claim is refuted** (`manifest.json:183-189`), the substantive one stands (3 s of digital silence, no non-speech events, no hours).

**C8 — Is a per-word confidence display worth building?** R5 3.6 (`R5:102`) reports +12 % relative error detection from confidence marking; R2 finding 2 and R6 §11 both raise the live possibility that grammar-mode `conf` carries near-zero information (`R2:96`, `R6:210`).
**Resolution: not a contradiction — a sequencing constraint, and I3 P6 states it correctly** (`I3:211`): compute NCE/ECE first, ship the listening states regardless, ship the marking only if NCE > 0.

**C9 — Does R4's decimation finding change I2's substitution hypotheses?** I2 M3 (phonetic matching) and M2 (grammar weights) attribute `cease fire → safe five` and `all → fall` to lexical/LM causes and propose text-layer remedies. R4 D1 supplies a *front-end* mechanism for the same two pairs — /s/–/f/ discrimination lives in the 4–7.6 kHz band that arrives 6–26 dB low.
**Resolution: R4's mechanism is the cheaper hypothesis and must be tested first.** It does not refute M3; it means **M3's recoveries-vs-inventions ratio would be measured against a front end that is itself broken**, so a phonetic-tolerance threshold tuned today would be tuned to compensate for a filter defect. R25 is therefore demoted below R14 in the ranking, which I2 could not have known.

**C10 — Does R4 change I3's latency chain?** I3 says nothing below depends on R4 (`I3:5`).
**Resolution: it does, in two places.** (i) I3 P4's VAD kill criterion 3 ("a VAD that eats the first 160 ms eats the verb") is compounded by R4 A4: the AGC's 10 ms attack out of a 20× silence gain distorts the first 20–30 ms of every utterance anyway, so I3's first-word-retention measurement must control for the AGC arm or it will attribute the AGC's loss to the VAD. (ii) I3 P2's endpointer sweep and R4's front-end work both change what the endpointer sees; R2's "sweep one knob at a time" rule (`R2:442`, echoed at `I3:88`) must extend to cover the DSP arm too.

**C11 — Should the parser get more permissive?** I2 M3 and M8 push toward learned/fuzzy matching; R2's own risk note (`R2:314`) and the shipped rule set (`scoring.md:213-215`, `:242`) push the other way.
**Resolution: I2 handles this correctly** — M3 makes the anchor exact-only, which is *stricter* than today — but I2 open question 2 (`I2:325`) asks whether the bar's uniformity is negotiable given positive evidence from N-best or phonetics. **That is a request to relax a maintainer ruling and must be presented as such**, not as a design decision inside R12 or R25.

**C12 — R1's decoder-migration optimism vs R6's evidence floor.** R1 rec. 3 proposes a Zipformer bake-off on "the existing corpora"; R6 §3 shows the synthetic/real gap is **architecture-dependent** (+6.3 to +18.7 pp), i.e. a TTS-only comparison between two decoders compares them on an axis that is itself the confound.
**Resolution: R6 wins.** The offline bake-offs (R41) remain worth running as *screens*, and their output must never be used to rank two decoders. I1's decoder-decision table already says "unconstrained first" but does not carry R6's caveat into the ranking; it should.

## Ranked shortlist

**1 — R7, the OOV vocabulary gate.** First because it is the only item whose entire mechanism is now verified end to end and whose cost is a day: the symbol is exported (h2), it is already declared at `vosk_api.h:21` so no header work is needed, the Kaldi warning string is present in the shipped binary, and `vosk_set_log_level(-1)` at `vosk_bridge.cpp:215` is what hides it. It unblocks nothing technically, but it converts the single worst developer experience in the package — a word silently deleted from the grammar with no signal at any layer — into a named Editor error, and it is the natural home for R8's proposals later. **Kill criterion:** if a grammar containing `cqb` does not produce a warning naming `cqb` while one containing `cease` stays quiet, the gate is not wired to the same string the grammar generator emits. **Cheapest experiment:** an EditMode test asserting exactly that pair, in the host project, no device.

**2 — R2, the two missing session-log fields.** Second because it is S-effort and every accuracy decision below it is currently unauditable in the direction that matters. A barred round returns before the `VoxrCommand` is even constructed (`VoxrCommandParser.cs:2742-2746`), so `rejectReason: no match` conflates "nothing matched" with "everything matched and was barred", and only round winners are logged, so the near-miss distribution R26 and R27 both need does not exist. Fixing the culture-formatted numbers in the same change makes the log machine-readable for R39. **Kill criterion:** if adding the fields costs any allocation on the poll path, the `ZeroAllocPollPathTests` pin fails and the fields must move behind a sampled writer. **Cheapest experiment:** replay one fixture that is known to be barred and assert `barred: true` appears with no accompanying command.

**3 — R9, the model cache version key.** Third because it is a correctness bug today (verified in c: any model change under the same folder name is silently ignored, and `conf/model.conf` is not even in the validity check) and a hard gate on R10 and R11. Without it the first upgrade after a tuned conf ships keeps the old decoder configuration on every device that already ran the app, and the resulting field data would be attributed to the new setting. **Kill criterion:** none — this is a bug fix; the only design question is whether the key goes in the zip name or a stamp file. **Cheapest experiment:** extract, mutate `conf/model.conf` in the source zip, re-run, and assert the extracted copy changed.

**4 — R1, join the two instruments.** Fourth, not first, because h1 shrank it: the push-audio harness already replays real audio through the real decoder (`NativeBridge~/harness/main.cpp:1-8`), and the parser rig already stages the real parser (`stage.sh:15-25`); what is missing is the pipe between them and a scorer with slot partial credit (`VoxrBatchTestRunner.cs:230-233` is exact equality). It gates R10, R11, R12, R13, R14's acceptance, R21, R22 and both R41 screens — everything decoder-, grammar- or DSP-side. **Kill criterion:** if the joined rig cannot reproduce the harness's committed `expectations.json` baseline byte for byte on the 16 fixtures, the plumbing is wrong and no number from it may be quoted. **Cheapest experiment:** run the existing harness and the existing rig on the same fixture and diff the transcript each believes it parsed.

**5 — R5, start the human recording campaign.** Fifth in order but it should be *started* alongside item 1, because it is the long pole and it is the only item that cannot be delegated. Everything from item 6 down is an accuracy or latency change that R6's arithmetic says cannot be ranked on the present evidence base — two speakers, one of them a single Piper voice, sixteen acoustic cases. Sealing half at generation time costs nothing extra and is the only chance to get an unspent holdout before the next tuning cycle consumes it. **Kill criterion:** none; the only failure mode is starting late. **Cheapest experiment:** record two speakers × the existing 16 phrases first, and check whether the *existing* pass rate moves at all — if it does, the corpus is already telling you something.

**6 — R11, the endpointer profile.** Sixth because it is the largest latency cut available with no native code, the mechanism is now corroborated in the binary (`/conf/model.conf` plus vosk's V1 defaults appear as literals), and the only route exists because the runtime setters are not exported (C2). It unblocks nothing but it is where 500–1000 ms lives. **Kill criterion:** if, on the joined rig, the rise in finals-per-utterance multiplied by the buffer window exceeds the endpointer time saved, the profile is a mean-latency regression and is rejected; and any change to transcript *content* rather than segmentation is an immediate stop. **Cheapest experiment:** sweep `rule2 ∈ {0.5, 0.35, 0.25}` on the fixture corpus in WSL, reporting finals-per-utterance and end-of-audio→final delay **in sample time** — the harness pushes faster than real time.

**7 — R15, unify the two AGCs (then gate).** Seventh because verification e turned this from a tidiness item into a measurement blocker: the C++ and C# gates are not merely different, they are *opposite* on digital silence, and the fixture corpus is built from digital silence (`generate.py:28-29`, `manifest.json:183-189`). Until they agree, R14's A/B, R16's first-word-retention test and R4's silence-then-cough fixtures all measure a signal the device never sees. The speech-gating and re-targeting half then follows, with R16 supplying the gate. **Kill criterion for the gate half:** if silence-then-command fixtures show first-word retention falling at any false-trigger reduction, the gate is eating the verb and the bar converts that into silence. **Cheapest experiment:** run the same WAV through the C++ harness and the C# Editor path and diff the post-AGC samples — if they differ, the unification is mandatory before anything else in the front end.

**8 — R14, the decimation filter.** Eighth because the defect is the only one in the entire research pass measured twice by independent methods (d), the fix is a coefficient table in two files, and the CPU cost is under 0.2 % of one core. It is not higher because its *benefit* is a hypothesis (R4 says so), because it shifts every score in every corpus, and because accepting it needs items 4 and 5. It must be evaluated jointly with R15: normalising the DC gain removes +2.51 dB the AGC currently absorbs. **Kill criterion:** command-level accuracy on the acoustic corpus does not improve, or regresses, at equal thresholds after a threshold re-sweep. **Cheapest experiment:** old vs new coefficients through the joined rig, same everything else — then re-pin `scoring.md`'s published numbers with `DocCheck.cs` rather than editing them.

**9 — R17, eager-commit on partials — instrumented, not implemented.** Ninth because it is the only proposal that removes *both* dominant timers and the only one that can reach the 200–300 ms target, and because verification a shows the C# side is smaller than I2/I3 assumed (partials already reach a player at `VoxrSpeechRecogniser.cs:595`) while the payload side is larger (`set_partial_words` is a precondition, not an optimisation). It ranks here and not higher because its whole case turns on a number nobody has: how often a partial yields a `Commit` the final contradicts. **Kill criterion:** if that contradiction rate exceeds ~1 % at the chosen stability setting, the proposal is dead and the answer is items 6 plus R16. A second, non-negotiable kill: any double-fire in the commit-watermark tests. **Cheapest experiment:** instrument the harness to log, per fixture, every partial and the `TryEagerCommit` verdict it *would* have produced, and compare against the final's verdict. Read-only, no package code.

**10 — R12, the N-best screen.** Tenth because it attacks all three named substitution classes at the only place the correct words still exist, and because b now says the load-bearing risk is corroborated but unproven: `Recognizer::NbestResult` and the `{"alternatives" : …}` literal are both in the shipped binary, and the payload shape carries no `conf`. Verification h3 makes that risk worse than either report states — the `-1` path silently disables **both** the `minConfidence` gate (`VoxrCommandRecogniser.cs:980`) and eager condition 7 (`VoxrCommandParser.cs:4510-4512`). It depends on R10 (at `--lattice-beam=2.0` the alternatives will be near-duplicates) and on R23 landing first so the confidence replacement extends rather than replaces. **Kill criterion:** on the corpus, rows where an alternative supplies a command the 1-best did not must clearly exceed rows where an alternative *invents* one; if not, drop it. **Cheapest experiment:** `set_max_alternatives(3)` in the desktop harness only, with a copy of `model.conf` at `--lattice-beam=6.0`, counting recoveries against inventions. Decide what replaces `minConfidence` **before** writing any C#.

**11 — R30, listening states and the early acknowledgement.** Eleventh because it is the cheapest change in the document that a player would notice, it changes nothing about what fires, and verification a shows it needs no bridge work at all: partials already reach a player build. Every latency number above stays where it is; what changes is that the wait stops being silent. **Kill criterion:** if the acknowledgement is followed by a rejection often enough to be confusable, the two signals must be distinguishable or the ack is worse than silence — measure the pair, not the ack. **Cheapest experiment:** in-game telemetry, no study: count re-utterances within 2 s of a prior utterance (the player's "did it hear me?" behaviour) before and after.

**12 — R4, the negative corpus and an operating point.** Twelfth because the project's scariest failure has never had a rate. The 2.0.0 bar was justified with a false-*reject* argument on a positive-only corpus (`scoring.md:242`, 9 lost against 39 suppressed), and the only negative audio that exists is 3 s of digital silence. Five hours of game audio, breathing, room tone and out-of-set chatter converts the phantom-command class from an anecdote into a number that can be regressed, and supplies the guardrail that stops any recall-improving change below from silently costing safety. **Kill criterion:** none — but if it becomes a second harness beside the existing one rather than inside it, it will not be used. **Cheapest experiment:** assemble one hour first, replay it through the joined rig with a live command set, and count fires; if the rate is zero at one hour, the corpus needs to be harder before it needs to be longer.

- **R16 (VAD)** — deferred behind the free probe: classify the existing 73-utterance field logs into non-speech versus speech-like false triggers first; that upper-bounds the whole win before an ONNX Runtime dependency (~15 MB) or a licence read on TEN VAD is taken.

## Redesign verdict

**Replace VOSK now? No, and the case for staying is stronger after verification than before it.** Roughly half the shipped C API is unused, and every one of the unused calls is confirmed present in the exact binary in the repository (h2): `set_grm`, `set_max_alternatives`, `set_partial_words`, `model_find_word`, `new_spk`/`set_spk_model`. The decoder's own configuration surface is a text file it demonstrably reads (`/conf/model.conf` appears as a literal in the binary) shipping at a third of vosk's own lattice beam. Two of the three most-cited failure classes now have a *front-end* hypothesis with a measured mechanism (d, e) that no decoder swap addresses. Against that, R1's accuracy headroom is real (9.85 % vs 3.94 % LibriSpeech test-clean at comparable int8 size) but every RTF in the pass is on non-Quest silicon, the NPU is unavailable to third-party Quest apps, no English VOSK Zipformer2 model exists, no small English streaming zipformer-CTC model exists for the HLG path, and R6 §3 shows a TTS-only comparison cannot rank two architectures anyway. Keep exactly two options alive as bounded offline screens (R41) and revisit when R5 exists.

**Rewrite the parser now? No — and the ideation reports agree, which is worth stating because it is the one place all three converge.** I2 M8 explicitly rejects the wholesale noisy-channel rewrite and enumerates why: it would subsume S1–S8, S14–S15, A1 and both thresholds, while having to keep the bar (E6–E8, E11), completeness (R4), selection determinism (A4) and the tie machinery (T1–T15) as hard constraints anyway — and it would invalidate five named 699-row measurements to be justified on a corpus that cannot certify a five-point change. Verification adds two reasons. First, the parser's real defects found here are *local and cheap*: a text-keyed confidence dictionary (h3), an unrebased word-timing array (h3), and a slot-initial `NumberSequence` that disables coverage grammar-wide. Second, the rule set is not merely documented but *pinned* — `scoring.md` publishes two enumerations as exhaustive and five corpus measurements as justification, and `DocCheck.cs` exists to hold them. A rewrite is a documentation project with a code project attached. Do R23, R24 and R27's screen; leave the model alone.

**Introduce decoder/audio interfaces now? Only the C# ones the register already needs, and not the abstraction for its own sake.** There is no interface anywhere in `Runtime/` (`01-code-audit.md:160`), and the decoder choice is a `#if UNITY_EDITOR_WIN` fork at nine sites. That is genuinely bad, but an `IDecoder` seam buys nothing until something needs to sit behind it, and nothing on the shortlist does. What *is* justified now is far smaller and concrete: unify the duplicated DSP (R15) so there is one implementation rather than a seam between two divergent ones, and let R12 introduce the first internal interface (`IHypothesisSource`) only because the alternatives loop needs a test seam. R28's full seam waits for a committed consumer — R29, R41, or a migration — exactly as I1 P9 says.

**Handle-based native ABI now? No.** The one-recogniser-per-process rule is a published contract with specified non-owner behaviour (`api/speech-recogniser.md:7-42`), its mechanical cause is file-scope statics (`vosk_bridge.cpp:20-42`), and the subsystem it would rewrite has no automated coverage at all — no unit tests for `ring_buffer.h`, `result_queue.h` or the bridge state machine, and the WSL harness exercises only the desktop build. It is L-effort, user-invisible, and its two would-be consumers are themselves deferred (R29 blocked, a migration unranked). One narrower change *is* worth taking when the bridge is next opened for another reason: `vosk_bridge_push_audio` returns a negated error code unlike every other binding, preserved by a comment at `BridgeNative.cs:55-58`, and `vosk_bridge_has_result` has no binding at all. Fix or delete those with whatever native work lands first; do not open the bridge for them alone.
