# VoXR "next level" research brief (2026-09-05)

This brief is the shared context for a fan-out of research and ideation agents. Read it fully before starting. It is written for an agent that has NOT seen this codebase before.

## 1. What VoXR is

VoXR is a Unity package (`com.jinwoo1601.voxr`, v2.0.0, Apache-2.0, ~11k lines C#, ~1.4k lines C++) for **offline voice commands in XR games**. Primary target: **Meta Quest 2/3/Pro (Android arm64, Snapdragon XR2 Gen 1/2, CPU-only inference, no GPU/NPU used)**. Secondary: the Unity Editor on Windows (live mic via `libvosk.dll`) for iteration without a headset. The maintainer's own game is a VR "FTL-like" spaceship command game: the player speaks tactical orders such as "launch missiles target hotel one", "orient heading two seven zero", "cease fire", "switch to navigation", "close distance cqb target alpha three".

Repository root: `/mnt/d/Game Development/VoXR-Speech-Recognition`. All paths below are relative to it.

## 2. Pipeline as built (audio → command event)

1. **Capture**: Android `AudioRecord` via JNI, 48 kHz mono float, ~20 ms chunks, into a lock-free ring buffer (`NativeBridge~/src/audio_capture_audiorecord.cpp`, `ring_buffer.h`). Editor: `UnityEngine.Microphone` at 48 kHz (`Runtime/EditorMicBackend.cs`).
2. **DSP**: 48→16 kHz decimation-by-3 downsampler (`downsampler.h`, `Runtime/Dsp/Downsampler.cs`), then an AGC with asymmetric attack/release targeting −18 dB (`agc.h`, `Runtime/Dsp/Agc.cs`; Quest 3 mic gain is low). Float → int16.
3. **Decoder**: **VOSK** (Kaldi nnet3 chain model) with the **small English model `vosk-model-small-en-us-0.15`** (~40 MB unpacked; `libvosk.so` is 8.9 MB). A dedicated recognition thread (`NativeBridge~/src/vosk_bridge.cpp`) reads 4096 samples (~85 ms at 48 kHz) per iteration and calls `vosk_recognizer_accept_waveform_s`. Partial results (JSON) and final results (JSON with per-word `conf`, `start`, `end`) are queued to C# and polled on the Unity main thread. `vosk_recognizer_set_words(1)` is on. **Only the 1-best hypothesis is used** — no N-best (`max_alternatives`), no lattice, no acoustic scores, no phone-level output.
4. **Grammar mode (default)**: the decoder is built with `vosk_recognizer_new_grm(model, rate, grammarJson)`. The grammar JSON is a flat list of strings generated by `VoxrCommandParser.GenerateGrammarJson` (`Runtime/Commands/VoxrCommandParser.cs` ~line 3076): each pattern's contiguous run of required literals as one multi-word phrase entry ("switch to navigation") PLUS every single word, every slot value / alias key as a phrase plus its words, the digit vocabulary when a NumberSequence slot exists, follow-up words (confirm/cancel), and `[unk]`. VOSK treats this list as a bag-of-phrases language model: any sequence of entries can be decoded in any order. Changing the active command set or a dynamic slot's values **frees and recreates the recognizer** → a ~50 ms+ "audio gap" on Quest 3 where speech is lost (`Documentation~/command-sets.md` "The Audio Gap"). Free-speech mode (full vocabulary) exists but is documented as unreliable for commands.
5. **Utterance buffer** (`Runtime/Commands/UtteranceBuffer.cs`): merges consecutive VOSK finals within `bufferWindow` (default 0.5 s, up to ~2 s used in the field) because VOSK's endpointer splits mid-command pauses. Optional **eager flush** fires a complete, unambiguous, unextendable command before the window closes.
6. **Parser** (`VoxrCommandParser.cs`, ~4900 lines, string-token level): patterns are token arrays of literals, optional literals (`?please`), and typed slots (`{target}` choice slots with aliases, `{heading}` NumberSequence, dynamic slot value providers, optional slots `{?quantity}`). Matching uses a sliding start to skip preamble; score = matched/elements with per-element miss costs, a **coverage** charge for utterance words no pattern explains, an **admission** rule (a candidate must match at least as many required elements as it misses), a **leading-required-miss bar** (a round whose winner missed its FIRST required element fires nothing — shipped in 2.0.0 after a phantom command executed a maneuver order in the field), a deterministic selection order (score → span → literal count → registration order), **sibling-tie** detection (two intents differing at one required word) that can enter a pending "ask the user" state, and **sequential extraction** of several commands per utterance. Thresholds: `minScore` 0.6, `minConfidence` 0.4 (min per-word confidence over matched tokens). Then debounce (`commandCooldown`) and **pending commands** (missing required slot, `requiresConfirmation`, disambiguation) resolved by follow-up speech. See `Documentation~/scoring.md` and `Documentation~/command-recognition.md` for the exact rules and the worked examples; these rules were each earned by a measured field failure, so a redesign must say which of them it subsumes and how.
7. **UX layer**: `VoxrPushToTalkController` (hold-to-talk, continuous, toggle modes), `OnPartialResult`, `OnCommandRecognised/Pending/Confirmed/Cancelled`, `OnUnrecognisedSpeech`; Inspector-authorable ScriptableObject command sets; Editor debug window and a per-session JSON debug log (`Library/VoxrDebugLogs/`).
8. **Verification**: text injection (`InjectText`), a WAV-replay fixture corpus (TTS-generated, 48 kHz, replayed through the real DSP+VOSK pipeline, `Tests~/Fixtures`), a push-audio bridge mode for fixture replay, an offline A/B rig on a 699-utterance TTS corpus against the real decoder, Unity EditMode+PlayMode suites in a host project. On-device Quest verification is human-only.

## 3. Observed failure modes (all measured; see `KNOWN_LIMITATIONS.md` and `Planning~/voxr-system-context.md`)

- **In-grammar substitutions**: "switch to weapons" → `switch two weapons`; "all modes" → `fall modes` when `fall back from target` is in the grammar; "cease fire" out of set → `safe five`. Grammar mode narrows candidates but does not sharpen posteriors.
- **Dropped short words**: "a", "to", "on" dropped or swapped; **an in-grammar word VOSK drops leaves no token and no timing hole** (field-verified: neighbouring alignments absorb it) — so the parser cannot see that a word went missing.
- **No silence/garbage output in grammar mode**: coughs, hums, breathing decode as short in-grammar words ("on", "from", "four") → false triggers. `[unk]` appears only for out-of-grammar speech.
- **OOV**: abbreviations ("cqb", "pdc") → `[unk]`; developers must spell phonetic aliases by hand.
- **Flat confidence**: "two" is ~0.50 confidence regardless of clarity; confidence is not calibrated, so `minConfidence` cannot be raised without rejecting number sequences.
- **Endpointing**: VOSK's VAD splits on ~0.8 s pauses; the buffer window trades latency for reassembly. Eager flush partially recovers latency for unambiguous complete commands.
- **Wrong-mode rejection has no explanation**: with a restricted grammar the out-of-set word becomes `[unk]`, so the game cannot say "that's a navigation command; you're in weapons mode".
- **Phantom commands** from stranded tails ("time to target track one two four four" → also fired `intercept_target`): fixed by the bar, at the cost of some legitimate leading-miss recoveries (zero observed in 73 field utterances).
- **Grammar rebuild gap** (~50 ms+) on set switching / dynamic slot change.
- **Single recogniser per process** (file-scope C++ state, no handle in the C ABI).
- Field evidence base: 10 sessions, 73 utterances, 361 words from one speaker on Quest; TTS fixture corpora.

## 4. What "next level" means to the maintainer

Three axes, all in scope, refactor/redesign explicitly allowed:

- **Accuracy**: fewer substitutions/drops on the words that matter; real out-of-grammar/noise rejection; calibrated confidence; robustness to the Quest mic, exertion, and game audio; fewer phantom or wrong commands.
- **Latency**: time from end of speech (or from the point the command is determinable) to the command event; endpointing that does not split commands; no audio gap on grammar/set changes; fast, streaming, incremental command hypotheses.
- **User experience**: for the player (feedback, confidence display, error recovery, disambiguation, wake/PTT modes, multimodal deixis with gaze/pointing in VR) and for the developer (authoring commands, tuning, testing, understanding why a command did or did not fire).

Hard constraints: fully offline; must run on Quest 2/3 CPU alongside a VR game at 72–90 fps (budget: a fraction of one core, tens of MB RAM, APK size matters — the current model is ~40 MB); Unity 6, C# plus a C++ native bridge; Apache-2.0-compatible licensing; English first, multi-language desirable later; existing public API and authored command assets should have a migration path.
