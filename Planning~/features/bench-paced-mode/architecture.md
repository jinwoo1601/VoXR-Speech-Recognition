# feat-bench-paced-mode — Architecture

Realizes `Planning~/features/bench-paced-mode/requirements.md` (Track **Full**; S1, F1–F10, the §6 NFRs, §10 items 1–5), the paced-mode feature of design `audio-bench` (§6), built on `bench-fast-replay` (PR #198). A paced run is fast mode's run, unchanged, followed by two passes of a new `--paced <samples>` mode of the verdict harness — the matched-chunk pass at 16384 samples and the 20 ms pass at 960 — each pushing the same samples as fast mode at real speed on an absolute schedule, stamping every push and pop on `steady_clock` beside the bridge's `consumed`, and tracing the consumed counter; the rig's `--bench run` reads the three dumps, refuses every number unless fast mode's self-check and the matched-chunk check pass, feeds the 20 ms timeline to the staged recogniser at its wall-arrival times, and appends a paced section to fast mode's report. The governing driver is **a split that can be trusted** (requirements §3; adr-0001): the paced passes run fast mode's binary, case sequence, model copy and padding, differing only in when a push is made, so the matched-chunk check isolates pacing; and nothing on Command 3's pinned run, its pins or the bridge interface moves (F10).

## Context & scope

Fast mode is the harness's own `--dump` run (`NativeBridge~/harness/main.cpp` `RunHarness` :316): per case the clip through `PushAll` in 16384-sample pushes (:177-207), the front-end wait (`WaitFrontEnd` over `WaitFrontEndBy`, :245-272), `48000 + RingBuffer<float>::kCapacity` samples of padding (:532; capacity 65536, `ring_buffer.h` :15), the drain to full consumption (:591-608), stop and reset; `DrainResults` dumps each result with its `consumed`/`origin` (:122-166). The bridge's recognition thread reads up to 4096 samples (`vosk_bridge.cpp` :62, :104), advances `g_consumed` at once (:111), runs the front end and the decoder (:126-150), and sleeps 10 ms only when the ring is empty (:106-109); a push is clamped to the ring's free space (:352-360). The rig's `--bench run` (`ab-rig/Bench.cs` `FastRun` :184-322) checks truth and the pin, drives each case through `Joined.ScoreRecogniser`, stamps offsets (`Stamps` :482-518) and writes `report.md`. Before this feature nothing recorded wall time (design §1).

**Owns:** the harness's `--paced` mode; `ab-rig/BenchPaced.cs`; `bench.sh --paced`; the paced report section. **Edited:** `NativeBridge~/harness/main.cpp` (the flag, the paced loop, the paced dump keys under the flag only), `NativeBridge~/harness/README.md` (usage and a note); in the rig `Bench.cs` (paced arguments, the `Stamps` selection extracted, toys), `BenchReport.cs` (the paced section; fast text unchanged), `JoinedInput.cs` (reads the paced keys), `Program.cs` (`BenchVerbs` gains `matched-check`, :154), `Rig.csproj` (the paired `flag bench` comment), `stage.sh` (copies `BenchPaced.cs` under `recogniser`, :113-116), `bench.sh`. **Untouched (F10):** `NativeBridge~/src/`, the bridge's public interface (`vosk_bridge.h`), `expectations.json`, the committed WAVs, `Runtime/`, Command 3's command line; `Joined.cs`, `JoinedRecogniser.cs`, `JoinedScorer.cs`, `BenchMetrics.cs`. **Out:** conditions, voices, A/B, repeats and spread (requirements §2, §7).

## Decision register

- **Paced push path — a `--paced <samples>` mode of the verdict harness (§10 item 1; F1, F10; adr-0002).** `main.cpp` gains a flag accepted only with `--dump`; under it each case runs the harness's own sequence — the front-end lifecycle check (:347-409), the grammar (:411-418), start, clip, front-end wait, padding, drain, stop, reset (:425-485) — with the clip and the padding's first second pushed by a paced loop modelled on `PushAll`, while `DrainResults`, `DumpCase`, `DumpCaseEnd`, `WaitFrontEnd`'s condition, the padding vector and `PushAll` itself (for the flush) are reused. Without the flag no line of the default path runs differently, so Command 3's pinned run and `expectations.json` are untouched and the bridge is consumed only through `vosk_bridge.h`. *Why:* adr-0002 has fast and paced modes share one code path; with fast mode's binary, case order, model copy and padding, the matched pass differs from fast mode only in when pushes are made, so its check isolates pacing; C++ `steady_clock` and a spin loop hold a 20 ms schedule and a microsecond poll that a managed runtime does not promise. Cost accepted: each phase that edits `main.cpp` triggers Command 3, its arm64 build included (`.claude/bindings/unity.md` Command 3). *Rejected:* the C# rig through a P/Invoke binding to `build-windows/bin/vosk-bridge.dll` — no `NativeBridge~/` change and Command 3 never triggered, but the case sequence (:340-485) would be copied into C#, with `VoxrWavReader`'s sample conversion standing in for `wav_reader.cpp`'s, so a matched-check failure could not tell pacing from copy drift, and GC and tiered-JIT pauses would ride the schedule; it would win if Command 3's cost came to dominate the gates. A new executable linking `vosk-bridge` — it triggers Command 3 through `CMakeLists.txt` anyway, and the helpers it needs live in `main.cpp`'s anonymous namespace (:31-219), so it copies them or splits `main.cpp`, editing it regardless. **Ruled at PLAN 2026-11-09:** "Command 3 untouched" (requirements §2 Out 4; design §4; adr-0002 *Consequences*) is read as its command, its pinned run and its pins unchanged, as §10 item 1 allows ("a mode of the harness ... with Command 3's pinned run unchanged"); `main.cpp` gains the flag-gated mode, triggering Command 3 at Phase 2 and at G2.

- **Pacing — an absolute schedule from the case's wall origin, held by a yield-spin loop (F1, F2, F9).** Right after `vosk_bridge_start_push` returns, the harness reads `steady_clock` once: t0, the case's wall origin. A push ending at case sample b is due at t0 + b ÷ 48000 s (the clip and the padding count as one sample sequence): a chunk leaves when its last sample would have been captured, as a mic delivers it. Between pushes the loop spins with `std::this_thread::yield()`, popping results through `DrainResults` and polling `vosk_bridge_get_consumed()`; a push is made at the first poll at or after its due time, and a short write is retried on the next poll. Every due time counts from t0, so lateness never accumulates; a late push is recorded, never a stop. *Why:* a sleep-based wait on Windows wakes at the system timer's granularity, not at a chosen instant; spinning keeps the pop stamps and the consumed trace at poll resolution, which the decode-time rule needs. Cost: one core busy during the paced passes. *Rejected:* `sleep_until` per push (granularity); `timeBeginPeriod` (a `winmm` link in `CMakeLists.txt`, and still coarser than one read's processing); relative sleeps (drift). **Amended 2026-11-09:** a stall is 10 s without progress, never lateness — do not seed a stall clock from a due time. `PushPaced` polls first and seeds its clock with `max(due, at)`, as the other paced loops seed theirs with the poll's stamp; seeded with `due`, a chunk over 10 s late whose first write was short ended the run with exit 2.

- **Flush padding in the paced passes (§10 item 3; F1, F6).** Each paced case pushes exactly fast mode's samples: the clip, paced; the clip-end front-end wait, `WaitFrontEnd`'s condition (`vosk_bridge_get_frontend_stats` input = clip samples, :185-206) checked inside the spin loop so no result waits on a sleep; the padding's first 48000 samples, paced on the same schedule; a spin until `consumed` equals the pushed count; then the remaining ring-capacity samples through `PushAll`, unpaced, and the harness's own drain, stop and reset. A result whose `consumed` exceeds the clip plus 48000 is a flush result: its audio stamp holds, its wall stamp prints `unpaced`. *Why:* identical samples keep the stop's tail final at fast mode's `consumed`; an endpoint can fall past the clip's 1.0 s tail (`Tests~/Fixtures/generate.py` `TAIL_SILENCE_S` :35; rule 4's `min-trailing-silence=1.0`, `expectations.json` `modelConf` :564), and a final popped from an unpaced push carries a compressed wall stamp — the split requirements §3 protects. *Rejected:* pacing the clip only (meets §4.6's run time; a late endpoint's compute part would be wrong); pacing all the padding (its ring-capacity part only drains the ring, `NativeBridge~/harness/README.md` :108, and would add that much real time per case). Cost: *Performance*, below.

- **Stamps — taken in the harness, recorded in the dump as integer µs from t0 (§10 item 5; F2, F9).** Under `--paced` only: the `header` gains `pace` (the chunk, in samples); each `result` gains `wall`, read in `DrainResults` at its pop; each `case-end` gains `pushes`, one `[end sample, due, made]` per push, and `reads`, one `[consumed, at, pushed]` per observed change of the consumed counter, `pushed` being the harness's count at that poll. The schema stays 2: `JoinedInput.ReadDump` ignores unknown keys (`JoinedInput.cs` :9-11), so `--joined` reads a paced dump as today; the bench's reader requires every paced key exactly when `pace` is present, and refuses a `pace` other than the one it expects. The harness records and the bench computes: lateness, offsets, the split and the factor are C# arithmetic over these integers, so the plan's toys cover them. *Why:* adr-0001 stamps at the bench's push and pop on the bridge's existing interface; integers print alike in C++ and C#, as fast mode's samples do. *Rejected:* a stamp in the bridge's queue (`result_queue.h` :9-14; an interface change, a scope stop); schema 3 (today's joined reader would refuse paced dumps, for no gain); aggregates computed in C++ (no toy reaches them); seconds as floating text.

- **Wall reference for end of speech — the schedule (§10 item 4; F2, F3).** End of speech on the wall clock is t0 + e ÷ r, e the `end` of the case's last `speech` segment and r the case's `sampleRate`: the instant its last sample is due. A stage's wall offset is its wall stamp minus that; its audio offset is `consumed` ÷ r minus e ÷ r, as fast mode's (`Bench.Stamps` :292-345). The compute part, wall offset − audio offset, is therefore wall stamp − `consumed` ÷ r: how long after its last consumed sample was due the result was popped — queueing, decoding and the reader's 10 ms idle sleep (`vosk_bridge.cpp` :106-109) included. Each value is computed from integers (µs and samples) and printed in seconds at three decimals, as fast mode's offsets. *Why:* the schedule is the mic's clock; push lateness stays its own column (F9) and, on a loaded machine, shows in the compute part as §6 asks. *Rejected:* the actual push of the chunk holding sample e (a late push would shrink the compute part); the first push's actual time as origin (same fault).

- **Decode time for the real-time factor — the matched pass's back-to-back reads (§10 item 2; F4).** The recognition thread advances `g_consumed` the moment it reads (`vosk_bridge.cpp` :104-111), then runs the front end, the decoder and the queueing (:126-159), and reads again at once while the ring holds samples. So a read's processing time is visible from the consumed counter alone: a change at t_k that left samples in the ring (`consumed` below the trace's `pushed`) ends at the next change, t_{k+1}. In the matched pass each 16384-sample push yields four 4096-sample reads, the first three measurable; the 20 ms pass's reads usually empty the ring, so the factor is taken from the matched pass. Decode time is the sum of measured intervals and audio duration the sum of their reads' samples ÷ r, over reads within the clip; the corpus factor is summed decode ÷ summed audio, not a mean of ratios (as corpus WER). A change larger than one read (4096: two reads merged between polls) is counted as a merged change, and the intervals on either side of it are excluded; a case with no measured read prints `undefined (no measured reads)`. The label says what it is: the recognition thread's per-read work, front end included, on fast mode's read grid, desktop-only. *Why:* no bridge interface change (design §4): the bench's push count, its clock and the existing counter suffice. *Rejected:* a case's wall time to drain (paced arrival dominates, not decode); an unpaced timed pass (a third pass where F4 says paced runs, its starvation by the push back-off, :177, unmeasured); pop time minus the counter's change (only reads that emit a result; biased); a bridge timer (scope stop). **Ruled at PLAN 2026-11-09:** the real-time factor is measured in the matched pass from back-to-back reads on the consumed counter.

- **Matched-chunk check — the matched dump against the fast dump, before any number (F6; R2; adr-0001, adr-0003).** Per case, paired by name: the non-empty finals equal ordinally (`Joined.FirstDifference`, `Joined.cs` :823), so a missing or extra final fails; each final's `consumed` within 4096 of fast mode's final at the same index; the first partial — the first non-final with a non-empty `partial`, fast mode's rule — within 4096 of fast mode's, or absent in both. On any failure the bench prints each differing case with both sides, writes no report and exits 3. It runs after the readers, the truth check and fast mode's self-check, before any world. `--bench matched-check` runs exactly that prelude and this check (Phase 2's probe; the F6 mutation on a `.scratch/` copy of the matched dump, one stamp moved by more than 4096 within the reader's order rules); `--bench run` runs it first. *Why:* F6's rule; the matched pass shares fast mode's push size, so read boundaries match (adr-0003). *Rejected:* checking the pins only (no stamps compared); per-stage tolerances (one decoder read is ruled, design Status).

- **Command stage — the 20 ms timeline at wall-arrival times, through the recogniser layer unchanged (F5; adr-0002).** Per case the bench builds a wall view of the 20 ms dump case: its results in order, each `Consumed` set to its `wall` and `SampleRate` to 1000000, so `JoinedRecogniser.ScoreCase`'s `consumed ÷ sampleRate` (:282) is the pop time in seconds and `DeliveryFrame` (:79) delivers it on the first 90 Hz frame at or after it; the view goes through `Joined.ScoreRecogniser` and `Joined.AppliedGrammarGuard` (:467) as fast mode's case does. The command event's wall offset is its first fire's frame k_p over 90 minus e ÷ r, computed as fast mode's (`Bench.cs` :337-341); its audio offset is fast mode's; its compute part, paced − fast, is (k_p − k_f) ÷ 90 exactly, since e cancels; `none` where either side does not fire. The recogniser's own frame cost is the frame clock's, not measured (adr-0002). *Why:* F5 defines the stage; reusing the drive keeps one classifier (bench-fast-replay *Timeline feed*). *Rejected:* a time-source parameter on `ScoreCase` (a joined-rig change for what a view supplies); an audio-time 20 ms world for the command row (F5 fixes its compute part as paced − fast). **Ruled at PLAN 2026-11-09:** the command row's audio column is fast mode's, its compute part paced − fast, while the first-partial and final rows take their audio stamps from the 20 ms pass, so that §4.5's "compute part (wall − audio)" and F5's "paced time − its fast time" hold together.

- **The 20 ms finding (F7; adr-0003; R3).** Per case, fast mode's non-empty finals against the 20 ms pass's, and fast mode's class against the wall view's class; each differing case listed with both sides, or `none`. It is never a check: it never stops the run, and the 20 ms pass's harness exit 1 (its finals off the pins, or a front-end digest moved by read size) continues as fast mode's exit 1 does. *Why:* adr-0003. *Rejected:* WER or calibration for the 20 ms pass (R3).

- **Report — fast mode's, unchanged, then the paced section (F8; F3–F5, F7, F9; adr-0008).** `--bench run` without paced arguments runs today's path and `BenchReport.Build` writes today's bytes (F10). With the paced arguments (the matched and 20 ms dumps and their harness exits) the title and the `Mode:` line name paced mode, the header adds both passes' harness exits and the matched check's line, fast mode's sections follow unchanged, then a paced section: its label — wall time and the compute part measure this machine; a single run, its run-to-run spread not measured (R1); never compared across machines; per case and stage (first partial, each final, command event) the audio offset, the wall offset and the compute part; per case the factor, its measured reads and merged changes and the largest push lateness in ms; the corpus factor; the 20 ms finding. *Why:* F8; adr-0008's axes side by side. *Rejected:* a separate paced report (F8 extends fast mode's); wall columns in fast mode's tables (breaks the byte-identity).

- **Code home — `BenchPaced.cs` beside `Bench.cs`, recogniser stage only (bench-fast-replay *Code home*).** New `BenchPaced.cs` holds the matched check, the wall view, stamps on both clocks, the factor, lateness and the finding. `Bench.cs` keeps the dispatch and fast mode; its `Stamps` result selection (first non-empty partial, non-empty finals) becomes one internal method both modes call, fast toys 24-25 unchanged. *Why:* one selection rule, so fast and paced stamps cannot drift — the review lesson that reversed bench-fast-replay's copies (*As-built deltas*, review fix). *Rejected:* a paced copy of the selection; the paced run inside `Bench.cs` (one file carrying two modes' runs).

- **Run order — `bench.sh --paced` (§4.2).** confgen; the fast harness `--dump` run; stage and build; the `--paced 16384` pass; `--bench matched-check` (exit 3 stops before the 20 ms pass); the `--paced 960` pass; `--bench run` with all three dumps. A harness exit 2 in any pass stops with its stderr and names the case from that pass's report (a push the bridge refuses, §6). The chunk, 960, is a named constant in `bench.sh`, provisional → the tuning pass; a named configuration passes the same pin copy to all three harness runs (bench-fast-replay *Configuration*). *Why:* fast mode first with its checks unchanged (§4.2), and a failed matched check costs one pass, not two. *Rejected:* one `--bench run` after both passes (a check failure found only after the 20 ms pass).

- **Known-value toys (F2–F4, F6, F9; §9).** Each is a `metrics-check` row after the 26 that exist (`Bench.cs` :400-515), r = 48000, e = 48000 (end of speech at 1000000 µs on the wall clock). T1, the stamps and the split: a partial at `consumed` 43200 popped at `wall` 912000 gives audio −0.100, wall −0.088, compute +0.012; a final at 72000 popped at 1534000 gives +0.500, +0.534, +0.034; in a 96000-sample clip, a final at 150000 gives audio +2.125 and wall `unpaced`. T2, the command stage: fast first fire at frame 135, wall-view fire at frame 144 give audio +0.500, wall +0.600, compute +0.100. T3, the factor: one 16384-sample push, `reads` [4096 at 10000, 8192 at 18600, 12288 at 27000, 16384 at 35600], `pushed` 16384 throughout, gives 3 measured reads, 25600 µs over 12288 samples, factor 0.1000; a second case with `reads` [4096 at 0, 8192 at 12800], `pushed` 8192, gives 0.1500, and the corpus over both 0.1125 (the mean of ratios would be 0.1250); `reads` [4096 at 0, 12288 at 5000, 16384 at 9000] give no measured read, 1 merged change, `undefined (no measured reads)`. T4, lateness: pushes due 20000, 40000, 60000, made 20150, 40020, 61200, give 1.200 ms. T5, the matched check: fast partial 24576 and final "fire" at 49152 against matched 28672 and "fire" at 53248 pass; a matched final at 53249 fails naming the case; matched finals ["fire", "missiles"] fail (an extra final); a partial in one dump only fails.

## Non-functional realization

- **Performance (§6).** Two paced passes, each the corpus's audio plus 48000 paced padding samples (one second, `main.cpp` :532) per case. Re-derived to check §4.6's figure, from the requirements' 193 s of audio (§4.6) and 52 cases (F1): 2 × (193 s + 52 × 1 s) = 490 s, about 8.2 minutes beyond fast mode; the paced padding second (register, *Flush padding*) is kept because §3 protects the split. **Ruled at PLAN 2026-11-09:** the run time is about 8.2 minutes, requirements §4.6 and §6 corrected on this branch. One core spins through both passes.
- **Input boundary (§6).** Fast mode's named stops hold, unchanged. The harness stops with exit 2 on `--paced` without `--dump` or with a chunk outside 1–16384, and on a push the bridge refuses (the case's `errors`, then exit 2), which `bench.sh` reports with the case named. The bench stops with exit 2, named, on a paced dump missing a paced key, a `pace` other than expected, or a case set differing from the fast dump's. A value with no basis prints `undefined` with its reason (`no measured reads`) or `unpaced` (a flush result's wall), never a number.
- **Degraded dependencies (§6).** A loaded machine shows as push lateness (F9) and in the compute part, never as a stop; the harness's stall guards stay the only liveness backstops — fast mode's (`PushAll` :194) and the paced loops' (`PushPaced`, `WaitFrontEndPaced`, `SpinConsumed`), each 10 s of wall time without progress. Wall numbers are labelled never comparable across machines.
- **Determinism.** Fast mode's sections stay deterministic and byte-identical to `main`'s (F10). The paced section is one run's measurement: wall values and the factor move run to run; the matched check's verdict rests on read boundaries within one read, as adr-0003 rules; the 20 ms pass's audio stamps may move by a read where a poll lags.
- **Untouched (F10), by construction and by check.** The default path is flag-gated, so the fast dump's records carry no new key. Phase 1 captures a fast-only `report.md` from the unmodified tree before any edit, the baseline "main's on the same inputs"; every later gate compares a fast-only run to it byte for byte, and runs Command 3 where `main.cpp` changed. `git diff main` stays empty for `NativeBridge~/src/`, `vosk_bridge.h`, `expectations.json`, the WAVs and `Runtime/`.
- **Hot paths and the device.** None touched: `NativeBridge~/src/**` and `Runtime/**` unchanged; the harness sits in the layout's Tests slot. No bridge source or `.so` changes, so no on-device check is owed by this feature.

## Build plan

Lowest risk first: rig-only arithmetic and readers with no native edit, then the harness mode, which carries the one native edit and the riskiest assumption — that real-speed pushes at fast mode's size reproduce fast mode's stamps — probed at its own gate, then the integration, the report and the closing gate. Every rig phase runs the recipe's DocCheck and a joined `main`-versus-`main` run at both layers, 0 flips, for the rig files it edits; every run is from Claude's Git Bash.

## Risks, tradeoffs & open questions

- **The split may not hold — the riskiest assumption, probed at Phase 2.** If the matched pass misses fast mode's stamps by more than a read — the front end's output depending on read size, or the reader's 10 ms sleep splitting a push across reads — that is adr-0001's kill criterion: a stop for the human and a design reopen, never a wider tolerance or a rounding fix.
- **Read separability.** The factor needs each change of the counter seen alone; a stalled poll (the bench thread pre-empted) merges reads, which are counted and kept out of the factor. If the probe finds many, the factor's coverage shrinks and the report shows it; raised at Phase 2's gate.
- **What the factor measures.** The recognition thread's per-read work with the front end, over three of every four reads of the matched pass, on fast mode's read grid — decode speed fed fast mode's reads, not the 20 ms pass's behaviour, whose lag is the compute part. Labelled; **Ruled at PLAN 2026-11-09** (register, *Decode time*).
- **The spin loop perturbs the machine it measures** (a busy core, shared caches, clock boost). Desktop-only, single run, never across machines — the labels F8 requires.
- **Pop resolution and flush results.** Stamps are at poll resolution, with `DrainResults`' dump write on the pop path, both landing in the compute part; a non-empty final past the clip plus one second prints wall `unpaced`, and if the green run shows one, the paced padding length is a tuning-pass question.
- **Command 3 per native phase.** Phase 2 edits `main.cpp`, so Command 3 runs there, arm64 included, and again at G2; a regression on the default path shows as a Command 3 failure or a fast-only report that differs from the baseline.
- **Coupling and drift.** A change to `JoinedInput.ReadDump`, the shared `Stamps` selection, the 90 Hz clock or `JoinedScorer.Classify` changes both modes' stamps or classes. The tolerance rests on `kReadChunkSize` (`vosk_bridge.cpp` :62); a change there changes the check's meaning. TTS-only evidence never ranks decoders (C12).
