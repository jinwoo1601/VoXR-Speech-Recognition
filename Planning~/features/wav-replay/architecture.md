# WAV Replay (Tier B) — Architecture

This feature builds the editor WAV-replay seam, fixture corpus, and PlayMode acoustic regression tests that realize [[requirements]] F1–F10 (Tier B of [[automated-verification]] §6). The governing architectural driver is the pair of hard constraints from the locked design: **replayed audio must traverse the identical processing pipeline as live microphone audio** (pre-DSP entry, F2), and **the live path must pay zero overhead when playback is unused** (F4). Everything below is shaped by satisfying both at once: the pipeline is extracted into a shared `ProcessChunk`, and playback gets its own capture source and pump that never touches the live `Tick()`.

## What this implements

| Requirement / decision | Code work | Section |
|---|---|---|
| F1 replay through full pipeline, same events | `ProcessChunk` extraction + playback mode in `EditorMicBackend`; internal accessors on `VoxrSpeechRecogniser` | §Components, §Flow |
| F2 pre-DSP entry, AGC engages | playback feeds raw 48 kHz floats to the same Downsampler→AGC→int16→Vosk chain | §Flow |
| F3 wrong-format rejection | `VoxrWavReader` format gate + `StartPlayback` rate validation | §Components (D-3, D-4) |
| F4 zero overhead off-playback | separate `TickPlayback` pump; mic `Tick()` behavior-identical after the code-motion extraction; playback-only buffer allocation | §NFR realization (D-2) |
| F5 containers + suite covers corpus | `VoxrAudioTestCase` / `VoxrAudioTestSuiteAsset`; manifest is the suite source | §Components (D-5) |
| F6 corpus content/format/amplitude | `Tests~/Fixtures/audio/tts/` corpus + EditMode corpus-verification tests | §Fixture corpus |
| F7 reproducible generation | `Tests~/Fixtures/generate.sh` + `manifest.json` (single source of truth) | §Fixture corpus (D-5) |
| F8 PlayMode regression tests | `Tests~/Runtime/VoxrWavReplayTests.cs` + `DemoGrammar` test fixture | §Tests |
| F9 skip off-platform | replay tests compiled under `#if UNITY_EDITOR_WIN` | §Tests |
| F10 faster than real time | test-driven pump: each editor frame processes one 100 ms chunk | §NFR realization (D-2, D-6) |

## Context & scope

The Windows-editor audio path lives entirely in `Runtime/EditorMicBackend.cs` (`EditorMicBackend`, `internal sealed`, whole file `#if UNITY_EDITOR_WIN`): `Tick()` (`:291-367`) currently couples mic capture (`Microphone.GetPosition` + `AudioClip.GetData` ring-buffer windowing) with the processing pipeline (`Downsampler.Process` → `Agc.Process` → `FloatToInt16` → `vosk_recognizer_accept_waveform_s` → result/partial dispatch). `VoxrSpeechRecogniser` owns the single backend instance (`Runtime/VoxrSpeechRecogniser.cs:108`) and pumps `Tick()` from `Update()` when recognising; results dispatch through `DispatchJsonResult` (`:400`) into the public events, which `VoxrCommandRecogniser` consumes. There is no backend interface and no factory — platform selection is `#if UNITY_EDITOR_WIN`/`#else` inline in the recogniser; this feature stays inside that structure rather than introducing one (non-goal: no shipped-runtime redesign).

This feature owns: the seam inside `EditorMicBackend`, two internal test accessors on `VoxrSpeechRecogniser`, the WAV reader and audio test-data containers in `Runtime/Testing/`, the fixture corpus + generation script in `Tests~/Fixtures/`, and the new tests in `Tests~/`. It deliberately does not own: the demo command grammar (`Samples~/CommandRecognition/` — replayed, not modified), `VoxrBatchTestRunner` (stays text-in), the native bridge, or anything Android (Tiers C/D).

## Decision register

- **D-1 — `ProcessChunk` boundary: capture stays in `Tick()`, everything from the downsampler down moves out.** `Tick()` keeps the mic-specific half (first-tick rate check, `Microphone.GetPosition`, ring-wrap copy into `_workBuffer`, `_lastSamplePos` advance) and ends by calling `ProcessChunk(_workBuffer, available, dispatch)`; `ProcessChunk(float[] samples, int count, EditorJsonDispatcher dispatch)` owns Downsampler → RMS → AGC → RMS → `FloatToInt16` → `accept_waveform_s` → final/partial dispatch with the partial-dedup cache. *Why:* this is exactly the source-agnostic segment (`EditorMicBackend.cs:335-366`); the design names the extraction as its own addition and its purpose — capture source and pipeline "cleanly separable" (§6.1). Error firing stays in `Tick()` (the only error in the current method is the mic-rate check, which is capture-side). *Rejected:* extracting a larger method that includes buffer windowing (drags mic state into the shared path); passing `fireError` into `ProcessChunk` (nothing in the processing segment fires errors today — don't widen the signature speculatively). **Buffer lifecycle (the segment's logic is source-agnostic; its buffers are not):** `ProcessChunk` consumes the shared field buffers `_downsampledBuffer`/`_int16Buffer` (`:42-45`), today allocated only by mic `Start()` (`:177-178`) — `StartPlayback` must (re)allocate those same shared fields, sized for the fixed 4800-sample chunk by the same sizing rule `Start()` uses (downsampled ≥ ⌈4800/3⌉ plus the decimator's carry margin); playback-only state (source sample buffer, read position) is separate new fields. Mic `Start()` keeps sizing them for the mic clip as today, so either mode entered later re-sizes correctly.
- **D-2 — Playback gets its own pump (`TickPlayback`), driven by the caller; the live `Tick()` is not modified beyond the D-1 extraction.** `StartPlayback` arms a playback buffer; the consumer (the PlayMode test) calls `TickPlayback(dispatch)` repeatedly, each call feeding one fixed-size chunk through `ProcessChunk`, returning `false` once the buffer is exhausted and the final result has been flushed. *Why:* (a) F4/v3.4's locked wording is "zero additional branches in non-recording mode", extended to playback — a separate pump means literally zero added work on the live path, not just a cheap branch; (b) a test-driven pump makes pacing deterministic and frame-rate-independent (D-6) and yields faster-than-real-time replay (F10) for free — each editor frame pushes 100 ms of audio. *Rejected:* a mode-branch inside `Tick()` reading from the playback buffer (v3.4's literal wording "Tick() reads … instead of AudioClip.GetData") — it puts a per-tick branch on the live path, ties playback pacing to `Update()` cadence and `IsRecognising` state (which would force `Microphone.Start` semantics into playback), and the design's own `ProcessChunk` rationale already reframes the seam as capture-vs-pipeline separation. **Design-fidelity note:** we read §6.1's "Tick() reads successive chunks" as describing the tick-cadence contract (successive fixed chunks per tick through the same pipeline), satisfied by `TickPlayback`; the sentence is v3.4 carry-over narrative, not a method-name mandate. Flagged for the human to ratify at PR/G2 — if read instead as a locked method-level mandate, that is a design-reopen conversation, not a silent patch.
- **D-3 — Seam API: `internal bool StartPlayback(float[] samples, int sampleRate, Action<VoxrBridgeErrorCode,string> fireError)`.** Validates `sampleRate == SourceSampleRate` (48000, `EditorMicBackend.cs:23`) and rejects with an error naming both rates (mirroring the existing mic-rate error text pattern at `:303-306`); rejects if the mic is running (and `Start` rejects if playback is active) — the two capture sources are mutually exclusive; `SetGrammar` and `Reset` likewise reject while `IsInPlayback` (they free/recreate the recognizer mid-stream otherwise; grammar is applied before playback starts). Resets the **full** pipeline state on entry — `Downsampler`, `Agc`, the partial-dedup cache (`_lastPartialBuffer`/`_lastPartialLength`, `:361-364`, otherwise reset only by mic `Start()`/`Reset()`), and the Vosk recognizer — so every replay starts identical regardless of prior-replay history (determinism NFR). `StartPlayback` over an active playback disarms and re-arms with fresh state, and an `internal StopPlayback()` disarms without flushing — so a mid-replay test failure can't wedge the shared backend for the rest of the suite (teardown calls it defensively). *Why the name:* v3.4 offers both `PlaybackFrom` and `StartPlayback`; `StartPlayback` mirrors the existing `Start`/`Stop` lifecycle verbs on the class. *Rejected:* validation only in the WAV reader (the seam must be self-guarding — F3's test feeds a wrong-rate buffer directly); an `AudioClip`-taking overload (see D-4).
- **D-4 — Fixtures load via our own byte-level WAV reader (`VoxrWavReader`), never Unity's audio importer.** `internal static` reader in `Runtime/Testing/`, parses canonical RIFF/PCM, accepts exactly 48 kHz/mono/16-bit and returns `float[]` in [-1, 1]; every other format is a distinct, message-bearing rejection. Tests resolve fixture paths to physical paths via the package location (editor-only API under `#if UNITY_EDITOR`). *Why:* Unity's default WAV import is lossy (Vorbis) and importer settings/`.meta` churn would silently alter the "pre-DSP" bytes — the corpus's whole value is bit-stable input; a byte-level reader keeps fidelity and needs no import pipeline. *Rejected:* `AudioClip`-based containers (v3.4's `public AudioClip clip` sketch) — import-settings drift, meta noise in `Tests~`, and PlayMode dependency on importer state.
- **D-5 — The phrase manifest is the single source of truth: generation script and test suite both read `Tests~/Fixtures/audio/manifest.json`.** Each entry carries the TTS input (`phrase`, or phrase segments + gap for the split-command case), output file, target peak, and the expectations (`expectedIntent`, `expectedSlots`, `expectNoCommand`, category). `generate.sh` synthesizes from it; the PlayMode suite materializes it into a `VoxrAudioTestSuiteAsset` via `FromJson` (same `JsonUtility` round-trip pattern as `VoxrTestSuiteAsset`, `Runtime/Testing/VoxrTestSuiteAsset.cs:23-29`) and runs every entry — F5's "suite covers the corpus" is true by construction. *Why:* one file keeps phrases, audio, and expectations from drifting apart; adding a fixture is one manifest line + one script run (DR-2's stated rationale). *Rejected:* a committed binary `.asset` suite (requires an editor to author, GUID/meta churn, duplicates the manifest); hand-listed paths in test code (F5 forbids).
- **D-6 — Fixed 4800-sample (100 ms) playback chunk.** `TickPlayback` always feeds 4800 samples (the tail chunk may be short). *Why:* live mic chunk size varies with frame rate; a fixed chunk makes replay results machine- and frame-rate-independent — the determinism NFR outranks simulating frame jitter, and 100 ms is a typical Vosk feed granularity. *Rejected:* frame-dt-sized chunks (nondeterministic across machines), whole-file single feed (bypasses the chunked-streaming behavior the live path exercises, incl. partial-result emission).
- **D-7 — `Voxr` prefix for the new types (`VoxrAudioTestCase`, `VoxrAudioTestSuiteAsset`, `VoxrWavReader`).** *Why:* the codebase is fully rebranded (`Vosk`→`Voxr`, commit `a77bca8`); the design doc cites v3.4's `Vosk*` names only as provenance. Requirements OQ1 flags this; a `Vosk`-prefixed pair would be the only unrebranded types in the package. *Rejected:* literal v3.4 names. **Flagged for the same PR/G2 ratification as D-2** — §6.1 does literally print the `Vosk*` names (and D-6's fixed chunk rides §6.1's "advancing by the same chunk size per tick"); all three are one bundled reading of §6.1's carried-over wording for the human to ratify.
- **D-8 — The tests carry their own copy of the demo grammar (`DemoGrammar` helper in `Tests~/Runtime/`), pinned by comment to `Samples~/CommandRecognition/CommandDemo.cs:33-158`.** *Why:* `Samples~` isn't compiled into any assembly the tests can reference, and moving the grammar into `Runtime/` would change the shipped package for a test's convenience (non-goal). This makes a third hand-synced copy of the grammar (code + assets + tests) — accepted and flagged in Risks; the corpus manifest phrases are keyed to the shipped `CommandDemo.cs` text. *Rejected:* referencing `Samples~` sources (not compiled); promoting the demo grammar into the package runtime (shipped-surface change).
- **D-9 — End-of-playback flushes the recognizer's final result explicitly.** When the buffer is exhausted, `TickPlayback` calls the Vosk final-result API once (the same flush `Stop()` performs at `EditorMicBackend.cs:188-211`, minus `Microphone.End`) and dispatches it, then reports completion. Fixtures still carry a ~1 s silence tail so utterance finalization happens acoustically first in the normal case. *Why:* a deterministic end-of-input signal — tests never hang waiting on VAD. *Rejected:* relying on trailing silence alone (couples test termination to VAD tuning).

## Components & responsibilities

- `Runtime/EditorMicBackend.cs` (`EditorMicBackend`) — gains `ProcessChunk` (extracted, D-1), `StartPlayback` / `TickPlayback` / `StopPlayback` / `IsInPlayback` (D-2, D-3, D-9), playback source state (sample buffer + read position) allocated only in `StartPlayback`, which also (re)allocates the shared pipeline buffers per D-1. Mic members otherwise unchanged except the new mutual-exclusion guards (`Start` rejects during playback; `SetGrammar`/`Reset` reject during playback — D-3).
- `Runtime/VoxrSpeechRecogniser.cs` (`VoxrSpeechRecogniser`) — two `internal` editor-only accessors so tests can drive the seam through the real dispatch chain: the backend instance (`_editorBackend`, `:108`) and the JSON dispatcher (`EnsureEditorDispatcher()` → `DispatchJsonResult`, `:400-434`). No public or behavioral change.
- `Runtime/Testing/VoxrWavReader.cs` (`VoxrWavReader`, new, internal static) — RIFF/PCM parse + format gate (D-4). Consumed by tests; independent of Unity audio.
- `Runtime/Testing/VoxrAudioTestCase.cs` (`VoxrAudioTestCase`, new, `[Serializable]`) — fixture path (relative to `Tests~/Fixtures/`), `expectedIntent`, `expectedSlots` (reuses `ExpectedSlot`, `Runtime/Testing/VoxrTestCase.cs:35`), `expectNoCommand`, `description`, `category`.
- `Runtime/Testing/VoxrAudioTestSuiteAsset.cs` (`VoxrAudioTestSuiteAsset`, new, `ScriptableObject`, `[CreateAssetMenu(menuName = "VoXR/Audio Test Suite")]`) — batches cases; `ToJson`/`FromJson` mirroring `VoxrTestSuiteAsset` (`Runtime/Testing/VoxrTestSuiteAsset.cs:23-38`) (D-5).
- `Tests~/Fixtures/generate.sh` (bootstrap wrapper) + `Tests~/Fixtures/generate.py` (the TTS → resample → normalize → pad worker) + `Tests~/Fixtures/audio/manifest.json` (new) — reproducible corpus generation (D-5, §Fixture corpus); `Tests~/Fixtures/audio/tts/*.wav` committed output; `Tests~/Fixtures/audio/human/` empty provenance folder.
- `Tests~/Runtime/DemoGrammar.cs` (new, test helper) — the demo grammar copy (D-8).
- `Tests~/Runtime/VoxrPlaybackSeamTests.cs` (new, PlayMode, `#if UNITY_EDITOR_WIN`) — seam-behavior smoke tests: wrong-rate and empty-buffer rejection, silence end-flush, AGC engagement, mic/grammar mutual exclusion, stop-without-flush, re-arm semantics.
- `Tests~/Runtime/VoxrWavReplayTests.cs` (new, PlayMode, `#if UNITY_EDITOR_WIN`) — the manifest-driven acoustic regression suite (`Replay_ManifestCase`) plus the Phase 3a probe; nothing else.
- `Tests~/Editor/VoxrFixtureCorpusTests.cs` + `Tests~/Editor/VoxrWavReaderTests.cs` (new, EditMode) — corpus format/peak/category verification over the committed WAVs (F6's mechanical check) and byte-level reader unit tests (crafted headers: 44.1 kHz, stereo, 8-bit, float PCM, truncated).

## Data contract & runtime flow

**Replay flow (one test case):** manifest entry → `VoxrAudioTestSuiteAsset.FromJson` → resolve fixture to a physical path (package root + `Tests/Fixtures/`) → `VoxrWavReader.Read` → `float[]` @48 kHz → `recogniser` initialised with the real model, `VoxrCommandRecogniser.Configure(DemoGrammar…)` + `SetActiveSets` applies the grammar to the backend (`GrammarManager` → `SetGrammar`, the same path live audio uses) → `backend.StartPlayback(samples, 48000, fireError)` (resets DSP + recognizer state) → test coroutine loops `backend.TickPlayback(dispatcher)` (one 4800-sample chunk per call through `ProcessChunk`: Downsampler → AGC → int16 → `accept_waveform_s`; partials and finals dispatch through `VoxrSpeechRecogniser.DispatchJsonResult` exactly as live audio) → buffer exhausted → final-result flush (D-9) → `TickPlayback` returns false → test asserts the captured `OnFinalResult`/`OnResult`/`OnCommandRecognised` payloads against the manifest expectations.
**Live flow (behavior-identical):** `Update()` → `Tick()` → capture window → `ProcessChunk` → same pipeline. The live path's structural changes are exactly two: the pipeline segment sits one (inlinable) call away, and `Start()` gains the reject-if-playback guard (D-3).
**Contract crossing the seams:** the manifest schema (JSON, `JsonUtility`-compatible: `{ file, phrase | segments+gapSeconds+silenceSeconds, peak, category, expectedIntent, expectedSlots[], expectedTranscript, description }` — empty `expectedIntent` means expect-no-command, per the as-built delta) is the cross-tier contract — Tier C's WSL harness and Tier D's on-device suite consume the same corpus + manifest (design §7.3, §8.3). Changing its shape after merge touches those features.

## Fixture corpus

Committed at `Tests~/Fixtures/audio/tts/` (16-bit/48 kHz/mono ≈ 96 KB/s; ~15 fixtures × 3–5 s ≈ 5 MB, inside the requirements footprint; `release.yml` strips `Tests~` from the published package). Generation: `generate.sh` bootstraps a python venv installing pinned `piper-tts` (1.6.0) + `soxr` + `numpy` — all verified in this WSL; neither `sox` nor `ffmpeg` exists here, so resampling is pure-Python via `soxr` and the only system dependency is `python3`. It downloads the pinned voice (`en_US-lessac-medium`, verified: outputs 22 050 Hz mono 16-bit), then per utterance entry: synthesize → resample 22.05 → 48 kHz (`soxr`) → peak-normalize to the entry's target within 0.04–0.4 → pad ~0.3 s lead / ~1.0 s tail silence (split-command entries: synthesize segments, join with the entry's gap) → write WAV. Silence-negative entries synthesize no speech — digital silence (or sub-0.005-peak noise) for the entry's duration, skipping peak normalization (which is undefined on silence). Regeneration is *functionally* reproducible (same phrases, format, peaks — F7's suite-passes bar), not bit-identical across machines (ONNX inference may differ in low bits); the committed WAVs are the regression baseline.

## Non-functional realization

- **Zero live-path overhead (F4):** structural, not measured — playback has its own pump method (D-2), so the mic tick gains no branch, no field read, no allocation; playback buffers allocate inside `StartPlayback` only (v3.4's allocation rule extended). The guard is structural review (the extraction is pure code motion; the only live-path additions are the D-3 mutual-exclusion guards on `Start`/`SetGrammar`/`Reset`, none on the per-tick path) — the existing `ZeroAllocPollPath`/lifecycle greens are a backstop, not the proof: they don't exercise `Tick()`.
- **Shipped behavior unchanged:** all new backend members are `internal` inside the existing `#if UNITY_EDITOR_WIN` guard; recogniser accessors are `internal` editor-only; nothing public changes (design §3).
- **Determinism:** committed WAVs (no TTS at test time), fixed chunk size (D-6), full DSP/recognizer state reset at `StartPlayback` (D-3), explicit end-of-input flush (D-9), manifest-pinned expectations.
- **Suite duration (and F10):** the pump is test-driven — one 100 ms chunk per editor frame ≈ 10× real time at 100 fps editor; the 15-fixture corpus (~60 s of audio) replays in well under a minute of PlayMode wall-clock plus model load.
- **Failure legibility:** assertions carry the manifest `description`, fixture file, expected vs. actual intent/slots/transcript in the failure message.

## Build plan

Ordered lowest-risk-first; every phase ends compile-clean and existing-tests-green via the `compile-check` agent (host project, EditMode + PlayMode per bindings). The genuinely risky unknown — *does Vosk recognize piper TTS at Quest amplitude through the real AGC?* — is probed with a single fixture (Phase 3a) before the corpus is mass-generated.

- **Phase 0 — WAV reader + containers (pure additive C#).** `VoxrWavReader` + `VoxrAudioTestCase` + `VoxrAudioTestSuiteAsset` + `VoxrWavReaderTests` (EditMode, crafted-byte fixtures for every rejection branch). No existing file touched. *Verify:* compile-check; new EditMode tests green.
- **Phase 1 — `ProcessChunk` extraction (pure refactor, zero behavior change).** D-1 split of `Tick()`. *Verify:* compile-check; existing suite green on both platforms — as a regression backstop only, stated honestly: nothing in the existing suite exercises `Tick()` or the extracted segment (the sole backend coverage is static `ComputeRms`, `Tests~/Editor/AudioMetricTests.cs`), so the real Phase 1 gate is the diff reviewed as pure code motion; the extraction's behavioral proof lands in Phase 2's synthetic smoke — the first test ever to drive `ProcessChunk` end-to-end.
- **Phase 2 — Playback mode + recogniser accessors.** `StartPlayback`/`TickPlayback`/`IsInPlayback` (D-2/D-3/D-9), mutual exclusion with `Start`, the two internal accessors. Smoke PlayMode test with synthetic buffers (sine + silence — no fixtures yet): events fire through the real dispatcher, wrong-rate rejection (F3), mic/playback exclusion. Also resolves the model-path question (how the host project's tests locate the Vosk model) with real code. *Verify:* compile-check; smoke + rejection tests green.
- **Phase 3a — Generation probe (riskiest part, prototyped first).** `generate.sh` skeleton + one manifest entry (fixture 1), **plus the `DemoGrammar` helper front-loaded from Phase 4** — the probe must decode grammar-constrained (the suite's actual acoustic configuration; unconstrained decoding is materially different) and assert intent+slots via `OnCommandRecognised`. This is the acoustic go/no-go: if real Vosk can't recognize piper output at 0.04–0.4 peak through AGC, stop and reopen the design's §6.2 assumption rather than tuning fixtures until they pass. *Verify:* probe fixture recognized end-to-end, grammar-constrained.
- **Phase 3b — Full corpus.** Complete the manifest (15 entries), generate, commit WAVs + `human/` folder; `VoxrFixtureCorpusTests` (EditMode: every committed WAV parses and is 48 kHz/mono/16-bit; **utterance** fixtures peak in [0.04, 0.4]; **silence-negative** fixtures peak below 0.005; every §6.2 category present in the manifest). *Verify:* compile-check; corpus tests green.
- **Phase 4 — Replay regression suite.** `VoxrWavReplayTests` over the manifest (suite materialized via `FromJson`, F5; `DemoGrammar` already landed in Phase 3a); calibrate provisional expectations against actual recognizer output (esp. fixtures 13–15; any expectation that has to be *weakened* from the design's category intent gets flagged, not silently relaxed). *Verify:* compile-check; full suite green both platforms.
- **Phase 5 — Reconcile + review.** As-built deltas pass on this doc; `review-cycle` on the branch; push; PR; `review-pr`; G2.
- **Editor-only assets the build needs:** none — no scenes, no committed `.asset`/`.meta` (manifest-driven suite, code-built test scene), no shader/mesh work. The corpus WAVs are generated files, not editor-authored assets.

## Risks, tradeoffs & open questions

- **Acoustic go/no-go (Phase 3a):** TTS-through-AGC recognition is assumed by the design (DR-2) but unproven on this pipeline; a failure is a design-level finding (reopen §6.2), not a fixture-tuning exercise.
- **Design-wording risk (D-2, D-6, D-7 — one bundled ratification):** the separate-pump reading of §6.1's "Tick() reads successive chunks" (D-2), the fixed 100 ms chunk as "the same chunk size per tick" (D-6), and the `Voxr` rename of §6.1's literal `Vosk*` container names (D-7) all interpret the same carried-over §6.1 wording; the human ratifies the bundle at PR/G2. Fallbacks (mode-branch inside `Tick()`, renames) are contained rework, not redesign.
- **Model discovery in the host project:** manual live-mic runs work in VoXR TestGround today, so a model + path convention exists; the exact resolution mechanism for tests is pinned in Phase 2. Until then it's the plan's least-verified dependency.
- **Grammar copies (D-8):** three hand-synced copies of the demo grammar after this feature (code sample, asset sample, test helper). Drift breaks the corpus's meaning silently — mitigation is the pinning comment + corpus tests failing when patterns diverge enough to change outcomes. A shared source is a possible later refactor, deliberately out of scope.
- **Split-command semantics (fixture 14):** the buffer-window expectation is pinned empirically in Phase 4 (requirements OQ6) — the manifest records current-correct behavior as the regression baseline, ratified at G2.
- **Generation environment:** verified end-to-end in this WSL before implementation (venv with piper-tts 1.6.0 + soxr 1.1.0 + numpy; `en_US-lessac-medium` downloads; smoke phrase synthesized at 22 050 Hz mono 16-bit) — `generate.sh` re-bootstraps the same venv; no system dependency beyond `python3`. None of it is needed to *run* tests (WAVs committed).
- **Piper voice pinning:** `en_US-lessac-medium` (verified); the voice file itself is not committed (venv + download in `generate.sh`) — regeneration depends on the voice remaining downloadable; acceptable because the WAVs are committed.

## As-built deltas

*(Running list during implementation; finalized before G2.)*

- **No `expectNoCommand` field:** `VoxrAudioTestCase` mirrors the house pattern instead — empty `expectedIntent` means "expect no command" (`internal ExpectsNoCommand`, same shape as `VoxrTestCase.ExpectsRejection`). The manifest schema drops the boolean; silence entries just leave `expectedIntent` empty.
- **Container schema additions:** `VoxrAudioTestCase` carries `category` (drives the corpus tests' per-category checks) and an optional `expectedTranscript` (asserted only when non-empty).
- **`Reset()` during playback is a silent no-op,** not an error rejection — `Reset` has no error channel; D-3's "reject" is realized as early-return. `SetGrammar` and `Start` do fire errors as specified.
- **Generation toolchain lives in the user cache** (`~/.cache/voxr-fixture-gen/{venv,voices}`), never inside `Tests~/Fixtures` — the fixtures tree is Unity-imported during host runs, so a venv there would poison imports. TTS temp files go to the system temp dir for the same reason.
- **Host-project model provisioning:** the "environment the existing verification bindings already run" (design §6.3) turned out not to include a Vosk model — the pre-existing suite was all injection-based and never loaded one. `vosk-model-small-en-us-0.15.zip` installed into TestGround's `StreamingAssets` (copied from VR FTL-Like 3) as a one-time host prerequisite; recorded in project memory `running-package-tests`.
- **`TickPlayback` takes only the dispatcher** (no `fireError`) — nothing in the pump can fire an error; refusals all live in `StartPlayback`.
- **First acoustic finding (Phase 4 calibration):** `"switch to navigation"` is mis-transcribed by grammar-constrained Vosk as `"switch two navigation"` (to→two — both words are in the demo vocabulary) and no command matches; `"switch to weapons"` survives the same trap. Treated per the plan's no-silent-relaxation rule: the fixture became a **negative homophone baseline** (expects no command, description documents why), a 16th fixture (`navigation mode`, the intent's other shipped pattern) keeps `mode_navigation` positively covered, and the corpus-shape test permits negative homophone entries. If recognition or the parser ever improves, the negative baseline fires and gets consciously re-ratified. Parser-side homophone tolerance is future issue-lane work (candidate GitHub issue after merge); a `KNOWN_LIMITATIONS.md` entry lands with the post-G2 product docs.
- **Suite duration measured:** the full PlayMode run (286 tests incl. all replays) executes in ~25–28 s warm — far inside the NFR's single-digit-minutes bound.
- **Reproducibility finding (F7 evidence run):** regenerating the corpus from a clean cache and running the suite gave 285/286 — the one failure was `fall_back_from_target_bravo_two.wav`, whose regenerated prosody decoded as "**pull** back from target bravo two": the *intent and slot still matched perfectly* (both phrasings are patterns of `retreat_from_target`), only the strict raw-transcript assertion failed. Consequence, flagged for G2: F7's acceptance is amended to an intent/slot-level bar for regenerated corpora; raw-transcript assertions are a property of the committed baseline and must be re-baselined (or the fixture regenerated) when the corpus is regenerated. The committed baseline itself passes 286/286 with transcripts asserted.
