# Bridge Push Audio (Tier C) — Architecture

*Plan-validator pass applied 2026-07-30: push contract corrected against the real `RingBuffer` semantics, grammar sourcing corrected against the real device grammar, harness flow made verdict-deterministic, plus minor fixes. The C-1 canon flag was ruled by the human the same day (gate chosen — §8) and the design doc amended. §9 records the as-built deltas.*

## 1. Purpose & responsibilities

Adds a push-audio seam to the native bridge so recorded audio can drive the full recognition path without a microphone; makes the bridge buildable for desktop Linux by making the capture backend selectable (with a stub for platforms that have no capture); and delivers a WSL CLI harness that replays the Tier B fixture corpus through the desktop bridge against a committed transcript baseline. Realizes requirements F1–F12 (`Planning~/features/bridge-push-audio/requirements.md`); the design contract is `Planning~/design-docs/automated-verification.md` §7 + DR-4.

Out of scope here (owned elsewhere): the fixture corpus and its manifest (Tier B, frozen), on-device tests (Tier D), the Windows-editor C# pipeline (`EditorMicBackend` + `VoxrNative` — a fully separate mechanism this feature never touches).

## 2. Key components

- **Push ABI** — three new `extern "C"` exports in `NativeBridge~/src/vosk_bridge.h` / `.cpp` (joining the existing 11): `vosk_bridge_push_audio`, `vosk_bridge_start_push`, `vosk_bridge_get_input_level`.
- **Backend selection** — new forwarding header `NativeBridge~/src/audio_capture.h`; new stub backend `NativeBridge~/src/audio_capture_stub.{h,cpp}`; CMake cache option `VOSK_BRIDGE_CAPTURE=audiorecord|aaudio|stub` (default `audiorecord`) selecting the compiled source, the forwarded header, and the `BRIDGE_HEADERS` entry; `vosk_bridge.cpp:7` include swapped from `audio_capture_audiorecord.h` to `audio_capture.h`.
- **Desktop build** — `NativeBridge~/CMakePresets.json` with a `desktop-linux` configure preset (stub backend, `VOSK_LIB_DIR` → `NativeBridge~/vendor/`, Release); `logging.h` gains an `#ifdef __ANDROID__` guard with `printf` fallback; `liblog` and the clang/lld-specific `-flto=thin` flags (`CMakeLists.txt:59-60`) applied only on Android; gitignored `NativeBridge~/vendor/` holds the provisioned Linux x86_64 `libvosk.so` and the model.
- **Harness** — `NativeBridge~/harness/`: a C++17 CLI (`vosk-bridge-harness`) calling `vosk-bridge` through its public C ABI, plus one deliberate internal dependency: it includes `ring_buffer.h` for `RingBuffer<float>::kCapacity`, which sizes the over-push padding that D-9's full-consumption arithmetic rests on (a type-level constant — the buffer instance itself stays private to the bridge). Bespoke minimal WAV reader (48 kHz mono 16-bit PCM or reject); vendored `nlohmann/json` single header (`harness/third_party/`) for manifest parse + JSON output; built via `option(VOSK_BRIDGE_BUILD_HARNESS)` (default OFF, ON in the desktop preset).
- **Expectation baseline** — `NativeBridge~/harness/expectations.json`: the committed bridge-level transcript baseline plus the grammar, AGC target, and libvosk version that produced it (schema in §3).
- **Managed bindings** — three new `[DllImport]`s in `Runtime/Native/BridgeNative.cs`, matching that file's existing conventions (no explicit calling convention, `[Preserve]`, `int` for integer parameters per house style); plus the additive error-code mirror in `Runtime/VoxrBridgeErrorCode.cs` (and its pin test). No managed caller until Tier D.

## 3. Contracts

**Push ABI** (all additive; existing 11 exports keep their signatures and observable behavior):

- `int vosk_bridge_push_audio(const float* samples, uint32_t count)` — writes pre-DSP 48 kHz mono float samples into `g_ring_buffer` (the same payload, format, and buffer a capture backend produces). Unlike the capture backend's unconditional `Write` (which overwrites oldest data on overflow — `ring_buffer.h:26-45`, `Write` always returns `count`), `push_audio` **clamps**: it writes `min(count, Size − Available())` samples and returns the clamped count, so a short write means "ring full — drain and retry" and pushed audio is never silently discarded. This realizes the design's "returns samples written / error code so a caller can pace against overflow" (§7.1) — the design's "exactly what a capture backend writes" is read as the payload contract, since capture's own overflow behavior would make pacing impossible; reading recorded for G2. Misuse returns a **negative** `VoskBridgeError` (`-VOSK_BRIDGE_ERR_NOT_INITIALISED`, `-VOSK_BRIDGE_ERR_NOT_RUNNING`); negative-on-error keeps the non-negative range for counts, and no existing export returns negatives (verified).
- `int vosk_bridge_start_push()` — starts the recognition thread exactly like `vosk_bridge_start()` but skips `g_audio_capture.Start()`; returns the same error enum. Both starts delegate to one internal helper taking `bool start_capture`, which also owns the mode flag: `g_push_mode = !start_capture`. **Lifecycle:** `vosk_bridge_start` clears the flag, `vosk_bridge_start_push` sets it, `vosk_bridge_stop` and `vosk_bridge_destroy` clear it; `vosk_bridge_reset` (`vosk_bridge.cpp:253-263` — a previously missed site: its restart path calls `vosk_bridge_start`, i.e. capture) becomes **mode-aware**: it records the active mode before stopping and restarts through the helper in that same mode, so a reset can never convert a push session into a microphone session. `push_audio` requires running-in-push-mode. Together these keep the SPSC ring single-producer by construction.
- `float vosk_bridge_get_input_level()` — rolling RMS (linear, 0..1) of drained pre-DSP chunks, computed in the recognition loop, published through a `std::atomic<float>`, zeroed on **start and stop**. The smoothing coefficient is derived from the actual chunk length (`alpha = 1 − exp(−chunk_ms / 300ms)`, the existing `agc.h:87-89` idiom) so the ~300 ms effective window holds on both desktop (~85 ms chunks) and device (~20 ms chunks — `audio_capture_audiorecord.cpp:13` writes 960-frame chunks, so a fixed per-iteration alpha would be ~4× off on the platform Tier D actually polls). Units and the single-pusher threading contract documented in the header comment.
- New enum value `VOSK_BRIDGE_ERR_NOT_RUNNING = 8` (additive; existing enum tops out at 7 — verified no collision). Mirrored in the public C# enum `Runtime/VoxrBridgeErrorCode.cs` (+ its pin test `Tests~/Editor/VoxrBridgeErrorCodeTests.cs`); the negative-return convention is unique to `push_audio` and must **not** flow through the existing `CheckBridgeError` cast pattern (`VoxrSpeechRecogniser.cs:517`) — noted for Tier D, which brings the first managed caller.

**Expectation manifest** (`harness/expectations.json`) — the F9 committed baseline:

```json
{
  "_comment": "Bridge-level baseline; relationship to Tests~/Fixtures/audio/manifest.json documented here",
  "libvosk": "<pinned version>",
  "gain": -18.0,
  "grammar": ["launch", "one", "...", "[unk]"],
  "cases": [
    { "file": "cease_fire.wav", "expectedFinals": ["cease fire"] },
    { "file": "silence_negative.wav", "expectedFinals": [] }
  ]
}
```

- `grammar`: the full word list passed to `vosk_bridge_set_grammar` (serialized as the JSON array Vosk expects — the real device shape: sorted unique single words + `[unk]`, `VoxrCommandParser.cs:566-583`). **Sourced from the runtime's own generator, not by hand:** `VoxrCommandParser.GenerateGrammarJson` (`:492-584`) draws on three sources invisible in `DemoGrammar.cs` — the full digit vocabulary for `NumberSequence` slots (`VoxrNumberParser.DigitVocabulary`, 30 words; the `set_heading_two_seven_zero` fixture needs "seven"/"zero", which appear nowhere in `DemoGrammar.cs`), the confirm/cancel follow-up words (`VoxrPendingCommand.cs:34-38`), and alias keys — ~98 words total vs. ~56 derivable by hand. Captured via Tier B's existing seam (`DemoGrammar.Configure` → `VoxrCommandRecogniser.TestGrammarJson`).
- `gain` and `libvosk`: the AGC target (device value `-18f`, `VoxrSpeechRecogniser.cs:34`) and the vendored libvosk version — pinned in-file because the baseline is only meaningful under the exact DSP regime and decoder that produced it (same argument as the grammar, D-4).
- `expectedFinals`: the ordered list of non-empty final-result `text` values the bridge must emit; `[]` = no non-empty final (the thread-exit flush always queues one final — `{"text": ""}` for silence — so "empty" means no *non-empty* finals). Exact string match. Multi-final fixtures (the split case, if Vosk finalises at the 0.7 s gap) are naturally two entries.
- `file` is a **basename** joined onto `--fixtures <dir>` — note the corpus manifest's same-named key is `Tests~/Fixtures/`-relative (`audio/tts/x.wav`); the D-8 seeding cross-check joins the two by basename (all 16 corpus files live flat under `audio/tts/`, verified).
- One `cases` entry per corpus fixture (16). The pins are **required and validated** (post-G2 hardening): `gain`, non-empty `grammar`, and the `libvosk` pin must be present and well-typed or the run is an operational error (exit 2) — a free decode can never produce or verify a baseline; the manifest schema is validated up front, zero-case manifests are refused, and every `.wav` in the fixtures dir must be listed (corpus-drift guard). Re-baselining is explicit: `harness --write-baseline` overwrites `expectedFinals` from actuals — the conscious step Tier B's F7-amendment policy requires; never run implicitly. The `libvosk` pin is carried verbatim (no version API exists to check it mechanically) — bumping libvosk means updating the pin in the same reviewed diff.

**Harness CLI**: `harness --model <dir> --fixtures <dir> --manifest <expectations.json>` (design §7.3 shape); `--write-baseline` as above. Output: one JSON object per fixture (file, expected, actual finals, pass/fail) + summary; exit 0 iff all pass. Malformed WAV/manifest/model → clear message naming file and problem, nonzero exit. Two result-handling obligations: result strings are copied immediately (the pointer from `vosk_bridge_get_result` is invalidated by the next call — same lifetime contract `BridgeNative.cs:49-54` documents), and `{"error": ...}` queue entries (ring overflow, capture errors — `vosk_bridge.cpp:72-76,117-120`) fail the run loudly rather than being skipped as unparseable.

**CMake surface**: `VOSK_BRIDGE_CAPTURE` (STRING, validated against the three values) compiles `src/audio_capture_<value>.cpp`, defines `VOSK_BRIDGE_CAPTURE_<VALUE>` for the forwarding header, and swaps the backend header in `BRIDGE_HEADERS` (`CMakeLists.txt:14-22` hardcodes the audiorecord header there too); `VOSK_BRIDGE_BUILD_HARNESS` (BOOL, OFF) gates `add_subdirectory(harness)`; `VOSK_LIB_DIR` keeps its existing meaning (now also the vendor dir on desktop); `log` link and `-flto=thin` (clang/lld-only, would hard-error under GCC) guarded to Android. Android invocations in CLAUDE.md/`build.sh` pass none of the new options and compile the same source list with the same flags — behavioral identity is proven structurally (§6), not bit-for-bit (the artifact changes because the additive push code exists).

## 4. How it works — runtime flow

Harness session, per fixture (gain pinned to the device value): `vosk_bridge_init(model, 16000, -18.0)` (once) → `vosk_bridge_set_grammar(grammar)` (once) → then per fixture: `vosk_bridge_start_push()` → push the fixture's samples in chunks with clamped-write pacing (short write ⇒ drain any ready results, brief sleep, retry — sleeps affect throughput only, never the verdict) → push **padding**: ~1 s of silence, then ≥ 65,536 further silence samples. Because consumption ≥ samples-pushed − ring-capacity at every accepted write, the padding guarantees every fixture sample (plus the 1 s pad) has been consumed by Vosk before the harness proceeds — full-consumption is proven by arithmetic, with no ring-occupancy ABI and no wall-clock reasoning (D-9) → `vosk_bridge_stop()` (joins the recognition thread; the thread's exit path flushes `vosk_recognizer_final_result` into the queue — `vosk_bridge.cpp:129-131` — so the tail final lands **during** stop) → drain the result queue to empty **after** `stop()` returns (deterministic post-join; the queue survives until the next start's `reset_pipeline`) → verdict = the ordered non-empty finals → `vosk_bridge_reset()` (recognizer state; safe here — not running, so no restart path) → next fixture.

Inside the bridge nothing downstream changes: the recognition loop keeps draining `g_ring_buffer.Read` (`vosk_bridge.cpp:79`) → `Downsampler` 48→16 kHz (`:87`) → `Agc::Process` (`:90`) → `float_to_int16` (`:43-50`, `:93`) → `vosk_recognizer_accept_waveform_s` (`:96`) → result queue. The loop is indifferent to who filled the ring — that indifference *is* the tier's claim that harness results exercise real bridge logic. Faster-than-real-time push is sound because Vosk endpointing consumes sample time, not wall clock: a 0.7 s gap is 33,600 samples regardless of push speed. (The loop's capture-error check is gated to capture mode per the ratified C-1 amendment: §8.)

The single-producer/single-consumer ring contract is preserved by substitution, not addition: in push mode the pusher thread *replaces* the capture thread as the sole producer, and the `g_push_mode` lifecycle (§3) — including the mode-aware reset — makes the modes mutually exclusive at every entry point, so there are never two producers.

Desktop build: the preset selects `stub`, so no `jni.h`, no `<android/log.h>`, no liblog anywhere in the TU set; `libvosk.so` comes from `vendor/`; the harness runs without `LD_LIBRARY_PATH` via CMake's default build-tree RUNPATH (absolute paths to the build dir and `vendor/` — fine for the in-place tool this is; it would not survive relocating the binary).

## 5. Decision register

- **D-1 — `vosk_bridge_start_push()` as a separate export**, not a mode flag on `vosk_bridge_start()`. Why: purely additive — the existing export, its `BridgeNative.cs` binding, and every current caller stay untouched, which is the cheapest honest proof of "Android build behaviorally identical". Internally both delegate to one static start helper taking `bool start_capture`, which owns `g_push_mode` (§3 lifecycle). Alternative kept on record: flag parameter on `vosk_bridge_start` (rejected: ABI churn on the one function everything already calls).
- **D-2 — Backend selection by compile definition + forwarding header**, not runtime polymorphism. Why: the design pins the mechanism (§7.2: neutral include + CMake option picking source and header); the two existing backends are already interface-identical non-polymorphic classes, and exactly one backend can exist per binary (both define `class AudioCapture`), so a vtable buys nothing and costs an indirection on the audio path. Alternative: abstract base + factory (rejected: runtime selectability is a non-requirement; duplicate-class collision makes it impossible without renaming both backends — needless churn in the untouchable capture file).
- **D-3 — Stub backend is honest, not inert**: `Start` records running and returns `VOSK_BRIDGE_OK`, `Stop` clears it, `HasError()` constant false — so non-push capture mode on desktop (F6) behaves like a silent microphone rather than an error state.
- **D-4 — Grammar, gain, and libvosk version embedded in `expectations.json`**, not separate files or fixture-derived vocabulary. Why: the baseline is only meaningful under the decode regime that produced it — one file makes them version together, and re-baselining can't silently decouple them. The vocabulary comes from the runtime's own `GenerateGrammarJson` output (via Tier B's `TestGrammarJson` seam), because hand-derivation from `DemoGrammar.cs` under-covers the real device grammar by ~42% (digit vocabulary, confirm/cancel words, alias keys — §3); fixture-derived vocabulary was rejected for the same reason plus the homophone trap ("two" must be in vocabulary though no fixture phrase says it); a hand-duplicated C++ grammar was rejected as a drift farm.
- **D-5 — Vendored `nlohmann/json` single header for the harness** (`harness/third_party/`, MIT). Why: the harness must parse JSON (manifest) and emit JSON (results); a hand-rolled parser is a bug farm out of all proportion to this tool. Never ships: `release.yml` strips `NativeBridge~/`. Alternative: minimal bespoke parser (rejected: fragile), non-JSON manifest (rejected: design names `expectations.json`).
- **D-6 — `CMakePresets.json` for the desktop preset**, not a second build script. Why: the design's own word is "preset"; presets are declarative, diffable, and leave `build.sh` + the CLAUDE.md Android commands untouched. Requires CMake ≥ 3.21 client-side (schema v3); the README carries the equivalent raw `cmake` command line as fallback.
- **D-7 — Provisioning is download-don't-build**: Alphacephei prebuilt Linux x86_64 `libvosk.so` + the small English model into gitignored `vendor/` (design §7.2 pins this). Fallback kept on record if the prebuilt's glibc doesn't load in WSL (glibc 2.39 measured — recent, low risk): extract `libvosk.so` from the `vosk` pip wheel (WSL has python3 3.12) — same upstream binary, different packaging. Building Vosk/Kaldi from source is explicitly rejected (hours-scale toolchain for zero verification value).
- **D-8 — Baseline pins bridge actuals, not corpus-manifest transcripts** (F9): the corpus manifest's `expectedTranscript` is parser-level and deliberately empty for filler/split/homophone-negative cases; the desktop bridge sees `[unk]` tokens and a different libvosk build. Seeding compares actuals against the corpus manifest as a sanity review (clean fixtures should agree; divergence is examined and documented in the baseline's comment), then commits what the bridge really produced.
- **D-9 — Full-consumption by over-push, verdict from the post-stop queue.** The loop exits on `g_running == false` without draining the ring (`vosk_bridge.cpp:69`), the tail final is flushed during `stop()`'s join, and the C ABI exposes no ring-occupancy query — so the harness (a) guarantees consumption arithmetically by pushing ring-capacity-plus-padding silence after each fixture (consumed ≥ pushed − 65,536 always), and (b) reads its verdict from the queue **after** `stop()` returns, which the join makes deterministic. Alternative rejected: a fourth ABI export exposing `Available()` (exceeds the design's three named additions for a problem arithmetic solves).

## 6. Non-functional realization

- **Android unchanged (NFR 1):** proven structurally — default option value compiles the identical source list with the identical flags (LTO and liblog stay Android-only by the same guards); the only source-line change on the Android path is `vosk_bridge.cpp:7`'s include indirection and the additive push/level code; verified per phase by the arm64 build and at G2 by the host-project suites. (Phase-1 source-list verification reads `build.ninja`/`CMakeCache.txt`, not the object dir — a stale `audio_capture_aaudio.cpp.o` from an old configuration lives in `build/`.)
- **SPSC preservation (NFR 2):** producer substitution (§4), the `g_push_mode` lifecycle incl. mode-aware reset (§3), plus the documented contract that `vosk_bridge_push_audio` is called from one thread at a time.
- **Determinism (NFR 3):** same WAV bytes + same model + same grammar + same gain ⇒ same sample stream ⇒ same finals, and the verdict is read from the post-join queue after arithmetically-guaranteed full consumption (D-9) — no verdict-relevant wall-clock dependence; pacing sleeps affect throughput only.
- **Speed (NFR 4):** faster-than-real-time push bounded by Vosk decode; **measured: 16/16 fixtures in ~1.8 s wall clock** (small model, x86_64, WSL), deterministic across consecutive runs.
- **Input-level cost:** one multiply-add pass over each drained chunk plus one atomic store per iteration in the recognition thread — negligible against the FIR + Vosk work already in that loop; no allocation.
- **Footprint (NFR 6):** `vendor/` gitignored (new `.gitignore` entry — the existing `NativeBridge~/build*/` pattern already covers the preset's `build-desktop/` binary dir); committed additions are harness sources, the vendored JSON header, and `expectations.json`.

## 7. Build plan

Phased lowest-risk-first with the one exception the dependency order forces: the backend refactor (zero-behavior-change) must precede the desktop build that needs it. **Known gates, probed 2026-07-30:** WSL has **no C++ toolchain** (no compiler, CMake, make/ninja; no libc dev headers; sudo requires a password) — human asked to run `sudo apt install -y build-essential cmake ninja-build` in an interactive terminal; phases 2, 4, 5 block on it (phases 1, 3, 6 verify against the Windows-side Android toolchain, which is present). §8 C-1's design-amendment ruling gates one line of phase 3. Every phase ends green: `compile-check` (Android CMake build; host Unity suites when C# changes) plus, once it exists, the desktop build/harness run. `rm` is blocked in this environment — use `find … -delete`.

## 8. Risks & assumptions

- **C-1 — RESOLVED (design amendment ratified 2026-07-30, human in-conversation ruling).** Design §7.1's claim that the loop's `HasError()` check "is benign in push mode" was verified false (sticky `error_occurred_` flag, cleared only by the capture `Start()` push mode skips — an errored capture session would kill the next Android push session). **Ruling: gate the check on capture mode** — `if (!g_push_mode && g_audio_capture.HasError())` — one line; the recognition loop is otherwise untouched. Amendment recorded in the design doc (§7.1 amendment block) and requirements F2; the `ClearError()` alternative and the defer-to-Tier-D option are on record there as rejected.
- **Toolchain (was an assumption, now measured):** WSL Ubuntu 24.04 has no compiler/CMake/make and sudo needs a password — human provisioning required before phases 2/4/5 (`sudo apt install -y build-essential cmake ninja-build`); CMake ≥ 3.21 needed for presets (Ubuntu 24.04 apt ships 3.28). glibc 2.39 measured — recent enough for the Alphacephei prebuilt with high confidence; pip-wheel fallback on record (D-7).
- **Baseline brittleness:** exact-match finals could churn if libvosk version changes — mitigated by pinning the version inside `expectations.json` (D-4); a version bump is a conscious re-baseline.
- **Grammar drift vs. the runtime generator:** the embedded vocabulary is a snapshot of `GenerateGrammarJson` output; if the demo grammar or parser vocabulary sources change, the snapshot rots — the D-8 sanity review catches gross drift, Tier D ultimately cross-checks on device. Accepted for v1; noted for the future if it bites.
- **`aaudio` option value is unverified legacy** (requirements non-goal): the option accepts it per the design's enumeration; selecting it may not even compile. README and this doc say so plainly.
- **Split-fixture finals count** — resolved as-built: two finals at the 0.7 s gap (§9).

## 9. As-built deltas

Reconciled 2026-07-30 after phases 1–5 (desktop side complete, suite green 16/16):

- **Grammar sourcing (D-4 refinement):** the vocabulary was derived by executing `GenerateGrammarJson`'s algorithm over `DemoGrammar`'s inputs directly (all four sources: pattern literals, slot values + alias keys, digit vocabulary, confirm/cancel words → 98 words, matching the plan-validator's independent count), rather than via a host-project `TestGrammarJson` dump — the dump would have required a Unity run just to emit a string. Empirically validated by the baseline run: digits ("seven", "zero"), the alias ("jackals"), and the homophone pair all decode; every clean fixture's transcript matches the corpus manifest's `expectedTranscript` exactly.
- **Desktop logging → stderr:** the plan's `printf` fallback polluted the harness's stdout JSON report; desktop `LOGI`/`LOGE` both go to stderr, stdout belongs to tool output.
- **Split fixture resolved (was §8 unknown):** Vosk endpointing does finalise at the 0.7 s gap — two finals (`"close distance safe range"`, `"target hotel one"`), recorded in the baseline.
