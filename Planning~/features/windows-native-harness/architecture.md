# feat-windows-native-harness — Architecture

Realizes `Planning~/features/windows-native-harness/requirements.md` (Track **Full**; S1, F1–F8, the two §6 NFRs): the native bridge and the push-audio harness build with MSVC from Visual Studio 2022 and run Windows-native, so Command 3's desktop half runs from Claude Code's Git Bash with no WSL (adr-0001…adr-0004, Amendment A2). The governing driver is that **the whole desktop half is one command run verbatim in Git Bash**: Unity's cmake 3.22.1 by absolute path (adr-0003) configures with CMake's "Visual Studio 17 2022" generator, which reaches Visual Studio 2022 itself (ruled 2026-10-14, "Use visual studio"), and no argument that crosses into a Windows program is one Git Bash would rewrite. Every decision below either makes that command work as written, or keeps the Android arm64 build, the committed baseline and `Runtime/` exactly as they are (F2, F3, F8).

## Context & scope

Before this feature the desktop build was Linux-only: one preset, `desktop-linux`, Ninja into `build-desktop/`, run under `wsl.exe` by the binding and the recipe. Three constructs blocked MSVC: the export macro `VOSK_BRIDGE_EXPORT` (`__attribute__((visibility("default")))`), the unconditional GNU flags `LINK_FLAGS "-Wl,--no-undefined -Wl,--strip-all"`, and the hard-coded `IMPORTED_LOCATION "${VOSK_LIB_DIR}/libvosk.so"`. No POSIX API is used: the harness and bridge use `std::thread`, `std::filesystem`, `std::chrono` and `fopen(…, "rb")` (`NativeBridge~/harness/wav_reader.cpp` :32), and the desktop logging branch is `fprintf` (`NativeBridge~/src/logging.h` :19-20). The bridge and harness sources carry UTF-8 punctuation in comments and one string literal (`wav_reader.cpp` :96).

**Provisioned inputs (F6, verified 2026-10-14, `.scratch/probe-windows-native-harness-zip-report.md`).** `vosk-win64-0.3.45.zip` is 14,882,445 bytes, SHA-256 `f1dcc9cca460630f81ea8f71794f69c80bed6556d2a4e6237b5785e1d2dff34b`, and holds `vosk-win64-0.3.45/{libvosk.dll, libvosk.lib, vosk_api.h, libstdc++-6.dll, libgcc_s_seh-1.dll, libwinpthread-1.dll}`. All four DLLs are byte-identical to `Runtime/Plugins/x86_64/` — `libvosk.dll` SHA-256 `9331c2f6a32cf77141af27c9750e79532718f51bbc2e3cea3c60f14ca4251e4e` — so the harness now runs the exact libvosk binary the Editor runs. `libvosk.lib` is an import library naming `libvosk.dll` (36 `vosk_*` exports in both, by `dumpbin`); the zip's `vosk_api.h` is byte-identical to the Linux 0.3.45 one. adr-0004 stands; no stop.

**Tools (verified).** cmake 3.22.1 at `C:\Program Files\Unity\Hub\Editor\6000.3.7f1\Editor\Data\PlaybackEngines\AndroidPlayer\SDK\cmake\3.22.1\bin\`, whose `--help` lists the "Visual Studio 17 2022" generator; the ninja 1.10.2 beside it serves the arm64 half only. ## Decision register

- **The route into the Visual Studio environment — CMake's "Visual Studio 17 2022" generator.** Ruled 2026-10-14 by the maintainer, in session: "Use visual studio" (requirements §5, §10 item 1). Unity's `cmake.exe` configures `build-windows/` with the "Visual Studio 17 2022" generator, which locates the VS 2022 installation itself and writes MSBuild projects; `cmake --build` drives MSBuild, which runs the v143 toolset's `cl` and `link`. No environment script runs, and Ninja is not used for this build. The harness runs afterwards from Git Bash. *Why:* the ruling; the generator needs no pre-configured compiler environment, so adr-0003's consequence for Ninja falls away and the whole desktop half is plain Git Bash with absolute paths; cmake 3.22.1 lists the generator (probe report), and it is one of the two routes design §4 and adr-0002 hand to this doc. The MSVC toolset is the generator's default for VS 2022, not pinned: a VS 2022 update moves it, and the 16/16 invariant judges any effect. *Rejected:* Ninja inside `vcvars64.bat` — `cl` exists only in a `cmd.exe` process that has run `vcvars64.bat`, so the command needs a `cmd.exe` hop from bash, with its own quoting layer under the MSYS runtime's re-quoting, `/`-switches that need path-conversion handling, and behaviour no input records (operator parsing on a `/c` line, the VS scripts' end-of-run directory, the exit code back to bash) — against a generator that finds VS 2022 itself; `VsDevCmd.bat` or `Launch-VsDevShell.ps1` (the same hop, plus switches or an execution-policy dependency). **Amended 2026-10-14:** replaces this draft's Ninja-inside-`vcvars64.bat` route, and with it the decision on how the command entered `cmd.exe` and the Phase 0 that was to prove it.

- **Held to VS 2022 — the generator name, plus `CMAKE_GENERATOR_INSTANCE` pinned to the Community path.** The "Visual Studio 17 2022" generator considers only version-17 instances, so it cannot select the installed VS 2026; the configure also passes `-DCMAKE_GENERATOR_INSTANCE=C:/Program Files/Microsoft Visual Studio/2022/Community`, the one VS 2022 instance on the host, so the build uses that installation or fails. It is passed on the command line beside the cmake path, keeping the bound command the one place that names machine paths (adr-0003). *Why:* the toolchain-drift NFR (no fallback) and requirements §7 (VS 2026 a non-goal). *Rejected:* the generator name alone (it excludes VS 2026, but chooses among VS 2022 instances itself, so a removed Community would pass silently to any other VS 2022 product, and its error names no path); the preset's `toolset` field with an MSVC version (pins a toolset a routine VS update replaces, not the installation); the instance in the preset (a machine path in a second committed file).

- **Git Bash path conversion — no `/`-prefixed argument reaches a Windows program, so nothing is disabled.** `cmake.exe` receives `--preset windows-x64`, `-DCMAKE_GENERATOR_INSTANCE=C:/…` (drive-letter form, which MSYS conversion leaves as is) and `--build --preset windows-x64`; the harness receives relative paths (`vendor/…`, `../Tests~/…`, `harness/…`); the absolute tool paths are command words bash resolves itself; `ls` is an MSYS program, outside conversion. `/utf-8` lives in `CMakeLists.txt` and reaches `cl` through MSBuild, never through bash. The command therefore behaves the same whether `MSYS_NO_PATHCONV=1` is set (Claude Code's Git Bash) or not (a plain Git Bash); Phase 2 runs it both ways. *Why:* F7, design §3. *Rejected:* a defensive `MSYS_NO_PATHCONV=1` prefix (a prefix binds one simple command, so it would repeat on each tool call while guarding no argument); `C:\…` backslash forms in arguments (each backslash then needs bash quoting, for no gain over `C:/…`, which CMake reads). **Amended 2026-10-14:** the recipe's `CMAKE=` line (Phase 1, ruling B) is the `/c/…` form: it is only a command word bash resolves, never an argument to a Windows program; the recipe's arguments stay `C:/…`.

- **The presets — `windows-x64`, one configure preset and one build preset, replacing `desktop-linux`.** Schema `"version": 3` (the maximum cmake 3.22 reads). Configure preset: `"generator": "Visual Studio 17 2022"`, `"architecture": { "value": "x64", "strategy": "set" }` (schema 3's platform field, equivalent to `-A x64`; `set` makes a generator without a platform an error), `"binaryDir": "${sourceDir}/build-windows"`, `cacheVariables`: `VOSK_BRIDGE_CAPTURE=stub`, `VOSK_BRIDGE_BUILD_HARNESS=ON`, `VOSK_LIB_DIR=${sourceDir}/vendor/vosk-win64-0.3.45`; a `displayName`/`description` naming Windows x64, MSVC (VS 2022), stub capture and the harness. No `CMAKE_BUILD_TYPE`: the generator is multi-config and ignores it. No `CMAKE_CXX_COMPILER`: a Visual Studio generator takes the compiler from its toolset, so the variable selects nothing. Build preset: `"name": "windows-x64"`, `"configurePreset": "windows-x64"`, `"configuration": "Release"`. `desktop-linux` is deleted (adr-0001). *Why:* F1, F4; `cmake --build` on a Visual Studio tree builds Debug when no configuration is given, so Release sits in the committed file beside the preset it pairs with, and no copy of the command can drop it; a fresh directory, because CMake 3.22 has no `--fresh` and `build-desktop/` holds a cache naming `/usr/bin/c++`, the Ninja generator and the old source path, which CMake refuses (`verification-recipe.md` :3). `NativeBridge~/build*/` is gitignored, so `build-windows/` needs no ignore rule. *Rejected:* `--config Release` on the command line (a word each of the three verbatim copies must carry); reusing `build-desktop/` (every first run would need a deletion the requirements leave out of scope, §7); keeping `desktop-linux` beside it (adr-0001's rejected branch b).

- **The export macro — a `_WIN32` arm keyed on CMake's `vosk_bridge_EXPORTS`, the GCC/Clang arm unchanged.** In `vosk_bridge.h` :6: under `_WIN32`, `VOSK_BRIDGE_EXPORT` is `__declspec(dllexport)` when `vosk_bridge_EXPORTS` is defined and `__declspec(dllimport)` otherwise; elsewhere it stays `__attribute__((visibility("default")))`, character for character. CMake defines `vosk_bridge_EXPORTS` when compiling the `vosk-bridge` SHARED target (it does so today on Android too, unused), and never for the harness, so the bridge exports and the harness imports with no new compile definition. The 14 use sites (`vosk_bridge.h` :25-62; the 15th occurrence is the definition) are unchanged. *Why:* adr-0002's consequence; MSVC emits no import library for a DLL with no exports, so the harness cannot link without it; F3 — the Android preprocessed output is token-identical, so the exported symbol list cannot move. *Rejected:* `GenerateExportHeader` (a generated header in the build tree, a new include path, and its own macros replacing the Android arm); `WINDOWS_EXPORT_ALL_SYMBOLS` (exports every internal C++ symbol, breaking the "only extern C exports" invariant at `CMakeLists.txt` :70); a `.def` file (a second list of 14 names to keep in step); `dllexport` on both sides (the harness would declare as exported functions it only imports).

- **libvosk named per platform — keyed on `WIN32`.** `if(WIN32)`: the imported `vosk` target takes `IMPORTED_IMPLIB "${VOSK_LIB_DIR}/libvosk.lib"` and `IMPORTED_LOCATION "${VOSK_LIB_DIR}/libvosk.dll"`; `else()`: `IMPORTED_LOCATION "${VOSK_LIB_DIR}/libvosk.so"`, as today. The `VOSK_LIB_DIR` default (:53-55) is unchanged, so a Windows configure without the preset points at `Runtime/Plugins/Android/` and fails the existence checks below rather than finding a DLL elsewhere. *Why:* F1, F3; the file names are a property of the platform's DLL model, not of the compiler. *Rejected:* `find_library` (searches beyond `VOSK_LIB_DIR`, the silent fallback the degraded-vendor NFR forbids); a `VOSK_LIB_NAME` cache variable (a knob nothing needs).

- **Vendor checks — at configure time, naming the file.** Under `WIN32`, before the imported target is defined, each of `libvosk.lib`, `libvosk.dll`, `libstdc++-6.dll`, `libgcc_s_seh-1.dll`, `libwinpthread-1.dll` under `VOSK_LIB_DIR` is checked with `if(NOT EXISTS …)` → `message(FATAL_ERROR …)` naming the missing path and `harness/README.md`. *Why:* the degraded-vendor NFR; the bound command configures on every run, so the check runs on every run. *Rejected:* letting the link fail (it names `libvosk.lib` only, and a missing runtime DLL surfaces only at run time as a loader failure, not the harness's legible exit 2).

- **The GNU link flags — guarded `if(NOT MSVC)`, same property.** The `set_target_properties` at :71-75 is split: the two visibility presets stay unconditional (MSVC ignores them), and `LINK_FLAGS "-Wl,--no-undefined -Wl,--strip-all"` is set inside `if(NOT MSVC)`. *Why:* adr-0002's consequence ("guarded off MSVC, not removed"); F3 — the Android link line is built from the same property with the same string. *Rejected:* `if(ANDROID)` (the condition is the linker that rejects them, not the platform); moving them into `target_link_options` with a generator expression (changes the property, and possibly the flags' place on the Android link line, for no gain).

- **Source encoding — `/utf-8` under MSVC.** In `CMakeLists.txt`, before the targets, `if(MSVC) add_compile_options(/utf-8) endif()`, which reaches the harness subdirectory too and enters the generated projects, not the command line. *Why:* F1, F2 — without it MSVC reads the sources' UTF-8 punctuation in the host's ANSI code page, which the inputs do not record; under a double-byte code page a lead byte can absorb the next character, and the harness's error text at `wav_reader.cpp` :96 would differ from the GCC build. `/utf-8` reads and emits UTF-8 as GCC and Clang do, and changes nothing else. *Rejected:* re-encoding the comments to ASCII (edits across the hot-path headers for no behaviour); leaving it (the build's correctness would depend on the host locale).

- **Run-time DLL discovery — one runtime output directory for every configuration, vendor DLLs copied in at configure time.** Under `WIN32`, `CMAKE_RUNTIME_OUTPUT_DIRECTORY` is `$<1:${CMAKE_BINARY_DIR}/bin>`, set before the targets: because the value is a generator expression, the multi-config generator appends no per-configuration subdirectory, so `vosk-bridge.dll` and `vosk-bridge-harness.exe` land together in `build-windows/bin/`; after the vendor checks, `file(COPY …)` puts the four vendor DLLs there. The loader searches the exe's directory first, for the exe's imports and for `vosk-bridge.dll`'s. The bridge's import library stays where the generator puts it (a per-configuration directory); the harness links it by target. *Why:* the degraded-vendor NFR and determinism — Git for Windows' `/mingw64/bin` is on Git Bash's PATH and carries its own `libgcc_s_seh-1.dll` (`.scratch/probe-windows-native-toolchain-host-report.md`), so PATH order must not decide which runtime loads; one fixed directory keeps the configure-time copy and `<CMD>`'s exe path free of the configuration name. *Rejected:* the default `bin/Release/` (the copy and the exe path in `<CMD>` would each name the configuration, kept in step with the build preset by hand); `CMAKE_RUNTIME_OUTPUT_DIRECTORY_RELEASE` (only Release lands in `bin/`; any other configuration builds a second layout without the vendor DLLs); prepending `vendor/` and the build dir to PATH (order-dependent against Git's own DLLs); a `POST_BUILD` copy (ties the copy to whether the harness relinks); `$<TARGET_RUNTIME_DLLS>` (knows only imported targets, not the three MinGW runtime DLLs).

- **The vendor layout — the zip extracted as-is.** `NativeBridge~/vendor/vosk-win64-0.3.45/` holds the six files exactly as unzipped, beside the model `vendor/vosk-model-small-en-us-0.15/`; nothing is copied up a level. The README checks the zip's SHA-256 against the value in *Provisioned inputs* before extracting; a mismatch stops for the human (adr-0004). It tells the reader that the Linux files from before this feature (`vendor/libvosk.so`, `vendor/vosk-linux.zip`, `vendor/vosk-linux-x86_64-0.3.45/`) are unused and to delete them. *Why:* F5, F6; the version in the directory name makes a re-pin a visible preset edit. *Rejected:* a flat copy into `vendor/` (as the Linux README did — a stale flat copy can survive a re-provision and sits beside a Linux `libvosk.so`); leaving the Linux files unmentioned (dead weight the reader cannot tell is unused; the WIN32 branch could not link them in any case). **Amended 2026-10-14:** the README's provisioning blocks run `mkdir -p NativeBridge~/vendor` first and `cd ../..` last — `vendor/` is gitignored, so a fresh clone lacks it, and a failed `cd` would unzip into the tracked project root; do not drop either.

- **The arm64 `.so` — not recommitted.** This feature makes no bridge ABI change: the Android arm of the macro expands to the same tokens, no signature changes, and the Android link flags and libvosk name are unchanged; Command 3's own text recommits only on an ABI change, and F8 requires `git diff --stat main -- Runtime/` empty. F3's symbol-list diff is the proof; a non-empty diff stops for the human, never a recommit.

- **The `libvosk` label.** `"libvosk": "0.3.45 (Alphacephei vosk-win64 prebuilt)"` in `NativeBridge~/harness/expectations.json` (:236), the line edited in place, nothing reformatted. *Why:* F2 as ruled 2026-10-14; the harness checks only presence and non-emptiness (`main.cpp` :140-142), so the label is a record, not a regime change.

## Data contract & runtime flow

**The configure contract.** Inputs: the configure preset's generator, architecture and cache variables, and `CMAKE_GENERATOR_INSTANCE` from the command line; no compiler environment is needed. `VOSK_LIB_DIR` must hold the five Windows files or configure fails naming the first missing one. Outputs in `build-windows/`: the generated MSBuild projects, `bin/vosk-bridge.dll`, `bin/vosk-bridge-harness.exe`, the four vendor DLLs in `bin/`, and the import library `vosk-bridge.lib` the harness links. The bridge imports `libvosk.dll` by the name `libvosk.lib` records; across that seam only `extern "C"` calls and `const char*` results the bridge copies, so the two C runtimes (MSVC's for the bridge, MinGW's msvcrt for libvosk) never free each other's memory (adr-0002's rejected branch c).

**One run of Command 3's desktop half**, from the project root in Git Bash: `cd NativeBridge~` → `ls -d` of the VS 2022 instance directory and `cmake.exe` (a moved tool fails here, named) → `cmake --preset windows-x64` with the instance pinned ("Visual Studio 17 2022", x64, vendor checks, DLL copy) → `cmake --build --preset windows-x64` (MSBuild, Release) → `./build-windows/bin/vosk-bridge-harness.exe` with the model, the 16 fixtures and the manifest → the JSON report on stdout; exit 0 = 16/16, 1 = a transcript mismatch (stop for the human, never a re-pin), 2 = operational error (`main.cpp` :262-264, unchanged). A failing configure or build returns non-zero and stops the `&&` chain.

## Non-functional realization

- **Toolchain drift fails loudly, naming the path, with no fallback.** The `ls -d` precheck is the first step after `cd`, so a moved Unity editor or a removed VS 2022 Community stops the command with `ls: cannot access '<path>'` before any tool runs, and before CMake can write a half-configured cache. Past it, nothing is searched for: `cmake.exe` is an absolute path; the Visual Studio installation is the pinned `CMAKE_GENERATOR_INSTANCE`, so a directory that exists but is not a registered VS 2022 instance fails in CMake rather than moving to another instance; the "Visual Studio 17 2022" generator considers no VS 2026 instance; MSBuild, `cl` and `link` come from that installation, not from PATH; Ninja is not involved. When the editor version or the VS location moves, the binding line is the one place to edit (adr-0003); step 2b and the README repeat it verbatim (Risks).
- **A degraded vendor fails loudly and links nothing else.** The `WIN32` branch names only `VOSK_LIB_DIR`'s `.lib` and `.dll`, so a Linux `libvosk.so` cannot be linked; the five existence checks run on every configure and name the missing file; `Runtime/Plugins/x86_64/` is on no search path and is never referenced; at run time the loader takes the vendor DLLs from the exe's directory before any PATH entry.
- **The Android build cannot move (F3), structurally.** Every Windows change sits behind `_WIN32`, `WIN32` or `MSVC`, which are false on the NDK toolchain; the Android arm of the macro, the `LINK_FLAGS` string and the `.so` imported location are textually unchanged. The symbol-list diff in Phase 1 is the enforcer.
- **The baseline cannot be quietly moved (F2).** The only `expectations.json` edit is the label; a divergent transcript is exit 1, which the binding and recipe text both name as a stop for the human (design §1 rule 4).
