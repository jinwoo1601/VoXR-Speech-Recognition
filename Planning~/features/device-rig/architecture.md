# Device Rig (Tier D) — Architecture

> **ABANDONED 2026-08-11.** Tier D was dropped from the automated-verification design (Amendment A1); the project's delivered scope is Tiers A/B/C. This doc is historical record only — nothing here is as-built on any merged branch. Phases 0–4 (of 5) were implemented and green on hardware, then archived at git tag `archive/tier-d` (`ff3ea62`) and the branch deleted; Phase 5 (F8/F9 — acoustic loopback + lifecycle delivery) was never started. Restore with `git checkout -b <name> archive/tier-d` if Tier D is ever revisited. Read alongside `HANDOFF.md`, which records exactly where the build stopped.

*Revised 2026-08-08 after a plan-validator pass against live source. The first draft's central bet — overriding `StartRecognitionCore` to start push mode and inherit the managed drain path — **does not work**, and §3 now records why and what replaces it. Builds the adb-driven on-device rig that runs the shipped arm64 bridge on a real Quest: two new test assemblies, a host-provisioning tool committed in this repo, a device prep + run script pair, and the four on-device checks. Realizes F1–F16 (`Planning~/features/device-rig/requirements.md`); the design contract is `Planning~/design-docs/automated-verification.md` §8 + DR-3. The governing driver is a constraint, not a performance budget: design §3 licenses **no change to shipped runtime behavior** and grants Tier D no new seam, so every capability the rig needs must be reached through what already exists.

## 1. Purpose & responsibilities

Owns: the on-device test assembly and its four checks; the shared test assembly; the host-provisioning editor tool; the prep/run tooling and its verdict logic; the `device-check` agent and the verification-binding rewrite.

Does not own: the fixture corpus and manifest (Tier B, frozen); the bridge ABI (Tier C, frozen); the process-global-bridge defect (issue #57 — routed around, not fixed); the `vosk_bridge.h:50-52` input-level contract error (issue-lane); the Windows editor pipeline.

## 3. The seam analysis — corrected

`BridgeNative` is `internal` to `Jinwoo1601.VoXR.Runtime` (`Runtime/Native/BridgeNative.cs:14`) and its three push members have **no managed caller anywhere in the repo** (`:53`, `:60`, `:64`). The first draft proposed reaching push mode by overriding `internal virtual void StartRecognitionCore()` (`Runtime/VoxrSpeechRecogniser.cs:212`) on a test subclass, expecting the rest of the managed path to inherit.

**That fails, for a reason visible only in the method body.** `StartRecognitionCore` is a two-line wrapper (`:212-215`) delegating to `StartRecognitionAsync` (`:217-237`), which performs the `_bridgeAvailable` guard, `await InitialiseAsync()` (`:222-223` — the only thing that loads the model and calls `vosk_bridge_init`), and the Android permission gate, before reaching the **private** `StartRecognitionInternal` (`:275-294`). That private method is the sole site of both `vosk_bridge_start()` (`:283`) and `_isRecognising = true` (`:285`) — and `_isRecognising` is a private field (`:46`) no subclass or IVT grant can reach. `Update()`'s drain loop is gated on it: `if (!_bridgeAvailable || !_isRecognising) return;` (`:435`). An override would therefore start push mode on an **uninitialised** bridge and never drain a single result.

The repo already documents this exact behavior, in the file the first draft cited as proof the seam works — `Tests~/Runtime/VoxrPushToTalkPauseTests.cs:28-29` notes the base `Update()` "returns early while the base's own `_isRecognising` stays false". Tier A's double depends on that property; Tier D needed its opposite.

**What replaces it — a deliberate coverage split.** The push check drives the ABI directly (§4.2); the capture-mode checks drive the *real, unmodified* `VoxrSpeechRecogniser` (§4.3, §4.4). Between them the suite still covers everything, and notably §4.3/§4.4 exercise `Update()`'s `BridgeNative` drain branch (`:435-463`) — which **no tier covers today**, because Tier B runs the `UNITY_EDITOR_WIN` branch above it (`:426-433`) instead. The split costs one thing honestly: no single device test spans fixture-audio → managed events end-to-end. That combination is Tier B's job, in the editor, where it already passes.

### 4.2 Push-audio integration (F5)

Direct-ABI, from the device test. **The sequence mirrors `NativeBridge~/harness/main.cpp` exactly** — Tier C already solved this and the first two drafts of this section did not carry it over.

*Once per suite:* `ModelExtractor.ExtractModelAsync` (see below) → `vosk_bridge_init(modelPath, 16000f, -18f)` → `vosk_bridge_set_grammar`. Grammar must precede start: `vosk_bridge_set_grammar` returns `ERR_ALREADY_RUNNING` while running and recreates the recognizer via `vosk_recognizer_new_grm` (`NativeBridge~/src/vosk_bridge.cpp:352-365`).

*Per fixture:*
1. `vosk_bridge_start_push`
2. push the fixture in chunks
3. **push padding** — `48000 + kCapacity` zeros (1 s of silence so endpointing fires in sample time, plus a full ring capacity so `consumed >= pushed - capacity` guarantees every fixture sample was consumed). Without it, up to **1.365 s** of every 2.08–4.64 s fixture is abandoned in the ring when the loop exits, and the truncation would masquerade as arm64 divergence against the new device baseline.
4. drain
5. `vosk_bridge_stop`
6. **drain again** — this is where the asserted transcript appears. The final is produced *inside* `stop`: the loop flushes `vosk_recognizer_final_result` into the queue after `g_running` clears (`:154-165`), and `stop` joins the thread (`:283-294`). Draining only before `stop` misses it; `vosk_bridge_destroy` → `reset_pipeline()` → `g_result_queue.Clear()` (`:59-66`) would then discard it. The shipped managed path drains after stop for exactly this reason (`Runtime/VoxrSpeechRecogniser.cs:314-327`).
7. `vosk_bridge_reset`

*Once at the end:* `vosk_bridge_destroy`.

**Pacing is on short writes, with a stall guard.** `vosk_bridge_push_audio` returns samples actually written, clamped to free ring space (`vosk_bridge.cpp:335-339`), or a **negative** error on misuse; it never returns `RingBufferOverflow` (4) — that reaches managed code only from the capture-mode overflow path, which push mode is built never to hit, and the binding's comment warns the return must be negated before being read as an error (`Runtime/Native/BridgeNative.cs:55-57`). A short write means drain-and-retry. It never blocks, so a dead consumer is observable via `-ERR_NOT_RUNNING` — but a *live-but-wedged* one returns 0 forever, so the push loop carries the harness's bounded stall guard (no progress for ~10 s → named failure). An unbounded spin inside a `[UnityTest]` coroutine would hang the player and surface only as a heartbeat timeout, the exact conflation F11 exists to prevent.

**Model path.** `vosk_bridge_init` needs an extracted model directory, and the only producer is `ModelExtractor.ExtractModelAsync` (`Runtime/ModelExtractor.cs:20`) — `internal`, and therefore a **third** internal type the D1 grant covers alongside `BridgeNative` and `VoxrWavReader`. The test must extract it itself rather than letting a `VoxrSpeechRecogniser` initialise first, because a second `vosk_bridge_init` returns `ERR_ALREADY_INITIALISED` (`vosk_bridge.cpp:212-213`). `sampleRate 16000f` and `micGainTargetDb -18f` are pinned to match Tier C's decode regime (`harness/expectations.json`), or cross-tier comparison is meaningless.

**Fixture and manifest loading on device** — the open question requirements §9 handed here. `File`-based reads cannot see inside the APK, so `VoxrWavReader.ReadFile` (`Runtime/Testing/VoxrWavReader.cs:15`) is unusable and both existing corpus loaders are editor-only (they resolve paths through `UnityEditor.PackageManager.PackageInfo`). The device path is: `UnityWebRequest` against `Application.streamingAssetsPath` — the mechanism `ModelExtractor` already uses on Android (`Runtime/ModelExtractor.cs:134-146`) — then `VoxrWavReader.Read(byte[])` (`:23`) for audio, and `VoxrAudioTestSuiteAsset.FromJson(string)` for the manifest — an **instance** method on a `ScriptableObject` (`Runtime/Testing/VoxrAudioTestSuiteAsset.cs:14, :29`), so it needs a `ScriptableObject.CreateInstance<VoxrAudioTestSuiteAsset>()` first. It parses the manifest correctly as-is; `JsonUtility` ignores the extra `voice`/`phrase`/`peak` keys. No new parser is written.

Transcripts are asserted from the drained JSON against a **committed device baseline** at `Tests~/Fixtures/audio/device-baseline.json` — same role as Tier C's `harness/expectations.json`, generated by a `--write-baseline`-equivalent mode on first green device run and committed thereafter. **Intents** are asserted by feeding each final transcript into `VoxrCommandRecogniser.InjectText`, with `BufferWindow`/`CommandCooldown`/`EagerFlushOnCompleteMatch` set as Tier B does (`Tests~/Runtime/VoxrWavReplayTests.cs:71-73`) — pushed audio is not wall-clock paced and the parser's buffering is `Time.time`-based.

The grammar JSON itself comes from `VoxrCommandRecogniser.TestGrammarJson` (`Runtime/Commands/VoxrCommandRecogniser.cs:831`, internal — covered by the D1 grant) after `DemoGrammar.Configure`, not from `VoxrCommandParser.GenerateGrammarJson`, which is a public *instance* method with no accessible route from a configured recogniser.

### 4.3 Mic liveness (F6, F7)

Capture mode, real unmodified `VoxrSpeechRecogniser`: start, poll `vosk_bridge_get_input_level()` for a few seconds, assert a rise above the noise floor within a timeout.

**No pre-start zero assertion** — the first draft required one to defeat a stale level surviving from a prior session. It cannot: `start_internal` stores `0.0f` into `g_input_level` unconditionally on every start (`NativeBridge~/src/vosk_bridge.cpp:179`), before the recognition thread launches, for both capture and push. The real residue is narrower — a self-exited loop leaves the level non-zero *while stopped* — and asserting zero pre-start would flake against exactly that, failing for a reason that is not a dead mic and violating F11.

Falsifiability (F7) comes instead from a **bounded negative control**: a separate run in which capture is disabled by `adb shell pm revoke <pkg> android.permission.RECORD_AUDIO`, asserting the liveness check fails. Three hazards it must respect. The revoke makes `Permission.HasUserAuthorizedPermission` false, so the start routes into `RequestMicPermissionThenStart` and its `while (!responded) yield return null` (`Runtime/VoxrSpeechRecogniser.cs:262-263`) waits forever for a human tap — so the test carries **its own timeout** and asserts "no level rise within N seconds" rather than awaiting the start. The in-headset dialog it raises is the one `disable_dialogs` would suppress, which D7 makes PIN-gated and optional — so the negative control is documented as leaving a dialog on screen that the *next* prep run clears, rather than assuming it never appears. And its verdict is an **inverted** criterion, since §4.7's green rule (`failed="0"`) would otherwise call a successful negative control a failure. Prep re-grants afterwards.

### 4.4 Acoustic loopback + latency (F8)

Nothing exists for this — there is no `AudioSource` anywhere in the repo. The test creates one: fixture floats → `AudioClip.Create` + `SetData` → `AudioSource.Play()` out the Quest speakers, with the real recogniser in ordinary capture mode. **It must also create an `AudioListener`** — Unity emits no audio at all without an active one, and a UTF-generated player scene has none; omitting it would make F8 fail silently for a reason unrelated to acoustics.

**Latency is measured from end-of-playback to `OnFinalResult`**, not from playback start. The figure F14 replaces is defined in `KNOWN_LIMITATIONS.md:280` as latency *"after speech ends"* (0.5–1.0 s). Fixtures run 2.08–4.64 s, so a playback-start frame would produce ≈2.6–5.6 s and silently overwrite an after-speech-ends figure with an including-the-utterance one — same word, ~4× apart. **Calibration and the trend file** — the two artifacts requirements §9 asks this doc to place. The *calibration* is a committed per-fixture speaker-volume + recognition-threshold set at `Tests~/Fixtures/audio/loopback-calibration.json`, produced by a one-off calibrated run and re-run only when the acoustic setup changes; it is not a per-run step, so a run cannot silently re-baseline itself. The *latency trend* appends to `Tests~/Fixtures/audio/latency-trend.json` (fixture, measured ms, run timestamp). **"Gross" is defined concretely:** hard-fail when a fixture's measured latency exceeds 3× the median of its committed trend entries, or exceeds 3000 ms absolute — chosen to sit far above the 0.5–1.0 s working range and well above room-to-room variance, so it catches a regression in kind rather than in degree.

### 4.5 Lifecycle delivery (F9)

No `SendMessage`, no reflection — that is Tier A's editor mechanism, both are IL2CPP-stripping risks with nothing preserving them (no `link.xml` exists; `[Preserve]` appears only on the two native binding classes), and a synthetic invocation cannot answer whether *Android* delivers the callback. The host fires the real broadcasts — `adb shell am broadcast -a com.oculus.vrpowermanager.prox_far` (doff) and `…prox_close` (don) — while the device test logs a marker on pause/resume receipt and the host confirms via `adb logcat -s`, plus recognition-state assertions after resume. Note the interaction with §4.6: `prox_close` is also the rig's primary auto-sleep defeat, so the `prox_far` window deliberately removes it for the duration of this check. The window is kept short and `prox_close` is re-fired immediately after, so the device cannot drift into sleep mid-suite.

**Design correction — RATIFIED by the human in-conversation, 2026-08-08.** Design §8.3.4 names the pair `prox_open`/`prox_close`; `prox_open` does not exist, and Meta documents `com.oculus.vrpowermanager.prox_far` for "headset removed" (verified against Meta's Scriptable Testing Services documentation, 2026-08-08). `prox_close` is correct as written. The human ruled this a factual correction to a command string rather than a change to the locked decision — which is *"drive proximity broadcasts to test lifecycle delivery"*, and is untouched. No design branch, no G1 reopen. Recorded here and in requirements §9 rather than self-authorized by this plan.

### 4.6 Device prep (F2)

`Tests~/DeviceRig/prep.sh`, idempotent, all commands `adb -s "$SERIAL" shell …` with the serial resolved up front (no device → named nonzero exit, never a hang). Package name comes from a single constant shared with §4.8, since Phase 1 changes it from the URP-template default.

- *Baseline, PIN-free:* `am broadcast -a com.oculus.vrpowermanager.prox_close` (fake "headset worn"; also the primary auto-sleep defeat); `setprop debug.oculus.guardian_pause 1`; `pm grant <pkg> android.permission.RECORD_AUDIO`.

**The grant must run after install, and UTF gives no hook between its install and its test start.** On a cold run (F3's acceptance case) the package does not exist when prep runs, so a single pre-run `pm grant` silently fails and the first `StartRecognition()` stalls forever in `RequestMicPermissionThenStart` waiting for a human tap. `run.sh` therefore resolves this structurally: it performs a **build-and-install pass first** (UTF's build step, or an explicit `gradle`/`adb install` if `-testPlatform Android` proves not to separate them — §8), then prep grants, then the test run proceeds against an already-installed, already-granted package. Prep remains idempotent and re-runnable on its own for warm runs.
- *Optional, PIN-gated:* `content call --uri content://com.oculus.rc --method SET_PROPERTY --extra 'disable_guardian:b:true' --extra 'disable_dialogs:b:true' --extra 'disable_autosleep:b:true' --extra "PIN:s:$VOXR_DEVICE_PIN"`. Its only gain over the baseline is `disable_dialogs`; skipped with a logged notice when unset, never echoed. The PIN is the Meta **account purchase PIN** (Meta documents `1234` as the default when none is set), unrelated to store publication.

`RECORD_AUDIO` has something to grant because the package ships `Runtime/Plugins/Android/VoXR.androidlib/AndroidManifest.xml:4`, which merges into any host APK.

**Amendment, 2026-08-09 (Phase 2 implementation) — the watcher is restored, and this paragraph was the deviation.** The paragraph above resolves the grant-ordering problem structurally and drops the watcher entirely. That inverted the canon: locked design §8.1 mandates "`pm grant <pkg> android.permission.RECORD_AUDIO` after install, **plus a watcher so a permission prompt never stalls a run**", and requirement F2 repeats the clause verbatim as a Must. The structural resolution is not wrong — it is simply not sufficient on its own, and its load-bearing half (the explicit build-and-install pass) cannot be written or verified without a cabled Quest, because §8's open question is precisely whether `-testPlatform Android` separates build from run. Phase 2 therefore implements **both**: the warm path exactly as this section specifies (prep grants before the run, against an already-installed package), and the watcher for the window this section cannot cover. This restores §8.1/F2 conformance rather than bending it, so no design reopen — and §4.6 itself already makes the explicit pass conditional ("*or an explicit `gradle`/`adb install` if `-testPlatform Android` proves not to separate them*"), which Phase 3 settles on first device contact.

**The watcher polls for the whole Unity window, not until its first success.** Granting once and exiting would make it a no-op on every warm run — the package is present at t=0, so it would finish seconds in, before Unity had started building, leaving unwatched the exact install window it exists to cover. If UTF's deploy turns out to be uninstall-then-install rather than `adb install -r`, the permission is dropped mid-run with no watcher alive and the run stalls in `RequestMicPermissionThenStart` — the stall this section identifies. So `prep.sh --watch-grant <sec>` re-grants whenever it finds the package present and the permission missing, and exits when `run.sh` deletes its sentinel file after the Unity call, or when `<sec>` elapses.

### 4.7 Runbook and verdict (F3, F4, F11)

`Tests~/DeviceRig/run.sh` performs the **full package-test procedure**, not just the Unity call — the first draft omitted it, and without it Unity cannot see a `~`-suffixed folder and the only possible outcome is F4's own "zero tests" red:

1. Assert the editor is closed (`<host>/Temp/UnityLockfile` absent).
2. Rename `Tests~` → `Tests`; confirm `"testables"` in the host manifest.
3. Build + install, then prep-grant (§4.6), then `Unity.exe -runTests -batchmode -projectPath "D:\Game Development\VoXR TestGround" -testPlatform Android -buildTarget Android -playerHeartbeatTimeout <n> -testResults <win path>.xml -logFile <win path>.log`.
4. Revert `Tests` → `Tests~`, restore the host's prior active build target, and delete **every** Unity-generated `.meta` in the tree plus the root `Tests.meta`. Not a folder enumeration — `git ls-files "Tests~" | grep -c .meta` is 0, so no `.meta` under `Tests~` is committed and all of them are generated; enumerating the four new directories (`Device/`, `Shared/`, `DeviceRig/`, `DeviceRig/HostSetup/`) invites a partial clean that leaves the tree dirty against Phase 2's own `git status` check. `rm` is blocked here; use `find … -delete`.

**Verdict is computed separately from the exit code**, because Unity documents no common definition for its exit codes. Green requires all three: `failed="0"`; `total=` at or above the expected count; and `start-time` newer than the run's start — **compared in UTC**.

The expected count is authored in Phase 2 when the device suite is one trivial test, and Phases 3–5 each add more; a stale-low expectation would reproduce exactly the vacuous green F4 exists to prevent. It is therefore **not a hand-maintained number**: `run.sh` derives it by counting `[Test]`/`[UnityTest]` methods under `Tests~/Device/` at run time, so it cannot drift behind the suite it guards. The attribute is UTC (`start-time="2026-07-30 11:19:03Z"`), the host is `+0900`, and `run.sh` executes in WSL, so a naive local-time comparison would mark every fresh XML nine hours stale and never go green. Each infrastructure condition maps to its own named outcome; the F7 negative control runs under an inverted criterion.

**Amendment, 2026-08-09 (Phase 2 implementation).** Five corrections and four settlements, each measured or reasoned from live evidence rather than assumed.

**The verdict parse must be anchored to the `<test-run>` root element.** Measured against a real result XML from this project (`<host>/TestResults/phase0-PlayMode.xml:2-4`): `failed=`, `total=` and `start-time=` repeat on the root **and on every nested `<test-suite>`**. On a red run the root carries `failed="1"` while sibling suites containing no failures still carry `failed="0"`, so an unanchored `grep -q 'failed="0"'` reports **green on a red run** — the exact false green this section exists to prevent, reintroduced by its own implementation. `run.sh` extracts the first `<test-run …>` opening tag and reads attributes only from that string. The consequence for the acceptance is sharper than the fix: synthetic XMLs must carry nested suites, including a red-root/green-children case, or a wrongly-unanchored parser passes the entire synthetic sweep.

**Freshness is checked on two clocks, because `start-time` is not written on this machine.** This section frames the hazard as a *zone* problem (UTC vs `+0900`) and that framing is correct but incomplete. Under `-testPlatform Android` NUnit executes in the player, so `start-time` carries the **Quest's** clock while the run's start carries WSL's. A device clock behind the host marks every fresh XML stale forever; ahead, it disables the check silently. Freshness therefore requires the results file's **mtime** (host clock, authoritative for "did this run write it?") to be newer than the run's start **and** this section's literal `start-time` condition to hold. Disagreement is not green and is reported as its own outcome, `results-clock-skew`, rather than mislabelled as staleness. Whether `start-time` really originates device-side is reasoned, not measured — no device run has happened; Phase 3 settles it.

**AMENDMENT 2026-08-09 — settled by measurement, and two corrections fall out of it.** `start-time` does originate device-side: a real run stamped `2026-08-09 01:20:48Z` against a logcat local time of `10:20:48` on a `+0900` device, so the two-clock design is right in substance. Two things about *where to read it* were wrong.

1. **The root element is never stamped on a player run.** Both real runs — one zero-test, one fully green — wrote `<test-run … start-time="0001-01-01 00:00:00Z">`, NUnit's unset sentinel, while every nested `<test-suite>` carried the true device time. Reading only the root therefore pins `start_fresh` at 0 forever and reports `results-clock-skew` on **every** device run, green or not. So `start-time` is read from the root when stamped and falls back to the first nested `<test-suite>` otherwise. This narrows, but does not weaken, the anchoring rule above: `failed=` and `total=` remain root-only, because their hazard is the opposite one — nested suites read `failed="0"` under a red root.
2. **The count must be checked before freshness.** A run that executes nothing has no clock to be fresh on, so a freshness-first verdict answers `results-clock-skew` — sending the reader to fix a device clock that was never wrong — when the true and actionable answer is `zero-tests`. Order reversed; a stale-but-complete XML still reaches the freshness checks and still reports `stale-results`.

**The expected-count derivation is one alternation, not a list of greps.** This section names `[Test]`/`[UnityTest]`; the implementation also counts `[TestCase`, because a `[TestCase(…)]` attribute contributes a test case to `total`. `[TestCaseSource` is a strict superstring of `[TestCase` and is therefore **not** counted separately — doing so would double-count every `[TestCaseSource]` and push the floor *above* the true `total`, turning every run falsely red. The pattern is `\[(Test|UnityTest)[],(]|\[TestCase`, whose character class also catches `[Test(ExpectedResult = 1)]` and `[Test, Category("x")]` that a bare `\[Test\]` would miss — that direction silently weakens the guard. Comment-only lines are stripped; `#if`-guarded attributes remain a known over-count path, flagged in a code comment for Phases 3–5.

**Step 4's "restore the host's prior active build target" is done by file backup, not by parsing.** `Library/EditorUserBuildSettings.asset` is a **binary** asset — `strings` exposes the field names but not the values — and `grep -rIl 'm_ActiveBuildTarget'` across the host's `ProjectSettings/` and `Library/` finds no text-readable source anywhere. With the editor asserted closed (step 1), backing the file up before the run and copying it back afterwards restores the target exactly, with no parsing and no extra Unity launch. Two caveats recorded rather than hidden: preflight must restore and clear a *leftover* backup from a crashed run before taking a fresh one, or a re-run backs up the already-switched file and loses the original target permanently; and the same Unity run also rewrites `Library/BuildSettings.asset`, `BuildProfileContext.asset` and `BuildProfiles/`, which are regenerable caches this does not restore — sufficiency is an assumption Phase 3 confirms.

**The renamed window is narrowed to the Unity invocation alone.** Step 3 places prep between the rename and the run, but `mv Tests~ Tests` invalidates `Tests~/DeviceRig/` and every `prep.sh` path under it — a `prep.sh` invoked after the rename dies with "No such file or directory". The order is therefore prep → start watcher → **[rename → Unity → revert]** → stop watcher → verify grant → verdict. No `prep.sh` call happens while the tree is renamed; the watcher resolves its paths and sources `rig.env` before the rename, so it is unaffected. Cleanup still runs from an `EXIT` trap, which must capture `$?` on entry, guard every step, and exit with the captured status — a preflight failure fires the trap with the tree never renamed, and an unguarded `mv` there would abort the remaining cleanup under `set -e` and lose the real exit code.

**Settlements this section left open.** `-playerHeartbeatTimeout` is **1800 s** with an outer `timeout` of **3600 s** (the inner must sit below the outer, or the outer pre-empts and masks `heartbeat-timeout`); both are unmeasured first guesses sized for first-install imports, local to `run.sh` and env-overridable, tuned at first device contact. Run artifacts land in `$VOXR_RIG_HOST/DeviceRigResults/` — outside this repo so `git status` stays clean, at fixed filenames so the staleness check has something to catch, and a pre-existing XML is deliberately **not** deleted before a run. `adb` comes from a new `rig.env` constant `VOXR_RIG_ADB`, derived from `VOXR_RIG_UNITY` rather than hardcoded: both installed copies of `adb.exe` are byte-identical (md5 `baa238bba5155683308510d4339b65a4`, platform-tools 36.0.0), so the version is not the question — the coupling to the editor that builds the APK is. `run.sh` also exposes `--verdict-only <xml> [--since <epoch>] [--expected <n>]`, which is how the synthetic acceptance runs and how a human re-reads a previous run; `--since` defaults to *now*, so a pre-existing XML reads stale.

**`set -e` discipline, which this section's own outcomes depend on.** `grep -c` and `grep -q` return 1 on zero matches, and under `pipefail` that kills the script inside a command substitution — so "zero tests" and "no results XML", both named outcomes above, would abort with **no `VERDICT:` line at all**. Every grep whose empty case is a legitimate outcome is written `$( … || true)`, and the Unity invocation is bracketed by `set +e` / `set -e`. `provision.sh` already does both (`:210`, `:267`, `:322`, `:227-236`); the hazard is inheriting its style without its guards.

**AMENDMENT (Phase 4, 2026-08-09) — the inverted criterion is realized, and one classifier order was wrong.**

This section said only that "the F7 negative control runs under an inverted criterion" and left the mechanism to §4.3, which pointed back here. The loop is closed as follows.

*The inversion is a rig mode, `run.sh --negative-control`, and it does **not** touch the green rule.* F4 defines green as `failed="0"` unconditionally, so a run that succeeds by failing a test cannot borrow that word without giving the rig's most important slug two meanings. The negative control reports **`negative-control-falsified`** instead, which `verdict()` exits 0 for alongside `green`. Its criterion: total at or above the floor, fresh, **exactly one** failure, and that failure carrying the `VOXR_DEVICE_MIC_SILENT` sentinel. Anything else is `negative-control-not-falsified` (nothing failed — the check is vacuous) or `negative-control-wrong-failure` (contaminated). Every infrastructure outcome passes through unchanged, because a stale or zero-test run means the same thing in either mode. New device-state outcomes: `mic-revoke-failed`, `mic-state-unknown`, `mic-regranted-midrun` (from prep's `mic-still-granted`).

*Ordering correction, measured on hardware.* The infrastructure classifier checked `rc=124` before the heartbeat pattern. On 2026-08-09 a real run produced **both**: the player never connected, the framework logged its heartbeat message at 1800 s, and Unity then **did not exit** — the outer `timeout` killed it at 3600 s. `run-timeout` therefore masked a cause the log had already named. Phase 2 assumed the outer ceiling could only pre-empt the heartbeat if `RUN_TIMEOUT` were configured below it (the README's invariant); in fact Unity hanging *after* its own timeout pre-empts it regardless. The heartbeat pattern is now checked first — the two orders differ only when both conditions hold, and then the heartbeat is the earlier and more actionable cause. A selftest case built from the measured shape locks it.

*And the outer `timeout` does not kill Unity.* `run.sh` framed this as unmeasured. It is now measured and **false**: after the kill, three `Unity.exe` processes survived (the batchmode one plus two `AssetImportWorker`s), holding the project lockfile — so the host is wedged until they are killed by hand, and WSL cannot even delete the lockfile while they live. WSL's `ps` cannot see them at all; `tasklist.exe` is required. The NOTICE now says so and gives the commands. Automatic killing was deliberately **not** added — silently terminating Windows processes is a behavioural change the human should opt into.

## 5. Decision register

- **D1 — A fourth `InternalsVisibleTo` grant.** *Canon judgement:* design §3's locked wording is *"No changes to shipped runtime **behavior**"*; an IVT attribute changes no behavior, so this is **inside** the non-goals and is not a G1 matter. An earlier draft of requirements §5 restated the constraint as "a production change in `Runtime/`", which is stricter than the design it paraphrases; that was a requirements-doc error, corrected on this branch (the locked design is untouched). *Why this over the alternative:* one additive attribute matching the three already present for the same purpose. *Rejected:* making the push bindings or `VoxrWavReader` `public` — a permanent, shipped API-surface change, which genuinely would be a design matter. *Surfaced for the human at G2* as the one place Tier D touches a shipping file.
- **D2 — Direct-ABI push, with capture-mode checks covering the managed drain path.** *Why:* the seam route is impossible without a runtime change (§3), and this split preserves full coverage — §4.3/§4.4 exercise `Update()`'s `BridgeNative` branch, which no tier reaches today. *Rejected:* overriding `StartRecognitionCore` (does not work — the drain gate is a private field); reflecting on `_isRecognising` (works in principle, but stakes the rig on IL2CPP reflection metadata surviving stripping, with no `link.xml` in the repo); adding a push API to the recogniser (a behavioral runtime change — reopens G1).
- **D3 — Latency trended, not gated.** *Why:* design §8.3.3 is explicit that speaker→mic differs from mouth→mic; a tight gate fails on room acoustics. *Rejected:* a fixed latency ceiling.
- **D4 — Liveness is a post-start threshold plus a bounded negative control; no pre-start zero assertion.** *Why:* `start_internal` already zeroes the level on every start, so the staleness the first draft guarded against cannot occur, while the guard itself would flake after a self-exited session. Falsifiability belongs in a negative control, which tests it directly. *Rejected:* pre-start zero read (guards a non-existent failure, creates a real one); fixing the bridge's stop-path zeroing (a native change — issue-lane).
- **D5 — Real broadcasts for lifecycle, not `SendMessage`/reflection.** *Why:* F9's question is whether Android delivers the callback; synthetic invocation cannot answer it, and both mechanisms are stripping risks. *Rejected:* reusing Tier A's driver — green, and proves nothing about the device.
- **D6 — Host provisioning committed here, applied to the host.** *Why:* the human's 2026-08-08 ruling; the host is unversioned, so anything living only there has no history. *Rejected:* a documented manual procedure.
- **D7 — Prep is PIN-free by default; the PIN is an optional enhancement.** *Why:* PIN-free equivalents exist for everything load-bearing (proximity broadcast for auto-sleep, `guardian_pause` for guardian); only `disable_dialogs` is PIN-only and those prompts are one-time. A rig that hard-requires a credential the user may not have set is blocked on a convenience. *Rejected:* requiring it; ignoring `SET_PROPERTY` entirely. *Canon note:* §8.1 names the command set without ruling it the only route — a realization choice, not a contradiction.
- **D8 — `DemoGrammar` moves to a shared assembly and becomes `public`.** *Why:* both tiers must decode against the same grammar; `internal` in any single test assembly cannot serve two. *Rejected:* duplicating it (already a hand-synced copy of the sample — a third copy compounds drift); an IVT on the test assembly (more machinery for a file that never ships).

### Phase 4 — persisted plan (2026-08-09)

Approved in plan mode after one independent validation pass against canon and live source, which found two blockers and seventeen lesser defects; all are folded in below. **Human-ratified decision, not to be re-litigated:** F7's inverted criterion is realized as a **rig mode**, `run.sh --negative-control`, not as a documented manual procedure and not as a test that flips its own assertion. **The success slug is `negative-control-falsified`, not `green`.** Validation caught that reporting `green` for a run whose XML carries `failed="1"` would break F4's unconditional *"green only when the results XML reports `failed=\"0\"`"* and design §8.2, and would give the one slug that matters most two meanings — against F11. A distinct slug exiting 0 satisfies F7 without amending F4, so **no canon amendment is needed here**, unlike Phase 3's F5 ruling.

**Why a mode and not a flipped permission.** The rig fights a revoked permission in three places: the background `--watch-grant` watcher would re-grant mid-run (`run.sh:483-488`); the post-run `--verify-grant` overrides the verdict with `permission-denied` (`:567-576`); and normal prep grants unconditionally (`prep.sh:283-310`, neutralised by ordering the revoke after prep rather than by changing prep).

**The liveness fixture runs FIRST, and cannot be made not to. Two attempts failed; both are recorded so the cycles are not spent again.** Measured from Phase 3's results XML, fixtures run alphabetically, so `VoxrDeviceMicLivenessTests` precedes both `PushAudio` and `RigSmoke`.

1. A class-level `[Order(100)]` is a **compile error** — CS0592, caught by the EditMode gate: NUnit's `OrderAttribute` is `AttributeTargets.Method` in this version.
2. Even compiling, it would do the opposite of what it reads like. `UnityEngine.TestRunner/NUnitExtensions/Runner/CompositeWorkItem.cs:236-245` inserts ordered children at the **front** (`Children.Insert(0, child)`) and sorts only that prefix (`Children.Sort(0, _countOrder, …)`); unordered children are appended after. A lone ordered fixture runs first, however high its number.

Since a fixture can only carry the `Order` property from a class attribute that will not compile, **fixture-level ordering is unavailable** — method-level `[Order]` orders methods inside a fixture and cannot reorder fixtures against each other. The alternative, renaming the class purely to game an alphabetical sort, is rejected: it encodes an invisible dependency on a discovery order measured once, and a future reader would have no way to know why the name was chosen.

**Running first is affordable**, which is why this is documented rather than worked around. This fixture bears the cold ~39 MiB model extraction instead of the push test (`ModelExtractor.cs:33-39` short-circuits only once `finalPath` exists) — that is exactly what `InitTimeoutSeconds = 180` budgets for, and the cost is *moved, not added*: whichever fixture runs first pays it. A cold extraction has never been timed by anyone; Phase 3's 9.48 s push fixture measured a device whose cache survived redeploy, so 180 s is margin over an unmeasured quantity, not a measured one.

The one real cost is the teardown race below: a leaked `g_initialised` now lands on the two fixtures that follow rather than on nothing. That path requires the Phase A timeout to fire — already a hard failure — and **cannot occur in a negative-control run at all**, where initialisation completes before the permission gate is reached. So the `failed == 1` criterion is not exposed to it. Order is confirmed from run 1's XML rather than assumed.

## 8. Risks & assumptions

- **UTF `-testPlatform Android` auto-deploy is unconfirmed.** Design §2 records it web-verified; Unity's current CLI reference says only that a BuildTarget runs tests on "a player built for the specified platform". First device contact confirms it or forces a manual build+install+run path in `run.sh`.
- **Immersive-app pause semantics without a provisioned scene** (§4.8). If the OS treats the UTF player as a panel app, F9 measures the wrong thing and Phase 1 gains a scene.
- **`AndroidMinSdkVersion: 25`** is below Quest expectations; raising it may not be sufficient alone (target SDK, graphics APIs). Phase 1 set it to **32** per the human's 2026-08-09 ruling. The risk runs both ways and only the upward half was recorded before: a min SDK *above* the connected device's API level makes the APK refuse to install. 32 is Android 12L, which Quest 3 ships and Quest 2 has shipped since its v47-era firmware update, so both install — but this becomes the first thing to check if `adb install` ever rejects the test player.
- **An editor-only `.cs` under `Tests~/DeviceRig/HostSetup/`** sits below no asmdef. Unity normally does not compile package scripts outside one, but if it does, `using UnityEditor` there is a hard error taking both suites red. Phase 1 verifies this early; the fallback is to ship it as a non-`.cs` template that `provision.sh` writes out.
- **Push-vs-lifecycle serialization is undocumented** (in-flight `Write` vs `RingBuffer::Reset()`), and a pre-existing joinable-thread `std::terminate` on restart-after-capture-error is live. Both are confirmed-unfixed Tier C findings; Phases 3–4 are where they would surface.
- **`vosk-model-small-en-us-0.15` lacks `cqb`/`railgun`** — undecodable on every tier. No committed fixture uses them.
- **The device baseline is a new artifact.** Device transcripts may differ from Tier B (editor libvosk) and Tier C (Linux x86_64) for the same fixture; divergence between tiers is information, not necessarily a bug.
- **The host project is unversioned**, so a green run depends on provisioning having been applied. F16 makes that recoverable, not automatic.
- **The device suite has no fast compile loop — measured, and it shapes Phases 3–5.** An `includePlatforms: ["Android"]` assembly is compiled only by a real Android *player* build, never by the editor at any active build target (§9). So every edit to a device test is syntactically unverified until a player build runs, and a typo surfaces as a build failure minutes later rather than as a red squiggle. Phases 3–5 should therefore batch device-test edits and treat "the test player built" as the first gate, before "the tests passed". The obvious shortcut — adding `Editor` to `includePlatforms` for a fast check — is **not** available: it would put the device tests into the editor PlayMode run, breaking F1's unchanged-count requirement and failing them against an absent arm64 bridge.
- **Not yet measured, by anyone:** every remaining claim about assembly discovery in a *player* build is still derived from asmdef contents rather than observed — Phase 3's first UTF Android build is where those become measurements.
