# Device Rig (Tier D) — Requirements

## 1. Feature & scope

Backlog line (design §11, row 3): adb prep script, UTF `-testPlatform Android` runbook, on-device suite (push-audio integration, mic liveness, acoustic loopback + latency measurement, lifecycle delivery via logcat handshake), `device-check` agent + binding update.

This feature realizes Tier D of the locked automated-verification design (`Planning~/design-docs/automated-verification.md` §8): "replaces the routine human in-headset pass with an adb-driven run Claude executes against a cable-connected Quest." It is the last item in the design's backlog; Tiers A (issue #49), B (`feat-wav-replay`), and C (`feat-bridge-push-audio`) are all merged. It consumes the fixture corpus Tier B committed and the push-mode seam plus input-level getter Tier C added to the bridge ABI (§11 "Depends on: 1 (fixtures), 2 (push mode, level getter)").

Tier D is the tier the other three are measured against. Per §4: "Tier D is the backstop that keeps Tiers B/C honest: B and C prove logic, D proves the shipped binary on the shipped hardware."

## 2. Why — verification value

Three change classes are marked human-only in the project's verification bindings: mic capture, MonoBehaviour lifecycle/pause behavior, and any native-bridge change. Tiers A–C automated everything that can be automated without hardware, and each is explicitly blind to the same things: the **arm64 binary**, JNI AudioRecord, Quest audio routing, and whether Android actually delivers `OnApplicationPause` at all. Every one of those blind spots is exactly where a shipped regression would live — the arm64 `.so` in `Runtime/Plugins/Android/arm64-v8a/` is the artifact package consumers actually load, and no tier to date has executed a single instruction of it.

Tier D closes that gap: it runs the shipped arm64 bridge against real libvosk on real hardware, proves the mic chain end-to-end through the permission and JNI path, measures acoustic latency instead of quoting anecdotes, and settles empirically whether the pause callback is delivered. When it lands, the "human-only" paragraph in the verification bindings shrinks to genuine human residue (§10) — device provisioning, human-voice realism, subjective feel — and every other on-device question becomes a check Claude runs (DR-3).

## 3. Observable behavior

With a Quest cabled and adb-visible, a single documented invocation prepares the device, builds and deploys the test player from the host project, runs the on-device suite, and streams results back. The run either reports green with a named count of executed tests, or reports red naming which check failed and why — and distinguishes a genuine test failure from an infrastructure failure (no device, build failure, permission denied, install failure, heartbeat timeout).

With **no** Quest connected, the same invocation fails fast with an unambiguous "no device — deferred" outcome. It never hangs, never silently succeeds, and is never mistaken for a green run.

On device, four things are observably true when the suite passes: committed fixture audio pushed into the real arm64 bridge decodes to the committed device baseline; the real microphone is demonstrably live (input level rises from a known-zero baseline once capture starts); fixture audio played out of the Quest speakers is heard by the Quest microphone and recognized, with the end-to-end latency recorded as a number; and the pause/resume lifecycle behaves as the recorded, measured device truth says it does.

## 5. Non-functional requirements

- **No shipped-runtime *behavior* change.** Design §3's non-goals are worded precisely: *"No changes to shipped runtime **behavior** beyond the minimal seams specified below"* — bridge push mode, the input-level getter, the editor playback mode, and at most a minimal internal recogniser seam for Tier A. **Tier D is granted no new seam.** If the rig turns out to require a behavioral change in `Runtime/` or `NativeBridge~/`, that contradicts locked design: stop, reopen the design on a design branch, re-lock (G1), then resume. Do not patch silently. *(Amended 2026-08-08, same day, before implementation: an earlier draft of this line read "a production change in `Runtime/`", which is stricter than the locked design it restates and would have made a behavior-neutral `InternalsVisibleTo` attribute a G1 matter. Corrected to track design §3's actual wording. A requirements-doc error is fixed on this branch; the locked design is untouched.)*
- **Nothing ships to consumers.** The on-device assembly lives under `Tests~/` (stripped by `release.yml`); host-project scene/StreamingAssets changes live outside this repo; `Planning~/` and the workflow layer are gitignored.
- **Reliability is a feature.** A green run must mean something and a red run must be worth investigating. Repeated runs on an unchanged tree agree. The loopback check is the one place flakiness is *expected*, and is bounded there by design (generous thresholds, calibration, latency trended not gated) rather than absorbed by loosening the whole suite.
- **Bounded wall-clock.** A warm run (APK already installed, no re-import) completes fast enough to be a routine per-change check rather than a ceremony; a cold run's slower path is documented so a long first run is not mistaken for a hang.
- **Zero human interaction during a run.** Once started with a prepared device, the run needs no headset donning, no dialog dismissal, and no permission tap (F2). A run that stalls waiting for a human has failed its purpose.
- **Ambient dependence stated, not hidden.** F6/F8 depend on the room. The procedure states the acoustic precondition (quiet room) and a failure caused by ambient noise is diagnosable as such from the output.

## 6. Non-goals / deferred

- **No fix for issue #57** (two recogniser components share one process-global bridge). Tier D routes around it (F10); fixing it is separate issue-lane work.
- **No CI or cloud device farm** (design §3): the rig targets the local, cable-connected Quest only.
- **No human-voice realism** (DR-2): the corpus stays TTS-only, and loopback is speaker→mic, not mouth→mic. Absolute recognition quality with real voices remains human spot-check (§10).
- **Not an absolute recognition-quality benchmark.** Like Tiers B and C, this asserts *regression* — same input, changed output — against a committed baseline.
- **No subjective feel** (§10): perceived latency, comfort, and push-to-talk UX stay human G2 judgments.
- **No replacement of Tiers A/B/C.** Tier D is the backstop, not a substitute; the cheaper tiers remain the per-change checks.
- **No Meta XR All-in-One SDK.** Nothing in §8.3 needs it; the host project uses OpenXR + the Meta Quest feature only.
- **No AAudio work** (broken on Quest per `KNOWN_LIMITATIONS.md`; capture stays on Java AudioRecord via JNI).
- **No new user-facing package features.**

## 7. Dependencies & assumptions

**Merged prerequisites (all satisfied):**
- Tier B `feat-wav-replay` (PR #50) — the fixture corpus and manifest at `Tests~/Fixtures/audio/`.
- Tier C `feat-bridge-push-audio` (PR #51) — `vosk_bridge_start_push()`, `vosk_bridge_push_audio()`, `vosk_bridge_get_input_level()` in the shipped arm64 plugin and bound in `Runtime/Native/BridgeNative.cs`. Nothing managed calls them yet; Tier D is their first consumer.
- Issue #55 / PR #56 — the PlayMode assembly's Android exclusion that F1 builds beside.

**Outside this repo (host project `D:\Game Development\VoXR TestGround`, unversioned):**
- OpenXR 1.17.1 with the Meta Quest feature, loader assigned to **Android only** with `InitManagerOnStart`, so the test player runs as an immersive VR app rather than a 2D panel app — without which F9 would measure panel-app semantics, not what package consumers ship. Configured and verified 2026-08-08; re-runnable via `VoxrTierDXrSetup.ConfigureAndroid`.
- A Vosk model present in the host project's StreamingAssets, extracted on device by the existing `Runtime/ModelExtractor.cs` path (Android StreamingAssets lives inside the APK and is read via `UnityWebRequest`).

**Human hardware prerequisites (§10 — only the user can satisfy these):**
- A Quest cabled, charged, and adb-visible; developer mode enabled via a verified Meta developer account; the "Allow USB debugging" prompt accepted *inside* the headset.
- Quest OS **v44+**, for the Meta Scriptable Testing Services commands F2 depends on.
- **Optional — the Store PIN of the account logged in on the device.** Verified 2026-08-08 against Meta's Scriptable Testing Services documentation: `SET_PROPERTY` (which sets `disable_guardian`, `disable_dialogs`, `disable_autosleep`) is PIN-protected, taking the PIN as `--extra 'PIN:s:####'`; the design does not mention this. The PIN is the Meta **account purchase PIN** (default `1234` when never set), not anything to do with store publication. It is **not a blocker**: the proximity broadcast defeats auto-sleep and `setprop debug.oculus.guardian_pause 1` handles guardian, both PIN-free; only `disable_dialogs` is PIN-only, and those prompts are one-time and hand-clearable. F2 therefore treats the PIN as an optional enhancement supplied via the environment, never committed, and logs when it is skipped.
- A quiet room for the F8 acoustic loopback.

**Known hazards designed around (confirmed but unfixed):**
- Input level is not zeroed on recognition-loop self-exit → F7.
- Push-vs-lifecycle serialization is undocumented (in-flight `Write` vs `RingBuffer::Reset()`), and the rig's natural threading shape is what hits it.
- A pre-existing joinable-thread `std::terminate` on restart-after-capture-error.
- `vosk-model-small-en-us-0.15` lacks `cqb` and `railgun` in its lexicon, so those demo-grammar words are undecodable on every tier. No committed fixture uses them, so the corpus is unaffected.

## 9. Open questions

- **Does the on-device test scene need a real XR rig (camera / XR Origin), or is initialising XR at startup enough for F9 to see genuine immersive-app pause semantics?** Unresolved — the architecture doc decides. The risk is that a scene with XR initialised but nothing rendering is treated by the OS differently from a real immersive app.
- **How do fixtures reach the device?** Design §8.3.1 says StreamingAssets; the shape (fixtures copied into host StreamingAssets by F16's provisioning vs. an adb push to app storage, and how the on-device tests locate them at runtime) is architecture's call. F16 settles the *reproducibility* half — whatever the mechanism, the provisioning of it is committed here — but not the mechanism itself.
- **Where does the latency baseline live, and what is "gross" regression?** F8 needs a concrete tolerance and a storage location for trended numbers.
- **What does the loopback calibration pass actually do**, and is it a per-run step or a committed calibration?
- **Does the doff broadcast produce `OnApplicationPause` at all?** F9 is written to measure rather than assume, but the answer materially shapes the test — and, if negative, is itself a documentation-worthy finding about the package's lifecycle behavior. **Naming correction — RATIFIED by the human in-conversation, 2026-08-08.** Design §8.3.4 names the pair `prox_open`/`prox_close`; `prox_open` does not exist, and the action Meta documents for "headset removed" is `com.oculus.vrpowermanager.prox_far` (verified 2026-08-08). `prox_close` is correct. The human ruled this a factual correction to a command string, not a change to the locked decision — which is that Tier D drives proximity broadcasts to test lifecycle delivery, and is untouched. Recorded here and in the architecture doc; no design branch, no G1 reopen.
- **Does UTF's `-testPlatform Android` actually build, deploy, and run automatically?** Design §2 records this as web-verified, but Unity's current command-line reference states only that a BuildTarget value runs "Play Mode tests that run on a player built for the specified platform" without confirming automatic deployment. Unity also documents that there is **no common definition for exit codes** — which is independent support for F4's non-vacuous green criterion. Confirm empirically on first device contact.
  **ANSWERED 2026-08-09, first device contact: yes.** One invocation builds the player, installs the APK, launches it, and collects results back over the editor connection; no explicit build or `adb install` step is needed. Unity's exit code is confirmed worthless as a verdict — it returned **0** for a run that executed no test at all.

- **F5's expectation split — AMENDMENT 2026-08-09, ruled by the human in-conversation.** F5 originally read "final transcripts **and parsed intents** are asserted against a committed device baseline", which leaves the intent expectations device-specific. They are not: the parser is pure C# and platform-independent, so given a reviewed transcript the intent it produces is not an arm64 property. The device baseline therefore holds **transcripts only** — the one genuinely arm64-specific artifact, mirroring Tier C's `expectations.json` — and intents are asserted against the **frozen** Tier B manifest, so an intent mismatch is always real signal rather than absorbed at the next re-baseline. The consequence is deliberate: if an arm64 transcript ever diverges enough to change the parsed intent, the run stays red until a human rules on it. Second ruling, same date: **a run with no committed baseline is RED** under its own outcome (`baseline-missing`), emitting the observed transcripts as an artifact to review and commit — a run with nothing to compare against proves nothing, which is the principle F4 already enforces against zero-test runs. Design §8.3.1 says only "assert transcripts/intents" and is untouched; **no G1 reopen**. Recorded here and in architecture §7's Phase 3 persisted plan.

- **F1's mechanism was wrong and is amended — AMENDMENT 2026-08-09, ruled by the human in-conversation.** F1 as written required "the new assembly builds into the Android player only, and contributes nothing to editor EditMode/PlayMode runs", which Phase 0 implemented as `includePlatforms: ["Android"]`. Measured on first device contact, **that assembly can never be executed by UTF at all**: the test framework selects the player's test assemblies from the ones loaded in the *editor* domain (`RuntimeTestLauncherBase.cs:27-28` → `EditorLoadedTestAssemblyProvider` → `EditorAssemblies.loadedAssemblies`), and an Android-only assembly is never loaded there. The first run built it into the APK, installed it, ran it, and executed nothing — reporting `total="0"` with exit code 0.
  The assembly is therefore made all-platforms and the Android-only property moves to an assembly-level `[UnityPlatform(RuntimePlatform.Android)]`. The **intent** of F1 is unchanged and is now stated in terms of what executes rather than what compiles: no device test runs in an editor suite. What changes is that the device assembly's tests become *visible* to an editor run and are reported skipped there, so "the same test counts" is no longer literally true and the acceptance now reads "executes the same tests". The design doc is untouched — §8.3 specifies on-device content and adb execution and never constrained assembly scoping — so **no G1 reopen**. Recorded here and in architecture §4.1.
- **Unverified, worth an early check:** does the editor PlayMode suite still compile while the active build target is **Android**? Reasoning says yes (Editor stays in the assembly's effective platform set), but it has never been measured. If an editor PlayMode run ever reports 0 tests, check the active build target first.
