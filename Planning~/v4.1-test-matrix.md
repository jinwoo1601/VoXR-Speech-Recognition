# v4.1 — Pending Command System Test Matrix

v4.1 (shipped as 0.15.0) adds a pending command system with partial
match, confirmation, and follow-up slot-fill. Commands can now enter a
"pending" state instead of being immediately rejected or fired, allowing
follow-up speech to fill missing slots or explicit voice confirmation
before execution.

New public API on `VoskCommandDefinition`:

- `AllowPartialMatch` — commands with unfilled required slots enter
  pending state instead of being rejected. Follow-up speech fills the
  missing slots.
- `RequiresConfirmation` — fully-matched commands enter pending state
  awaiting explicit voice confirmation before firing.

New public API on `VoskCommandRecogniser`:

- `OnCommandPending` event — fires when a command enters pending state
  (partial match or awaiting confirmation).
- `OnCommandConfirmed` event — fires when a pending command is
  confirmed. Also fires `OnCommandRecognised` and
  `OnCommandsRecognised`.
- `OnCommandCancelled` event — fires when a pending command is cancelled
  (timeout, explicit cancel, or preempted by a new complete command).
- `HasPendingCommand` property — true if a command is currently pending.
- `PendingCommand` property — the currently pending `VoskCommand`, or
  null.
- `CancelPendingCommand()` — programmatically cancels the pending
  command.

Key behaviours:
- `AllowPartialMatch` + `RequiresConfirmation` on the same definition →
  two-stage pending: first slot-fill, then confirmation.
- Configurable `pendingTimeout` (default 5s) and
  `pendingTimeoutBehavior` (`Cancel` or `FireAsIs`).
- Custom `confirmVocabulary` / `cancelVocabulary` Inspector arrays.
  Defaults: confirm = "confirm", "affirmative", "yes", "go ahead",
  "do it"; cancel = "cancel", "abort", "negative", "belay that",
  "never mind".
- Confirm/cancel vocabulary words are automatically merged into the VOSK
  grammar JSON.
- `RebuildGrammar()` defers while a command is pending; drains when the
  pending command resolves.
- `Configure()` and `SetActiveSets()` cancel any active pending command
  before rebuilding.

The matrix has three sections:

1. **Phase 0: Automated coverage.** All 20 test suites including the
   new `VoskPendingCommandTests`.
2. **Phases 1–4: Manual verification.** Injection-based spot-checks of
   partial match entry, follow-up slot-fill, confirmation flow, cancel
   vocabulary, timeout behaviours, dual partial+confirmation flow,
   preemption, debug window display, and Inspector authoring — exercising
   paths not covered by the automated tests.
3. **Phase 5: Regression.** Confirms v4.1 did not break any existing
   behaviour from v3.0–v4.0.

## Prerequisites

1. **Consuming project**: `D:\Game Development\voxsdk` (per
   `reference_unity_test_project.md`) — the package is referenced via
   `file:` and `manifest.json` already has
   `"testables": ["com.jinwoo1601.vosk-xr"]`.
2. **No device required.** Quest does not need to be connected. Native
   bridge does not need to be built. All phases work in the Editor.
3. **Unity 6000.3.7f1** (matches the Android toolchain pinned in
   `CLAUDE.md`).
4. **Command Recognition sample imported.** The sample's slot assets
   (6), command assets (11), and command set assets (3) are used by
   manual phases.

## Phase 1: Partial Match & Follow-Up Slot-Fill — Injection Driver

Enter Play Mode with the CommandDemo scene. Open **Window > VOSK XR >
Command Debug** for visual confirmation of matches. Use the text
injection bar at the bottom of the debug window.

These tests require a command definition with `AllowPartialMatch = true`.
Via a test MonoBehaviour or Console script, configure the recogniser
with a `launch_weapon` command (pattern: `launch {weapon} target
{target}`) with `AllowPartialMatch` enabled on the definition. Both
`weapon` and `target` are required slots.

### What this matrix proves

- The `AllowPartialMatch` flag correctly routes commands with unfilled
  required slots into pending state, and follow-up speech fills the
  missing slots via `TryMatchSlotByName()` — verified through both
  automated tests (32) and manual injection-based pipeline tests (7).
- The `RequiresConfirmation` flag correctly holds fully-matched commands
  in pending state until explicit voice confirmation or cancellation,
  with full default and custom vocabulary support.
- The dual-flag flow (`AllowPartialMatch` + `RequiresConfirmation`)
  correctly sequences two pending stages: slot-fill first, then
  confirmation.
- Timeout behaviours work correctly: `Cancel` drops the command,
  `FireAsIs` fires with whatever slots are filled.
- Custom `confirmVocabulary` and `cancelVocabulary` override the
  defaults and are recognised by the pipeline.
- Preemption works: a new complete command cancels an existing pending
  command and fires immediately.
- `CancelPendingCommand()` provides reliable programmatic cancellation.
- `HasPendingCommand` and `PendingCommand` properties accurately reflect
  pending state.
- `RebuildGrammar()` correctly defers during pending state and drains
  after resolution. `SetActiveSets()` and `Configure()` cancel pending
  before rebuilding.
- Confirm/cancel vocabulary words are merged into the VOSK grammar JSON.
- `VoskCommandAsset` Inspector fields (`allowPartialMatch`,
  `requiresConfirmation`) drive the same behaviour as code-based
  configuration.
- `VoskDebugWindow` displays pending command state (intent, reason,
  filled/unfilled slots, elapsed time) and clears it on resolution.
- All prior v3.0–v4.0 features (injection, debug window, batch test
  runner, command parsing, alias resolution, command sets, dynamic slot
  providers) continue to work — zero regressions across 231+ automated
  tests.

### What this matrix does NOT cover

- **Live audio input.** All tests use text injection. Any test that
  depends on what VOSK actually hears (transcription accuracy, grammar
  vocabulary coverage, confirm/cancel phrase recognition accuracy) is
  out of scope.
- **Quest 3 on-device regression.** No Android build or deploy is
  required for v4.1. The feature is pure C# recogniser-side logic.
- **Timeout precision.** The timeout test (3.1, 3.2) verifies the
  timeout fires, not that it fires at exactly `pendingTimeout` seconds.
  Unity's `Time.time` granularity and frame timing may cause minor
  drift.
- **Concurrent pending commands.** The system supports only one pending
  command at a time (new pending preempts old). Multi-pending scenarios
  are not tested because the design explicitly disallows them.
- **Provider exception handling during pending.** What happens if a
  follow-up slot-fill triggers a dynamic slot provider that throws is
  not tested.
