# v0.16.0 — Refactoring & Allocation Regression Test Matrix

v0.16.0 is a pure refactoring release. No new features, no public API
changes, no intentional behaviour changes (except one bug fix). The
v4.1 pending command system (v0.15.0) was never manually tested before
this refactoring landed, so this matrix serves double duty:

1. **Validate v0.15.0 features** — Phases 1-4 exercise the pending
   command system end-to-end through the now-refactored pipeline.
2. **Validate v0.16.0 refactoring** — Phase 0 catches automated
   regressions; Phase 5 expands regression coverage to stress
   refactoring-sensitive paths (extracted helpers, pre-allocated
   buffers, span-based access, cache correctness).

### What v0.16.0 changed (internal only)

- Extracted `VoskCommandRecogniser` into: `CommandDebouncer`,
  `CommandSetManager`, `DynamicSlotManager`, `GrammarManager`,
  `PendingCommandHandler`, `UtteranceBuffer`.
- Extracted JSON parsing from `VoskSpeechRecogniser` into `VoskJsonParser`.
- Pre-allocated reusable buffers replace per-utterance `List` allocations.
- Pre-computed `_slotNameCache` and `_optionalSlotElements` caches.
- `UtteranceBuffer.GetWordsSpan()` returns `ReadOnlySpan<VoskWord>`.
- `VoskCommandParser.ParseInternal()` accepts pre-split tokens and
  pre-built word-confidence dictionary.
- Span-based confirm/cancel vocabulary matching.
- Removed unsound `BorrowSlotArray`/`ReturnSlotArray` pool (bug fix).

## Prerequisites

1. **Consuming project**: `D:\Game Development\voxsdk` — package
   referenced via `file:` and `manifest.json` has
   `"testables": ["com.jinwoo1601.vosk-xr"]`.
2. **No device required.** All phases work in the Editor.
3. **Unity 6000.3.7f1**.
4. **Command Recognition sample imported.** The sample's slot assets
   (6), command assets (11), and command set assets (3) are used by
   manual phases.

## Phase 1: Partial Match & Follow-Up Slot-Fill — Injection Driver

Enter Play Mode with the CommandDemo scene. Open **Window > VOSK XR >
Command Debug** for visual confirmation of matches. Use the text
injection bar at the bottom of the debug window.

These tests require a command definition with `AllowPartialMatch = true`.
Via a test MonoBehaviour or Console script, configure the recogniser
with a `launch_weapon` command (pattern: `launch {weapon} target
{target}`) with `AllowPartialMatch` enabled on the definition. Both
`weapon` and `target` are required slots.

### What this matrix proves

- All 236 automated tests pass unchanged — the refactoring did not
  break any existing test-verified behaviour.
- The v0.15.0 pending command system works end-to-end through the
  refactored pipeline (Phases 1-4, first-ever manual validation).
- Extracted helper classes (`CommandDebouncer`, `CommandSetManager`,
  `DynamicSlotManager`, `GrammarManager`, `PendingCommandHandler`,
  `UtteranceBuffer`) preserve identical behaviour to the monolithic
  implementation.
- Pre-allocated buffer reuse does not cause cross-command slot
  corruption or stale data leakage (5.13, 5.14).
- Pre-computed caches (`_slotNameCache`, `_optionalSlotElements`) do
  not break pattern-to-slot mapping (5.20).
- `VoskJsonParser` extraction does not break result/word/alternative
  parsing (5.19, Phase 0 row 0.18).
- `UtteranceBuffer` span-based access and fragment accumulation work
  correctly (5.12).
- Rapid sequential commands do not corrupt debouncer or buffer state
  (5.10, 5.11).
- Extracted managers interact correctly across set switches and
  provider updates (5.15-5.17).
- Sequential pending commands process correctly through the extracted
  `PendingCommandHandler` state machine (5.18).
- The slot array pool removal (bug fix) is validated by the absence of
  corruption in rapid multi-command scenarios (5.10, 5.13, 5.14).
- All prior v3.0–v4.0 features continue to work: injection, debug
  window, batch test runner, command parsing, alias resolution, command
  sets, dynamic slot providers, NumberSequence slots.

### What this matrix does NOT cover

- **Live audio input.** All tests use text injection.
- **Quest 3 on-device regression.** No Android build required — the
  refactoring is pure C# recogniser-side logic.
- **Allocation measurement.** The matrix verifies correctness, not
  that allocations actually decreased. Profiling with
  `Unity.Profiling` markers or the Memory Profiler is a separate step.
- **Concurrent pending commands.** The system supports only one pending
  command at a time.
- **Performance under load.** Large slot sets, rapid provider cycling,
  or high-frequency injection are not benchmarked.
