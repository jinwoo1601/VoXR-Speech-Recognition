# v4.0 — Dynamic Slot Value Providers Test Matrix

v4.0 (shipped as 0.14.0) adds dynamic slot value providers for runtime
filtering of which slot values the parser accepts. The grammar
(VOSK vocabulary) is unchanged — only the parser narrows, avoiding the
~50ms audio gap that grammar rebuilds cause.

New public API on `VoskCommandRecogniser`:

- `RegisterSlotValueProvider(slotName, Func<string[]> valueProvider)`
- `UnregisterSlotValueProvider(slotName)` — returns bool
- `NotifySlotChanged()` — rebuilds parser only (no grammar change)
- `RebuildParser()` — explicit parser rebuild
- `RebuildGrammar()` — full grammar rebuild with stop/set/start cycle

Key behaviours:
- Provider returning `null` → slot uses full static values (no-op)
- Provider returning `[]` → nothing matches for that slot
- Provider returning subset → only those values match
- Aliases pointing to excluded canonical values are auto-pruned
- `NumberSequence` slots are unaffected by providers
- `Register` without `NotifySlotChanged` does not affect the parser

The matrix has three sections:

1. **Phase 0: Automated coverage.** All 19 test suites including the
   new `VoskDynamicSlotTests`.
2. **Phases 1–3: Manual verification.** Injection-based spot-checks of
   dynamic slot filtering, alias pruning, provider lifecycle, and
   interaction with command sets — exercising paths not covered by the
   automated tests (Inspector workflow, Play Mode injection driver,
   combined set + provider scenarios).
3. **Phase 4: Regression.** Confirms v4.0 did not break any existing
   behaviour from v3.0–v3.3.

### What this matrix proves

- The `RegisterSlotValueProvider` / `UnregisterSlotValueProvider` /
  `NotifySlotChanged` API correctly narrows and restores parser slot
  values at runtime, verified through both automated tests (17) and
  manual injection-based pipeline tests (9).
- Provider return semantics are correct: subset filters, null = full
  values, empty = nothing matches.
- Alias filtering works: aliases pointing to excluded canonical values
  are automatically pruned; aliases to active values persist.
- Providers survive grammar rebuilds (`RebuildGrammar()`) and command
  set switches (`SetActiveSets()`). The two features are orthogonal.
- `NotifySlotChanged()` does not touch the grammar (verified by
  reflection in automated tests) and does not flush the utterance
  buffer.
- `Register` without `NotifySlotChanged` does not affect the parser
  (lazy rebuild contract).
- Multiple providers on different slots work simultaneously.
- NumberSequence slots are unaffected by providers.
- All prior v3.0–v3.3 features (injection, debug window, batch test
  runner, command parsing, alias resolution, command sets) continue to
  work — zero regressions across 213 automated tests.

### What this matrix does NOT cover

- **Live audio input.** All tests use text injection. Any test that
  depends on what VOSK actually hears (transcription accuracy, grammar
  vocabulary coverage, audio gap timing) is out of scope.
- **Quest 3 on-device regression.** No Android build or deploy is
  required for v4.0. The feature is pure C# parser-side logic.
- **Performance under load.** Large slot sets (1000+ values), rapid
  provider cycling at frame rate, or many simultaneous providers are
  not benchmarked. The implementation is a dictionary lookup + parser
  rebuild, so scaling issues are unlikely for typical game use cases.
- **Provider exception handling.** What happens if a provider delegate
  throws is not tested. The current implementation does not catch
  provider exceptions — a throw in the delegate will propagate to the
  caller of `NotifySlotChanged()`.
