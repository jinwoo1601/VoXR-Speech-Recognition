# upgrade

## What this is

A project composed from the base drifts behind it: packs move, files change, keys appear. `upgrade` is how a project catches up without losing what was written locally — the dry run says what would happen, the human rules on it, and a snapshot of the working tree sits under the apply.

> The verb plans, reports, and writes. The snapshot, the human's word, and the verification after are this skill's.

## Bindings

The key is read from **the project being upgraded**, not from the base, because the snapshot is taken of that project's working tree.

- `vc` (required, the project's) — the snapshot procedure SNAPSHOT follows: the record, the read that confirms it, and how the human restores it. The binding absent, or present without its *Snapshot procedure* slot → stop in the first line, name the binding interview, and run nothing. The slot still `TODO` → stop the same way: an unanswered slot is no snapshot.
- The slot answering `none` → state that no snapshot is possible and wait for the human's explicit word that the upgrade applies without one.
- `process-docs` (optional, the project's) — the bindings file answering it, whose *Design docs* slot the report's `design docs:` line flags for step 7's second trigger.
- `doc-writer` not composed in this project while the report names keys to append or carries a `design docs:` or `path form:` line, or while a slot its `slots to revisit:` line names is ruled adopted or merged → say so at the stop, before the apply, so the human rules on an upgrade whose binding interview has no writer.
- `session-launch` (optional, the project's) — the List command and the Hub session name that `## A cross-project round`'s hub check reads. Absent, or a slot missing or `none` → the check reads as that section says of a missing slot; never a stop.
- `verification` (optional, the project's) — the *Path form* in which the hub check compares a session's `cwd` with the project's root. Absent, `none`, or the slot missing → the check reads as `## A cross-project round` says of a missing slot; never a stop.

## Prerequisites

Confirm before proceeding:
- The project holds `.claude/harness.json`, and its `base` points at a base that exists.
- The project's own work is committed or known: this skill does not check in, and the apply lands on whatever branch the project is on.

## Workflow

**A re-invoked run.** A compaction may re-invoke this skill between any two steps, so each run, once LOCATE has named the project, first runs `harness.py upgrade --held --root <project>` — inside an open catch-up merge with the FILE forms the catch-up's *The upgrade* act gives it, `--conflicted <list>` and, where `<list>` holds `.claude/harness.json`, `--sides <ours> <theirs>` and `--base-side <base side>` —, one command alone in its call, its Bash call given 600000 ms, which reads step 6's saved file for the project under this session's project root and removes an old run's, `harness.py upgrade --help` stating each case's rule; the table after this paragraph reads its first line.

| `upgrade --held` prints | The act |
|---|---|
| `none: …` | nothing is held: the run goes on as written and step 4 asks, any snapshot and exit the line names said beside the report there |
| `old: removed …` or `old: not removed …` | an old run's file, removed by the verb, its failure stopping nothing: the run goes on as written |
| `unrecorded: snapshot <id>; <file>`, then the dry run | the apply may have run with its outcome unrecorded: the dry run shown whole, and the run stops, putting it to the human by `.claude/references/core/ruling-form.md`, the snapshot's id shown — never asking step 4 as if nothing ran |
| `applied: snapshot <id>; <file>`, then the applied report | APPLY ran, and APPLY runs only after HARD STOP's word, so nothing is asked again: DRY RUN and steps 4, 5 and 6 do not run, and steps 7, 8 and 9 run on this applied report and snapshot's id |
| exit 1, `upgrade: refused` on stderr, or any other output | stop, and put it to the human by `.claude/references/core/ruling-form.md`, the refusal shown |

1. **BINDINGS** — read the project's `vc` binding **and its *Snapshot procedure* slot** before anything else. Either absent → stop in the first line, name the binding interview, and run nothing. The slot `TODO` → stop. The slot `none` → state that no snapshot is possible and wait for the human's explicit word.
2. **LOCATE** — the project root: the walk-up core's `add-pack` skill describes, an explicit root the human named, or a workspace root for `--all`. A session in this repository upgrades project zero by its root and runs `--all` over the workspace root.
3. **DRY RUN** — `harness.py upgrade --dry-run --save --root <project>`, one command alone in its call, its Bash call given 600000 ms, which saves the dry run in step 6's saved file under this session's project root, replacing it whole, the table below this step reading its first line. The report is shown **whole**, never summarized. Its migration lines are part of it, shown with the rest: a `status rewrite:` line with its `before:` and `after:` lines for each STATUS line the apply would rewrite, a `status left:` line for each STATUS line left to the human, a `status not read:` line where the STATUS file cannot be read, a `lite row left:` line, with its `as:` line where a form is given, for each `**Lite**` row of a design backlog, and a `lite rows not read:` line for each backlog that cannot be read. `upgrade`'s migration rewrites STATUS lines only, under step 4's word on the report — the `## Current` lines its `status rewrite:` lines name, in the hub's STATUS file where the project's `trees` binding is filled — and writes no locked doc and no binding value: each `lite row left:` row is listed for the human and never written, and each slot a `slots to revisit:` line names is the human's to rule on at step 4, step 7 writing only a slot ruled adopted or merged.

   | `upgrade --dry-run --save` prints | The act |
   |---|---|
   | `saved: <file>`, one line per project planned, then the dry run | the dry run shown whole: HARD STOP on it |
   | `unsaved: <reason>`, then the dry run | stop, and put it to the human by `.claude/references/core/ruling-form.md`: APPLY would have no saved dry run to compare with |
   | `manual: <slot>` alone | DRY RUN took the catch-up's flags: they are passed as `gate-close.md` *The upgrade*'s table passes the FILE forms, then this call again with them |
   | exit 1, `upgrade: refused` on stderr, or any other output | stop, and put it to the human by `.claude/references/core/ruling-form.md`, the refusal shown |

4. **HARD STOP — the human's word** on the report, on the snapshot the skill will take or the statement that none is possible, on any single `--take-theirs`, on step 7's same-version recompose, where a fill there changes a section a composed skill splices, and, for `--all`, on which projects to apply here and, in the workspace hub session, which to send a round request — each project put with its route by the `--all` paragraph below — put to the human by `.claude/references/core/ruling-form.md`. Each slot a `slots to revisit:` line names is a ruling of its own at this stop, one per slot in the line's order, the template's current value — the slot's line in the template the filling pack declares for the key, in the base — shown beside the project's own, the section's `- <Label>:` line: adopt the template's current value, each placeholder in it that the project's own line fills carried over filled, merge it into the project's own, or keep the project's own — where the template's value carries `TODO`, adopt and merge are one option, the slot answered anew by that value's current guidance; the line clears after this upgrade whatever is ruled, and where `doc-writer` is not composed and a slot is ruled adopted or merged, that too is said before the apply. Nothing is written before it. The word covers the report's `status rewrite:` lines with the rest — the apply writes each listed STATUS line as its `after:` line shows, all or none — and each `status left:` line and each `lite row left:` row is the human's, to act on after this upgrade, since `upgrade` writes none of them. Where `doc-writer` is not composed and the report names keys to append or carries a `design docs:` or `path form:` line, it is said **here**, before the apply.
5. **SNAPSHOT** — run the *Snapshot procedure* slot's record, then its confirming read; show the snapshot's id. A failed confirm stops the skill before the apply.
6. **APPLY** — `harness.py upgrade --snapshot-id <id> --root <project>`, one command alone in its call, its Bash call given 600000 ms, `<id>` the snapshot's id, or `none` where the human's word applies with none, with at most one ` --take-theirs "<file>"` the human named at the stop appended and DRY RUN's own flags where it took any; the verb writes the id to step 6's saved file, `.scratch/upgrade-<slug>-report.txt` under this session's project root, before the apply and the call's output and exit after it, applies, and compares the applied report with the dry run DRY RUN saved, `harness.py upgrade --help` stating each rule, and the table below this step reads its first line: the run the human ruled on is the run that must have happened, so a difference is a **stop on a difference**. Where the report lists `status rewrite:` lines, the apply writes the STATUS file first, before any composed file — in place in the project, or, where the project's `trees` binding is filled, in the hub, landed there by the verb itself as every hub write lands — and prints `upgrade: rewrote <m> STATUS lines in <cell>` after its last line, the outcome of that write, outside the comparison; a STATUS file changed since the verb read it, or a hub that refuses the write, refuses the whole apply with nothing written, a non-zero exit. The comparison takes the migration lines like any other line of the report: a difference among them stops the run as any difference does, any STATUS write already made.

   | `upgrade --snapshot-id` prints | The act |
   |---|---|
   | `matched: snapshot <id>`, then the applied report | steps 7, 8 and 9 run on it, an `unsaved:` line after the first told in one line, and the run goes on; where the display cut the applied report, steps 7 and 9 take their triggers from the saved file, which holds it whole |
   | `differs: <n> lines`, the lines, then the applied report | stop on the difference: the lines shown, put to the human by `.claude/references/core/ruling-form.md` |
   | `failed: exit <code>`, then the output | stop, show its output whole, and put it to the human by `.claude/references/core/ruling-form.md`; nothing later runs |
   | `manual: <slot>` alone | nothing applied, the saved file as DRY RUN left it: the flags passed as step 3's `manual:` row passes them, then this call again |
   | exit 1, `upgrade: refused` on stderr, with any `re-run:` line | nothing applied: stop, and put it to the human by `.claude/references/core/ruling-form.md`, the refusal shown, a fresh DRY RUN taking HARD STOP's word again |
   | a first line the display cut or that cannot be read | stop, and put it to the human by `.claude/references/core/ruling-form.md`, the saved file holding the whole output |

7. **BINDING INTERVIEW** — for each bindings file with appended keys, file `.scratch/doc-writer-<slug>-brief.md` from `.claude/references/core/decision-brief.md` and dispatch `doc-writer` through the Agent tool without a `name`, as core's `add-pack` skill does. One brief per bindings file; the dispatches run serially. The report's `design docs:` line is the second trigger: for the bindings file the `design docs:` line names, ask the human where this project's design docs live — the `process-docs` interview's design-docs question, `none` refused — then file that file's one brief from `.claude/references/core/decision-brief.md` and dispatch `doc-writer` as for the other triggers, also where the `design docs:` line is that file's only trigger; the brief carries the question asked and the human's answer, for `doc-writer` to write as the section's `- Design docs:` line, in place of the value that read `none` or added where a section answered slot by slot — one carrying the template's other slot lines — lacks the line, nothing else in the section rewritten. Any other `process-docs` section the `design docs:` line flags as lacking the line — a whole key answered `none` in any spelling (`- none`, `- None`, `- none — …`), a `none` line beside other bullets, prose with no slot lines — takes the whole `process-docs` interview in place of the design-docs question alone, `none` refused for *Design docs* only; the brief carries every question asked and every answer, and names as the form to match the template the filling pack declares for the key in the base, for `doc-writer` to rewrite the section from it — the heading, the comment line, one filled line per slot — nothing of the old section kept. A file the `design docs:` line names that also has appended keys takes one brief carrying all of it. The report's `path form:` line is the third trigger: for the bindings file the `path form:` line names, ask the human for the `verification` binding's *Path form* slot, as that pack's template for the key asks it, then file that file's one brief from `.claude/references/core/decision-brief.md` and dispatch `doc-writer` as for the other triggers, also where the `path form:` line is that file's only trigger; the brief carries the question asked and the human's answer, for `doc-writer` to write as the section's `- Path form:` line — replacing the line read, or added to the section where it has none — nothing else in the section rewritten. A file the `path form:` line names that has other triggers takes one brief carrying all of it. The report's `slots to revisit:` line is the fourth trigger: for each slot it names that step 4 ruled adopted or merged, the bindings file the line names takes that file's one brief from `.claude/references/core/decision-brief.md`, dispatched as for the other triggers, also where it is that file's only trigger; the brief names as the form to match the template the filling pack declares for the key in the base, and carries, per slot, the key, the slot's label, the template's current value as step 4 showed it, the project's value as read and the human's ruling — for adopt of a value carrying no `TODO`, the template's value, each placeholder the project's own line fills carried over filled, dictated under that ruling; for merge or a slot answered anew, the line the human gave or ruled — for `doc-writer` to write as that slot's `- <Label>:` line, replacing the line read, nothing else in the section rewritten. A slot ruled kept writes nothing, and a file whose every named slot is kept and that has no other trigger takes no brief. A file the `slots to revisit:` line names that has other triggers takes one brief carrying all of it. A re-invoked run, whose step 4 did not run here, first puts each named slot whose file has no brief on disk to the human by `.claude/references/core/ruling-form.md`, as step 4 does. Where a dispatch here filled or rewrote a section, or a slot line of one, that a composed file under `.claude/skills/` splices, those files read `V23` until recomposed: run `harness.py upgrade --recompose-only --root <project>`, inside an open catch-up merge with the lead's FILE forms, one command alone in its call, its Bash call given 600000 ms, the step 4 word covering a recompose within the bound; the verb plans the dry run, applies it only within the bound, compares the applied report with it and runs `validate`, `harness.py upgrade --help` stating the bound, and the table below this step reads its first line. Its `<slug>` is the one in step 6's saved file's name, `.scratch/upgrade-<slug>-report.txt`, as DRY RUN's `saved:` line or the lead's `applied:` line names it, with the bindings file's name after it, less `.md`, so a brief keeps its name across a re-invocation. A re-invoked run takes these triggers from the saved report and dispatches only a brief not yet on disk: a brief with no report is still out, and a second dispatch would race it. Its report lies beside it as `doc-writer-<slug>-report.md`, numbered `-2`, `-3`, or, where the report filer read another first line, under `.scratch/reports/` as `doc-writer-<agent id>-report.md`, holding that bindings file's path: read once, by Glob and Grep. None → stop, and put it to the human by `.claude/references/core/ruling-form.md`: the brief's path, that `doc-writer` may still be running, and the choice to read again or go on to VERIFY, whose `doctor` is the backstop, REPORT naming the brief; never a second dispatch.

   | `upgrade --recompose-only` prints | The act |
   |---|---|
   | `recomposed: <n> files; validate PASS`, then the dry run and `validate`'s report | the recompose applied: go on |
   | `outside: <n> lines; nothing written`, those lines, then the dry run | stop, and put it to the human by `.claude/references/core/ruling-form.md`, the lines outside the bound shown; where the display is cut, the human runs `harness.py upgrade --dry-run --root <project>` themselves |
   | `differs: <n> lines`, then the dry run, the lines and the applied report | stop, and put it to the human by `.claude/references/core/ruling-form.md`: the applied recompose differs from its dry run |
   | `failed: exit <code>`, then the dry run and the output | stop, show its output whole, and put it to the human by `.claude/references/core/ruling-form.md` |
   | `invalid: validate FAIL`, then the dry run and `validate`'s report | the recompose applied and matched: go on, VERIFY reporting the failure, as today's step 7 runs no `validate` |
   | exit 1, `upgrade: refused` on stderr, or any other output | stop, and put it to the human by `.claude/references/core/ruling-form.md`, the refusal shown |

8. **VERIFY** — `harness.py upgrade --verify --root <project>`, one command alone in its call, its Bash call given 600000 ms, which runs `validate`, **then** `doctor`, in that order: `doctor` checks neither V3, V4 nor V10, which an upgraded composition can break; the table below this step reads its first line.

   | `upgrade --verify` prints | The act |
   |---|---|
   | `pass: validate PASS; doctor PASS`, then both reports | REPORT, the verification a pass |
   | `fail: …`, then both reports | REPORT, the verification the failing check and its rows |
   | exit 1, `upgrade: refused` on stderr, or any other output | REPORT, the verification not run, the refusal shown |

9. **REPORT** — every outcome class the run produced, of which replaced, skipped, appended and adopted are only the common ones and a `not written: …` is never dropped, it being the class where a file was not written at all, and each orphan line by its label — `removed` (deleted, its ledger row dropped), `orphaned: locally modified` (edited, kept with its row), `dropped from the ledger` (its row dropped, the disk untouched) or `orphaned: unreadable` (not readable, kept with its row); the snapshot's id; the verification result; and, where the project is the session's own, that the session restarts to load what was written. Then what is left to the human, read by row path from the `SCRATCH` rows of step 8's `doctor`: `.scratch` not ignored → the ignore line for `.scratch/`, which this skill never writes; `.scratch` reading NOT CHECKED → that, with its reason, the human checking the ignore by their own system; the row whose message opens `an old scratch folder is present` → that folder, the human's to remove. No `SCRATCH` row → nothing added. Each `orphaned: locally modified` path is left to the human as well: to remove it, or to compose the pack that now ships it. A `legacy entries:` line in the report is left to the human as well: the project's PM triages those STATUS `## Deferred` entries and `memory/backlog-candidates.md` bullets into items with the human; this skill converts none of them. Each `status left:` line is left to the human as well, the STATUS line to correct as its reason says, and so is each `lite row left:` row, with the form its `as:` line gives where one is given, since `upgrade` writes no backlog. On a re-invoked run the applied report and the snapshot's id come from the saved file, and the report says the compare was not re-run: the dry run it compared lived only in the earlier context. Last, any outcome line owed being sent first, `harness.py upgrade --clear-saved --root <project>`, one command alone in its call, once per project, which removes the saved file; a refusal stops nothing, since the next run's `## Workflow` lead reads an old file.

   | `upgrade --clear-saved` prints | The act |
   |---|---|
   | `cleared: <file>` or `absent: <file>` | done |
   | exit 1, `upgrade: refused` on stderr, or any other output | told in one line; it stops nothing |

For `--all`, DRY RUN runs `## A cross-project round`'s hub check once per `project:` line the report prints, its result shown beside that project's report, and a project whose hub runs is never applied here, save this session's own: the project step 2's walk-up finds from this session's working directory, the workspace project in the workspace hub session, a session its hub check finds being this session — the listed session whose `sessionId` is this session's own `CLAUDE_CODE_SESSION_ID`, as `.claude/references/core/claude-code-cli.md` `## List` gives it — never a hub running elsewhere. In the workspace hub session each project takes its route as the workspace pack's role file, `.claude/references/workspace/cross-project-rounds.md` `## The round`, reads: the session applies only its own project, being its hub; another behind project whose hub runs is offered for a round request; a behind project with no hub running, or "hub not checked" (the slot named), is not reached; and a `ROUND` goes only to a project picked at HARD STOP, after the word. While lines are out, its turn ends on the stop line `Stop: declared — the wait for outcome lines while round requests are out`. In another session a project whose hub runs, save its own, is named as its hub's, a project with no hub running is applied as today, and "hub not checked" is today's pick, the slot named. Steps 5 to 8 then run once per project the human picked to apply here, serially, parents before their delta children.

**This skill does not check in.** An upgrade runs on whatever branch the project's work is on, and a check-in here would commit whatever else is uncommitted there; that work's own ceremony commits the upgrade with it. The one commit an upgrade makes is the verb's own: where the project's `trees` binding is filled and the apply rewrites STATUS lines, the verb lands that change in the hub as one commit changing only the hub's `memory/STATUS.md`, as every hub write lands, and its `upgrade: rewrote` line names it, save where the project is the hub itself, checked out on its own branch, whose rewritten STATUS file is written in place and committed with the rest of the upgrade; with `trees` absent the rewritten STATUS file is the project's own, committed with the rest of the upgrade. (`promote`, whose branch is its own, does check in.)

## A cross-project round

The workspace hub session is the hub session of the workspace project, the project whose manifest records the `workspace` preset; the base's manifest records none, so the base is never the workspace project. It sends a project's hub session one request for a round and gathers one outcome line back; the upgrade itself stays that project hub's, behind its own DRY RUN and HARD STOP.

Each line is one plain-ASCII line sent by SendMessage, kept from the `<EVENT> - <branch>; lane: <lane>; <detail>` form of `.claude/references/core/trees-contract.md` `## A report to the hub session`, the project in the branch's place and no lane field; a `ROUND` is answered only by its one outcome line, and an `UPSTREAM` only by its `FILED`, and the outcome, `RELEASE`, `FILED` and `RELAYED` lines are never answered:

- The request: `ROUND - <project>; packs: <moves>; changelog: <entries>; reply: <name>` — `<project>` and `<moves>` the sender's dry run report's `project:` line and `packs:` field, verbatim; `<entries>` the base's `CHANGELOG.md` entries named, never their text; `<name>` the sender's Hub session name.
- The outcome: `UPGRADED`, `DECLINED` or `BLOCKED`, then ` - <project>; <detail>`, `<project>` as the request wrote it.
- The base's facts: `RELEASE - <base>; packs: <versions>; changelog: <entries>`, from the base's hub session to the workspace hub session.
- The relay: `UPSTREAM - <project>; item: <slug>; source: <path>; reply: <name>`, workspace hub to base's hub — `<project>` the survey's `project:` line; `<path>` the item file's absolute path; `<name>` the sender's Hub session name.
- The filing: `FILED - <project>; item: <slug>; as: <slug>`, base's hub to `reply` — `<project>` and `item:` as the `UPSTREAM`'s; `as:` the base's `candidate` slug.
- The close: `RELAYED - <project>; item: <slug>; as: <base> <slug>`, workspace hub to that project's hub — `<project>` and `item:` as the `FILED`'s; `<base>` as `RELEASE` writes it, `<slug>` `FILED`'s `as:`.

A project hub session that receives a `ROUND` runs this skill on its own project root, never on a root the line names. DRY RUN runs as written; at HARD STOP the line is shown whole beside the report, its `packs:` field next to the report's `packs:` line, and the human's word is on the report as today: the request is never the word. It then sends the session `reply` names one outcome line: `UPGRADED` after REPORT, `<detail>` the applied report's `packs:` field; `DECLINED` at the stop where the human declines, `<detail>` that step's name and the reason given; `BLOCKED` at the step where the skill stops, `<detail>` that step's name and its reason. It never searches for the workspace hub session: the line names its sender.

The first act at receipt, before DRY RUN: the line saved whole, by the Write tool, to `.scratch/round-request.txt` under this session's project root. A further `ROUND` while the file holds one is added as its own line, an identical line not, and the run in hand goes on: each saved line gets the one outcome, at the name its `reply` gives. A re-invoked run reads the file first and holds that `ROUND`; with no file it holds none, runs as written and sends nothing, a summary's memory of a `ROUND` being no name to send to, which REPORT says. At HARD STOP a saved line is shown as a fresh one is; an old line is the human's to call, and then it is removed and nothing sent. The human's clear may take this file, the saved report or a brief mid-run: the timing is the human's (`adr-0183`), the run goes on as written, and a run that has read the line still sends its outcome to that name. Once the outcome is sent: `rm -f "<the file>"`, by its absolute path, one command alone in its call, its failure stopping nothing.

A base's hub session that receives an `UPSTREAM` runs no `## Workflow` step. It first Greps its own `memory/items/` for a `candidate`, `open` or `taken <branch>`, whose body's first line is `Source: <project> item <slug>`; found → `FILED` with its slug, nothing filed. The Grep sees only a live candidate, never one closed between rounds: an `UPSTREAM` re-sent after the base closed its candidate files again, a second one, which the base's triage closes `superseded by` the earlier one. Else it reads the `source:` file and files one `candidate` — slug the source's, another if held; `route: untriaged`; title the source's; body that line, then the source's body — then sends `FILED`. The filing: under a filled `trees`, the hub not on the session's own branch, one `hub.py write` per `.claude/references/core/gate-close.md` `## The record`, `--note` (an entry in `## The dated note`'s form naming the line received) with `--item new <file>`; else the session's own edit in `## The dated note`'s form, checked in as `## The dated note` says. An unreadable source or a BLOCKED filing sends nothing and says so to its human in one line naming the `UPSTREAM`; the item stays open at the consumer, re-sent next round. It never writes the consumer's `memory/`.

A project hub session that receives a `RELAYED` runs no `## Workflow` step and answers nothing: it closes `item:` — under a filled `trees`, the hub not on the session's own branch, one `hub.py write` per `## The record`, `--note` (an entry in `## The dated note`'s form naming the line received) with `--close-item <slug> relayed`; else the session's own edit in `## The dated note`'s form, checked in as `## The dated note` says; an item gone is closed already. The line is not saved: nothing is owed, and an open item is re-sent.

The hub check, for one project, reads that project's own bindings: its hub runs where its `session-launch` List command lists a session whose `name` is its Hub session name, or whose `cwd` equals its root in its `verification` *Path form*, compared as `.claude/references/core/trees-contract.md` `## The hub and the comparison of paths` compares — equal, never under, since every session lies under the workspace root; `cwd` and `name` as `.claude/references/core/claude-code-cli.md` `## List` gives them. Either suffices. Where neither finds a session, `session-launch` read as absent (the trees contract's `## Reading the optional keys`), a slot either half needs missing or `none`, or a failed List read, is "hub not checked", the slot named, never a stop; otherwise no hub runs.

With no workspace project, no line of this section is sent or received and `upgrade` works exactly as today, one project at a time on the human's word.
