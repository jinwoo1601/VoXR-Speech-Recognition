# upgrade

## What this is

A project composed from the base drifts behind it: packs move, files change, keys appear. `upgrade` is how a project catches up without losing what was written locally — the dry run says what would happen, the human rules on it, and a snapshot of the working tree sits under the apply.

> The verb plans, reports, and writes. The snapshot, the human's word, and the verification after are this skill's.

## Bindings

The key is read from **the project being upgraded**, not from the base, because the snapshot is taken of that project's working tree.

- `vc` (required, the project's) — the snapshot procedure SNAPSHOT follows: the record, the read that confirms it, and how the human restores it. The binding absent, or present without its *Snapshot procedure* slot → stop in the first line, name the binding interview, and run nothing. The slot still `TODO` → stop the same way: an unanswered slot is no snapshot.
- The slot answering `none` → state that no snapshot is possible and wait for the human's explicit word that the upgrade applies without one.
- `process-docs` (optional, the project's) — the bindings file answering it, whose *Brief budget* line step 7 reads, and whose *Design docs* slot the report's `design docs:` line flags for step 7's third trigger. The binding absent, or its *Brief budget* slot not filled → step 7's second trigger does not fire, and step 8's `doctor` is the backstop.
- `doc-writer` not composed in this project while the report names keys to append or carries a `design docs:` or `path form:` line, or while the *Brief budget* line needs step 7's update → say so at the stop, before the apply, so the human rules on an upgrade whose binding interview has no writer.
- `session-launch` (optional, the project's) — the List command and the Hub session name that `## A cross-project round`'s hub check reads. Absent, or a slot missing or `none` → the check reads as that section says of a missing slot; never a stop.
- `verification` (optional, the project's) — the *Path form* in which the hub check compares a session's `cwd` with the project's root. Absent, `none`, or the slot missing → the check reads as `## A cross-project round` says of a missing slot; never a stop.

## Prerequisites

Confirm before proceeding:
- The project holds `.claude/harness.json`, and its `base` points at a base that exists.
- The project's own work is committed or known: this skill does not check in, and the apply lands on whatever branch the project is on.

## Workflow

**A re-invoked run.** A compaction may re-invoke this skill between any two steps, so each run, once LOCATE has named the project, first reads step 6's saved file for it. No file, a `project:` line naming another root, or no `exit: 0` line: nothing is held, the run goes on as written and step 4 asks, any `snapshot:` and `exit:` lines it holds said beside the report there. With `exit: 0`, DRY RUN runs as written. The saved file is an old run's where the dry run's `packs:` line holds a `->`; where the dry run would write any file other than a `replaced:` file under `.claude/skills/`, beside the `manifest:` line, which counts only beside such a file; or where it would write such a file and no step 7 brief for this project, `.scratch/doc-writer-<slug>-*brief.md` with `<slug>` step 6's, lies under this session's project root. Then `rm -f "<the saved file>"`, one command alone in its call, its failure stopping nothing, and the run goes on as written. Otherwise APPLY ran, and APPLY runs only after HARD STOP's word, so nothing is asked again: steps 4, 5 and 6 do not run, and steps 7, 8 and 9 run on the file's applied report and snapshot's id.

1. **BINDINGS** — read the project's `vc` binding **and its *Snapshot procedure* slot** before anything else. Either absent → stop in the first line, name the binding interview, and run nothing. The slot `TODO` → stop. The slot `none` → state that no snapshot is possible and wait for the human's explicit word.
2. **LOCATE** — the project root: the walk-up the workspace pack's `add-pack` skill describes, an explicit root the human named, or a workspace root for `--all`. A session in this repository upgrades project zero by its root and runs `--all` over the workspace root.
3. **DRY RUN** — `harness.py upgrade --dry-run --root <project>`. The report is shown **whole**, never summarized.
4. **HARD STOP — the human's word** on the report, on the snapshot the skill will take or the statement that none is possible, on any single `--take-theirs`, on step 7's same-version recompose, where a fill there changes a section a composed skill splices, and, for `--all`, on which projects to apply here and, in the workspace hub session, which to send a round request — each project put with its route by the `--all` paragraph below — put to the human by `.claude/references/core/ruling-form.md`. Nothing is written before it. Where `doc-writer` is not composed and the report names keys to append or carries a `design docs:` or `path form:` line, it is said **here**, before the apply.
5. **SNAPSHOT** — run the *Snapshot procedure* slot's record, then its confirming read; show the snapshot's id. A failed confirm stops the skill before the apply.
6. **APPLY** — first the snapshot's id goes on disk, one Bash call: `mkdir -p "<dir>" && printf 'project: %s\nsnapshot: %s\n' "<project>" "<id>" > "<file>"`, `<dir>` this session's project root's `.scratch`, `<file>` `.scratch/upgrade-<slug>-report.txt` under that root, each by its absolute path as the Bash tool takes it, `<slug>` the project's root path lower-cased, each run of characters other than a letter or a digit one `-`, none at either end, and `<id>` the snapshot's id, or `none` where the human's word applies with none. A failed call stops the skill before the apply. Then the apply, one Bash call: `harness.py upgrade --root <project> >> "<file>" 2>&1; rc=$?; printf 'exit: %s\n' "$rc" >> "<file>"; [ "$rc" -eq 0 ]`, with at most one `--take-theirs` the human named at the stop, before the `>>`. Read `<file>` by the Read tool. A non-zero exit, or no `exit: 0` line → stop, show its lines whole, and put it to the human by `.claude/references/core/ruling-form.md`; nothing later runs. On exit 0, compare the lines between `snapshot:` and `exit:`, the applied report, with the dry run's body and **stop on a difference**: the run the human ruled on is the run that must have happened.
7. **BINDING INTERVIEW** — for each bindings file with appended keys, and for the bindings file answering `process-docs` where its filled *Brief budget* line names a pattern under `.claude/scratch`, file `.scratch/doc-writer-<slug>-brief.md` from `.claude/references/core/decision-brief.md` and dispatch `doc-writer` through the Agent tool without a `name`, as the workspace pack's `add-pack` skill does. That line's brief dictates it: its KB figure kept, the pattern's folder replaced by `.scratch`. One brief per bindings file — a file with appended keys and that line takes one brief carrying both; the dispatches run serially. The report's `design docs:` line is the third trigger: for the bindings file the `design docs:` line names, ask the human where this project's design docs live — the `process-docs` interview's design-docs question, `none` refused — then file that file's one brief from `.claude/references/core/decision-brief.md` and dispatch `doc-writer` as for the other triggers, also where the `design docs:` line is that file's only trigger; the brief carries the question asked and the human's answer, for `doc-writer` to write as the section's `- Design docs:` line, in place of the value that read `none` or added where a section answered slot by slot — one carrying the template's other slot lines — lacks the line, nothing else in the section rewritten. Any other `process-docs` section the `design docs:` line flags as lacking the line — a whole key answered `none` in any spelling (`- none`, `- None`, `- none — …`), a `none` line beside other bullets, prose with no slot lines — takes the whole `process-docs` interview in place of the design-docs question alone, `none` refused for *Design docs* only; the brief carries every question asked and every answer, and names as the form to match the template the filling pack declares for the key in the base, for `doc-writer` to rewrite the section from it — the heading, the comment line, one filled line per slot — nothing of the old section kept. A file the `design docs:` line names that also has appended keys or the old *Brief budget* line takes one brief carrying all of it. The report's `path form:` line is the fourth trigger: for the bindings file the `path form:` line names, ask the human for the `verification` binding's *Path form* slot, as that pack's template for the key asks it, then file that file's one brief from `.claude/references/core/decision-brief.md` and dispatch `doc-writer` as for the other triggers, also where the `path form:` line is that file's only trigger; the brief carries the question asked and the human's answer, for `doc-writer` to write as the section's `- Path form:` line — replacing the line read, or added to the section where it has none — nothing else in the section rewritten. A file the `path form:` line names that has other triggers takes one brief carrying all of it. Where a dispatch here filled or rewrote a section a composed file under `.claude/skills/` splices, those files read `V23` until recomposed: run `harness.py upgrade --dry-run --root <project>` again and show its report whole; where every file it would write is a `replaced:` file under `.claude/skills/`, beside the `manifest:` line, the step 4 word covers it, and `harness.py upgrade --root <project>` applies it, its body compared with this dry run's as in step 6; any other write → stop, and put it to the human by `.claude/references/core/ruling-form.md`. Its `<slug>` is step 6's with the bindings file's name after it, less `.md`, so a brief keeps its name across a re-invocation. A re-invoked run takes these triggers from the saved report and dispatches only a brief not yet on disk: a brief with no report is still out, and a second dispatch would race it. Its report lies beside it as `doc-writer-<slug>-report.md`, numbered `-2`, `-3`, or, where the report filer read another first line, under `.scratch/reports/` as `doc-writer-<agent id>-report.md`, holding that bindings file's path: read once, by Glob and Grep. None → stop, and put it to the human by `.claude/references/core/ruling-form.md`: the brief's path, that `doc-writer` may still be running, and the choice to read again or go on to VERIFY, whose `doctor` is the backstop, REPORT naming the brief; never a second dispatch.
8. **VERIFY** — `harness.py validate --root <project>`, **then** `harness.py doctor --root <project>`, in that order: `doctor` checks neither V3, V4 nor V10, which an upgraded composition can break.
9. **REPORT** — every outcome class the run produced, of which replaced, skipped, appended and adopted are only the common ones and a `not written: …` is never dropped, it being the class where a file was not written at all, and each orphan line by its label — `removed` (deleted, its ledger row dropped), `orphaned: locally modified` (edited, kept with its row), `dropped from the ledger` (its row dropped, the disk untouched) or `orphaned: unreadable` (not readable, kept with its row); the snapshot's id; the verification result; and, where the project is the session's own, that the session restarts to load what was written. Then what is left to the human, read by row path from the `SCRATCH` rows of step 8's `doctor`: `.scratch` not ignored → the ignore line for `.scratch/`, which this skill never writes; `.scratch` reading NOT CHECKED → that, with its reason, the human checking the ignore by their own system; the row whose message opens `an old scratch folder is present` → that folder, the human's to remove; `.claude/bindings` → the *Brief budget* line still under the old scratch folder, which step 7 missed. No `SCRATCH` row → nothing added. Each `orphaned: locally modified` path is left to the human as well: to remove it, or to compose the pack that now ships it. On a re-invoked run the applied report and the snapshot's id come from the saved file, and the report says the compare was not re-run: the dry run it compared lived only in the earlier context. Last, any outcome line owed being sent first, `rm -f "<the saved file>"`, one command alone in its call, once per project; its failure stops nothing, since the next run's `## Workflow` lead reads an old file.

For `--all`, DRY RUN runs `## A cross-project round`'s hub check once per `project:` line the report prints, its result shown beside that project's report, and a project whose hub runs is never applied here, save this session's own: the project step 2's walk-up finds from this session's working directory, the workspace project in the workspace hub session, a session its hub check finds being this session — the listed session whose `sessionId` is this session's own `CLAUDE_CODE_SESSION_ID`, as `.claude/references/core/claude-code-cli.md` `## List` gives it — never a hub running elsewhere. In the workspace hub session each project takes its route as the workspace pack's role file, `.claude/references/workspace/cross-project-rounds.md` `## The round`, reads: the session applies only its own project, being its hub; another behind project whose hub runs is offered for a round request; a behind project with no hub running, or "hub not checked" (the slot named), is not reached; and a `ROUND` goes only to a project picked at HARD STOP, after the word. While lines are out, its turn ends on the stop line `Stop: declared — the wait for outcome lines while round requests are out`. In another session a project whose hub runs, save its own, is named as its hub's, a project with no hub running is applied as today, and "hub not checked" is today's pick, the slot named. Steps 5 to 8 then run once per project the human picked to apply here, serially, parents before their delta children.

**This skill does not check in.** An upgrade runs on whatever branch the project's work is on, and a check-in here would commit whatever else is uncommitted there; that work's own ceremony commits the upgrade with it. (`promote`, whose branch is its own, does check in.)

## A cross-project round

The workspace hub session is the hub session of the workspace project, the project whose manifest records the `workspace` preset; the base's manifest records none, so the base is never the workspace project. It sends a project's hub session one request for a round and gathers one outcome line back; the upgrade itself stays that project hub's, behind its own DRY RUN and HARD STOP.

Each line is one plain-ASCII line sent by SendMessage, kept from the `<EVENT> - <branch>; lane: <lane>; <detail>` form of `.claude/references/core/trees-contract.md` `## A report to the hub session`, the project in the branch's place and no lane field; a `ROUND` is answered only by its one outcome line, and the outcome and `RELEASE` lines are never answered:

- The request: `ROUND - <project>; packs: <moves>; changelog: <entries>; reply: <name>` — `<project>` and `<moves>` the sender's dry run report's `project:` line and `packs:` field, verbatim; `<entries>` the base's `CHANGELOG.md` entries named, never their text; `<name>` the sender's Hub session name.
- The outcome: `UPGRADED`, `DECLINED` or `BLOCKED`, then ` - <project>; <detail>`, `<project>` as the request wrote it.
- The base's facts: `RELEASE - <base>; packs: <versions>; changelog: <entries>`, from the base's hub session to the workspace hub session.

A project hub session that receives a `ROUND` runs this skill on its own project root, never on a root the line names. DRY RUN runs as written; at HARD STOP the line is shown whole beside the report, its `packs:` field next to the report's `packs:` line, and the human's word is on the report as today: the request is never the word. It then sends the session `reply` names one outcome line: `UPGRADED` after REPORT, `<detail>` the applied report's `packs:` field; `DECLINED` at the stop where the human declines, `<detail>` that step's name and the reason given; `BLOCKED` at the step where the skill stops, `<detail>` that step's name and its reason. It never searches for the workspace hub session: the line names its sender.

The first act at receipt, before DRY RUN: the line saved whole, by the Write tool, to `.scratch/round-request.txt` under this session's project root. A further `ROUND` while the file holds one is added as its own line, an identical line not, and the run in hand goes on: each saved line gets the one outcome, at the name its `reply` gives. A re-invoked run reads the file first and holds that `ROUND`; with no file it holds none, runs as written and sends nothing, a summary's memory of a `ROUND` being no name to send to, which REPORT says. At HARD STOP a saved line is shown as a fresh one is; an old line is the human's to call, and then it is removed and nothing sent. The human's clear may take this file, the saved report or a brief mid-run: the timing is the human's (`adr-0183`), the run goes on as written, and a run that has read the line still sends its outcome to that name. Once the outcome is sent: `rm -f "<the file>"`, by its absolute path, one command alone in its call, its failure stopping nothing.

The hub check, for one project, reads that project's own bindings: its hub runs where its `session-launch` List command lists a session whose `name` is its Hub session name, or whose `cwd` equals its root in its `verification` *Path form*, compared as `.claude/references/core/trees-contract.md` `## The hub and the comparison of paths` compares — equal, never under, since every session lies under the workspace root; `cwd` and `name` as `.claude/references/core/claude-code-cli.md` `## List` gives them. Either suffices. Where neither finds a session, `session-launch` read as absent (the trees contract's `## Reading the optional keys`), a slot either half needs missing or `none`, or a failed List read, is "hub not checked", the slot named, never a stop; otherwise no hub runs.

With no workspace project, no `ROUND` is sent or received and `upgrade` works exactly as today, one project at a time on the human's word.

## Output

Report, in the PM's own voice: the project or projects upgraded, the snapshot id for each, one line per outcome class the run actually produced (commonly replaced, skipped, appended and adopted; any `not written: …` never dropped, it being the class where a file was not written at all; each orphan line by its label, `removed`, `orphaned: locally modified`, `dropped from the ledger` or `orphaned: unreadable`), the `validate` and `doctor` results, and what is left to the human — the check-in on the project's own branch, the restart where the project is the session's own, and each act step 9 read from the `SCRATCH` rows: the ignore line for `.scratch/` or the NOT CHECKED read with its reason, the old scratch folder to remove, and the *Brief budget* line still under it. Each `orphaned: locally modified` path joins what is left to the human: to remove it, or to compose the pack that now ships it.
