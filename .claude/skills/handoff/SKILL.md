# handoff

## What this is

Write a **handoff brief** that another session can start from cold, with no access to this conversation. The goal is to hand off ONE focused task — not to dump this whole session. Include only what the next session needs to do that task well, and deliberately leave everything else out.

Focus of the handoff: whatever focus the human gave when invoking this skill (arguments or the free-form ask). If none was given, infer the single most likely next task from where this session left off, and state that inference in the Objective so it can be corrected.

> One task, the minimum state, every path exact. The next session reads the file, not this conversation.

## When to hand off

A branch session hands off at a phase boundary, or, inside a phase, at the next skill-step boundary once its context passes the bound — never below the bound merely because a step ended. A hub session does not hand off at the bound: it files what only its context holds and carries on, and hands off on the human's word.

- **A phase boundary** — the start of a build-plan phase's pickup by a branch session that ran the previous phase's `implement`: there the session hands off whatever its context, the objective that phase's pickup.
- **A skill-step boundary** — in any skill, in any lane — feature, light and design — and between skills, once the context-bound hook's line has appeared (`.claude/references/core/context-bound-hook.py`, on `PostToolUse`, which reads the `session-launch` binding's *Context bound* after each tool call in the main thread), a branch session finishes the step in hand and invokes `handoff`, its objective the next step, or, after a skill's last step, the skill that follows it; the boundary it hands off at is its judgment, and a skill that must carry something across names it.
- **No line** — the *Context bound* or the *Context read* missing, `none` or `TODO`, or the hook silent → phase boundaries only; never a stop, and never a guessed figure. The *Context read* stays the human's manual read.

A branch session that reaches a handoff point invokes this skill itself, without waiting to be asked.

A hub session invokes this skill on the human's word, at any boundary, and that word is its way back where compaction fails or thrashes, or where it was opened without `--autocompact`, on idle compaction alone: the brief targets the hub or, where `trees` reads absent, the project root, and nothing launches (`references/launch.md` condition 3).

## Where it goes

Write the brief to a file — **do not** print it as a copy-pasteable block.

- Path: the slot, `.scratch/session-brief.md` under the target's root — the tree the next session opens in, per the List read, or the Hub path; the project root where `trees` is absent or it has no `memory/`. One live brief per tree, by the Write tool, after the first act and `## The dated note`'s records.
- Only the hub session writes the hub's slot. A branch session whose next session opens at the Hub path writes no slot: its word is a record by `## The dated note`'s placing call, `--note <file>`, or with it `--append memory/backlog-candidates.md <file>` where that word is a backlog candidate, and `## What you show me` names that entry.
- **Another project.** Where the next session opens in a project at another path, as under `new-project`'s HANDOFF, the target's root is that project's root, whatever this project's `trees` and `memory/` hold, no List read naming it, and this session writes the slot under it before any session starts there. `## The dated note`'s records stay this project's; the brief's Context names that root as the tree the next session opens in and that project's `memory/` as where its STATUS is read; and the hub `## Sections` item 9 compares the target with is that project's, where its `trees` reads filled, read as `## Bindings` reads its `session-launch`.
- The first act, before any draft: one Bash call, `rm -f "<slot>"`, the slot's absolute path in the `verification` binding's *Path form*; where the brief carries Reporting into this session's own root (`## Sections` item 9), `rm -f "<slot>" && printf 'session: %s\n' "$CLAUDE_CODE_SESSION_ID"`. Non-zero exit → stop, nothing drafted. A session writing no slot skips it.
- Start the file with a one-line instruction to the new session (e.g. "You're picking up: <objective>. Read the files below, then start at Next steps."), then the sections.

## The dated note

Before the brief, after the first act where one runs, write the session's dated note, `memory/<YYYY-MM-DD>.md` under the project root for today's date, created when absent. Re-read it first, since concurrent sessions share it, then append one entry at its end and edit nothing above: an H1 naming the date, the branch or task and `handoff`, then `## Summary`, `## Changes`, `## Decisions` and `## Open issues` in that order, none dropped, an empty one saying so in one line. `## Summary` names the handoff's objective and the slot's absolute path, or that no slot was written; `## Decisions` carries the rulings, fork-default takes, the human's statements and `PLAN take` lines, `## Changes` and `## Open issues` what this session changed and left open, each that no earlier entry records; the brief only points at it. The entry moves nothing out of `memory/STATUS.md`'s `## Current`, since the branch handed off is still active. Where `trees` is filled, outside the trees contract's exception for a hub session on its own branch (`.claude/references/core/trees-contract.md` `## The hub operation`), under which this skill writes as today, the note is the hub's, `memory/<YYYY-MM-DD>.md` under the Hub path, and the note and the STATUS line are drafted into one record directory in the tree this session runs in — where the step that invoked this skill names drafts an earlier step made and did not land (`g2-accept`'s CLOSE OUT, `tackle-issue`'s STATUS), the directory holding them, `.scratch/<skill>-<slug>-record/`, `<skill>` and `<slug>` that drafting step's, else `.scratch/handoff-<slug>-record/`, `<slug>` naming the objective — the note as `handoff-note.md`, the branch's STATUS line as `status-line.md`, for a launch brief the new branch's, and the commit message as `message.md`, which `handoff` redrafts where the drafting step wrote one, naming that step too, and a backlog candidate for the hub as `backlog-candidate.md`. The STATUS line is the branch's `## Current` entry as one line, opening `- **` and its key, as `tackle-issue`'s STATUS draft does, its next action the brief's next step, within the `board` binding's *STATUS line cap* where one is bound. On a feature's line it also names the path and stage, as `.claude/references/core/path-read.md` `## The STATUS line` says; a launch brief's entry does not, no path being agreed before that branch's G0. This skill's drafts are written by the Write tool, each to its file in the record directory, which the Write tool creates where absent, all issued together in one message; they cite the brief by the slot's absolute path. Then one Bash call, the placing call, places every draft: the `scripts/hub.py write --root <hub> --message <file> …` command alone, placing no brief, with `--main` as the trees contract says, `<hub>` the Hub path, run from this tree: the carried edits first, in their order, then `--entry Current <branch> <file>`, `<branch>` this session's branch and `<file>` `status-line.md`, only where the branch stays active — never where the carried edits remove the branch's `## Current` entry, as `g2-accept`'s CLOSE OUT's `--remove-entry Current <branch>` does, and never on the main branch, as on a hub session's hand-off from `close-tree` or the hub session's own — then `--note <file>`, both save for a launch brief, then the `--append` edits of `## Where it goes`; the note's re-read is the command's, inside its lock, so the records land as one commit, before the brief is written. A refusal printing a `correct:` line: correct it and re-run; any other refusal, the re-run cap spent, or a lock the command holds on its own failure: BLOCKED and stop — both by the trees contract's rule (`.claude/references/core/trees-contract.md` `## The hub operation`), and no brief is written or launched; the directory is kept, the call landed or refused, until `## The hub's clear` takes one whose call landed.

Where the project root has no `memory/` at all, say so and write no note: the brief still goes to the root's slot, `Records:` `none`.

A launch brief takes no dated note: its record is the new branch's `## Current` entry, landed first — where `trees` is filled, outside that exception, by the call above with no `--note`, its one edit `--entry Current <new branch> <file>`, `<file>` `tackle-issue`'s STATUS draft, else `status-line.md` drafted from the lane and next step the invoking step names — then the brief is written into the new tree's slot. A slot Write that fails after that entry landed → BLOCKED and stop, as above: the entry kept, no launch.

## Sections

Write the brief from `assets/session-brief-template.md`: its first line, then its sections in its order, each `<…>` placeholder replaced by this hand-off's text and each `<!-- … -->` line left out, a section, or the `Pending:` line, kept or dropped as below.

Use these; drop any that are genuinely empty rather than padding them — except Lane, which every brief carries, and Reporting, which is present exactly where the target's `session-launch` binding reads filled with its Hub session name and the brief's target is not the hub:

1. **Objective** — the one task, in a sentence or two. Concrete and verifiable.
2. **Lane** — `design`, `feature`, `light` or `lab`: the lane of the task handed off — the work's own, or else the one its branch gives, matched against the forms the `vc` binding's *Branch procedure* names (a `<…>` placeholder matches any text): its design, feature, light-lane or lab form, the lab form `lab-<topic>` where the binding names none. A light lane's value is one ASCII line, `light, class <c>`, or for a batch `light, class <c>, batch <id>, <id>...`: the class the work declared, slim where none was. The lane is `prototype` where the work is a prototype's, or its branch is in the prototype form the binding's *Branch procedure* names, `proto-<topic>` where it names none.
3. **Context** — the minimum background needed to understand *why*, plus any project or workflow state that matters (active branch, gate or stage, design decisions in play). Pull from `memory/STATUS.md`, the latest session note, and the project's process docs per the `process-docs` binding's *Design docs* and *Feature docs* slots. Where `trees` is filled, name the tree the next session opens in — the branch's own tree, by its path per the List read, or the hub — and say that `memory/` lives in the hub, at the Hub path, where the STATUS and the session note this section pulls from are read. It opens with the template's stamp, `read <date time zone>, <branch>@<sha>`, the time and the head its facts were read at, then the `Records:` line naming the dated-note entry this hand-off landed, by its path and its H1, or, for a launch brief, the new branch's `## Current` block, or `none` where the project root has no `memory/`, then, only where `## The hub's clear` names a directory, the `Pending:` line, each directory by its path and its state; a fact read at another time carries its own stamp, and the reader re-verifies a stamped fact before acting on it.
4. **Current state** — what's already done and what's in progress, so the next session doesn't redo it.
5. **Key files & locations** — exact paths (with line refs where useful) the task touches.
6. **Constraints** — locked choices, each cited by path and section, conventions, and gotchas that must be respected; things NOT to change. No rulings section: the rulings, fork-default takes, the human's statements and `PLAN take` lines are the dated note's `## Decisions`, which the `Records:` line points at.
7. **Next steps** — an ordered, concrete starting sequence. **State, not process:** if the next task is a workflow step, this section names the skill to invoke plus the state it needs — it never re-transcribes that skill's own steps.
8. **Open questions** — anything unresolved that needs the human's input, so the new session asks instead of guessing.
9. **Reporting** — only where the target's `session-launch` binding reads filled with its Hub session name, as `## Bindings` reads it, and the brief's target is not the hub — the target is the hub where `trees` reads filled and the next session opens at the Hub path, or, where `trees` reads absent, this is a hub session's own hand-off, as `references/launch.md` condition 3 reads it: the text `references/launch.md` `## Reporting` gives, written into the brief as it says. Where the target is this session's own project root, that text's STARTED clause names this session as the predecessor: the first act's `session:` line gives the id, written whole in the `<predecessor>` token's place. Otherwise the token is removed. Unset or empty → no predecessor, and `## What you show me` says so. Where `trees` reads absent and that name reads filled, condition 3's read comes before the first act, whose `printf` form depends on it: one Bash call, `printf 'session: %s\n' "$CLAUDE_CODE_SESSION_ID" && <the List command>`, the entry read as `.claude/references/core/claude-code-cli.md` `## List` gives it. A List command missing or `none`, or a refused call, told in one line and not retried in another form, reads as a failed read; a brief condition 3 calls no hand-off of its own needs no read.

Keep it tight and skimmable. Prefer precise paths and names over prose. Don't invent facts to fill a section — if something is unknown, say so.

Cite canon — skill steps, contract sections, bindings — by path and section, never restating or quoting it; the human's own words are facts, quoted verbatim.

**A launch brief for a new branch** — written when `g0-open` or `tackle-issue` invokes this skill for a branch it has just cut, naming the new tree as the target, the lane, and the skill the branch's session resumes — carries four sections, or five where Reporting applies (item 9): Objective — agree the G0 scope of the item, its line quoted, or work issue `<n>`; Lane — `design` or `feature` from `g0-open`, `light, class <c>`, or for a batch `light, class <c>, batch <id>, <id>...` from `tackle-issue`; Context — the backlog line or the issue, the new tree's path by the List read, and that `memory/` lives in the hub, at the Hub path; Next steps — invoke `g0-open`, whose branch run starts at SCOPE, or `tackle-issue` for issue `<n>`, whose resumed run goes on from DIAGNOSE; and Reporting, as item 9 says. It is written into the new tree's slot after that entry lands, before its session starts, with no dated note, and its prompt is the paste line of `## What you show me`. A prototype's launch brief, from `g0-open`, carries the Lane `prototype`.

After the brief is written, where the `session-launch` binding reads filled, as the contract reads it, this session launches the next one as `references/launch.md` says; otherwise nothing is launched, and `## What you show me` gives the paste line.

## The hub's clear

The hub session's own hand-off clears the hub's `.scratch/`: the one where `trees` reads filled, as the contract reads it, this session's project root is the Hub path, as the trees contract (`.claude/references/core/trees-contract.md`) compares them, and the brief's target is the Hub path, each read before the brief's Write. Any other hand-off clears nothing beyond its target slot and runs nothing here. Where the `verification` binding carries no *Path form*, or is a single `none`, the comparison stops this section, as that contract says: one line naming the slot, nothing read here and nothing cleared, the hand-off going on. `references/launch.md` condition 3 bars a launch here, so a clear and a launch never share a run.

After the placing call where one runs, before the brief's Write: the Grep tool, in content mode, over this root's `.scratch/` by its absolute path, glob `*.hub-write`, pattern `^(running|refused|held)$`. Each match gives a mark's path and its state; a `re-run:` line never matches. The entry directly under `.scratch/` on that path is the pending directory, named once with each state its marks gave; a match directly in `.scratch/` names no directory, the verb taking it as a file. Any such directory goes on the brief's `Pending:` line (`## Sections` item 3). A Grep that fails or is refused: one line saying so, no retry in another form, no `Pending:` line; the verb still keeps by the marks, and the comparison says what differs.

Last, only with the brief written: one command, alone in its call, run from that root: `py <script> scratch-clear --root "<project root>" --keep session-brief.md`, `<script>` and `<project root>` as `.claude/references/core/gate-close.md` `## The clear` gives them, a missing manifest and a failed or refused call as it says; the brief stands whatever the clear does. A slot Write that fails or is refused → BLOCKED and stop: the records kept, nothing cleared. A stop before the brief reaches no clear. On exit 0, the `kept:` lines are compared with the Grep's directories by the entry's name; `## What you show me` says a difference, and none adds nothing.

## What you show me
