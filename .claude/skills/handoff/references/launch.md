# handoff — the launch

How `handoff` launches the next session and what the brief's Reporting section carries, where the `session-launch` binding reads filled; "the contract" is `.claude/references/core/trees-contract.md`.

## The launch

After the brief is written into the target's slot, this session launches the next one where all four conditions below hold; where any fails, nothing is launched, and `## What you show me` gives the paste line naming the slot. The target is the tree the next session opens in, as the brief's Context names it: where `trees` is filled, the branch's own tree by its path per the List read, or the hub; where it reads absent, the project root.

Where the next session opens in a project at another path, as `handoff` `## Where it goes` says, the target is that project's root, and the hub of condition 3 is that project's, where its `trees` reads filled, read as `handoff` `## Bindings` reads its `session-launch`.

1. **A handoff point** — the human invoked this skill or asked for this handoff, or ordered the branch opened for which `g0-open` (for one item or a set) or `tackle-issue` invokes this skill, or this session reached a handoff point of `## When to hand off` and invoked this skill itself; and the human did not say they will open the session themselves. The Launch command's permission prompt is the human's check: nothing is asked before it.
2. **The slots** — this session's `session-launch` binding reads filled with its Launch command, List command and Confirm window, and the target's with its Hub session name, read as `handoff` `## Bindings` says, each as the contract reads it, and the `verification` binding carries its *Path form*; one missing or `none` is named with the paste line.
3. **Not the hub** — where `trees` is filled, the target is not the hub: a second session there would be a second writer in the hub's one tree; where `trees` reads absent, this is not a hub session's own hand-off: a session whose name, the List command's `name` on the entry whose `sessionId` is its `CLAUDE_CODE_SESSION_ID` (`.claude/references/core/claude-code-cli.md` `## List`), equals this project's Hub session name, invoked for its own next step. A launch brief for a branch `g0-open` or `tackle-issue` has just cut, or a brief whose next session opens in a project at another path, is no hand-off of its own and launches as it does today. A failed read or no such entry reads as not the hub, and BEFORE meets the same list.
4. **A plain-ASCII prompt** — the paste line's text, the file's absolute path written in, is plain ASCII.

The steps, in order: HANDOFF, its own `SendMessage`, first; then BEFORE, RUN and CONFIRM as one Bash call; then LAST ACT.

1. **HANDOFF** — only where the target is this session's own project root — its own tree, or the project root where `trees` reads absent — a hand-off launch: one line by `SendMessage` to this project's Hub session name, `HANDOFF - <branch>; lane: <lane>; brief <file name>`, `<branch>` this session's branch, `<lane>` the Lane of the brief this session has just written, and `<file name>` the slot's file name, `session-brief.md`, not its path. A launch into another tree sends nothing.
2. **BEFORE** — the call opens by removing PATH's duplicates, first occurrence kept, in that call's shell, since a launched session inherits this shell's PATH and each session's shell adds to it, so without the removal PATH grows each generation until `cmd.exe`, finding nothing past 8191 characters, fails the List command and stops the launch. BEFORE is the next command, `py scripts/hub.py sessions-at "<tree>" > "<record>\before.txt"`, with `--vacant` added before the `>` where the target is not this session's project root: the List command read once, and the sessions at the target printed, each line ending in its full id, into `<record>\before.txt` by the shell's redirect. A session is at the target when its working directory, as the list shows it, is the target's path or lies under it, compared as the trees contract (`.claude/references/core/trees-contract.md`) compares paths. Where the target is not this session's project root and a session is at it → no launch: one line saying that tree has a session running, then the paste line.
3. **RUN** — chained to BEFORE by `&&` and grouped with CONFIRM in one `{ …; }`, so `--vacant`'s exit 3 skips both: the Launch command as bound, its `<tree>` the target's path in the `verification` binding's *Path form*, its `<branch>` the branch the next session works on, and its `<prompt>` the paste line's text; then `; rc=$?` keeps its exit status, and `; cd "<root>"` returns the shell to this session's project root whatever that status, since the Bash tool keeps its working directory between calls; then `&& [ "$rc" -eq 0 ]`, so a Launch command that errored ends the call there, CONFIRM not run, and the call exits non-zero with no `hub.py sessions-at:` line.
4. **CONFIRM** — inside RUN's group, chained to that status test by `&&`: `py scripts/hub.py sessions-at "<tree>" --since "<record>\before.txt" --wait <seconds>`, `<seconds>` the `session-launch` binding's *Confirm window* in seconds, which re-reads the List command until a session at the target appears whose full id ends no line of the file BEFORE wrote. It appears → one line: the branch launched, and its tree. The Launch command errored, or the window passed, each told by the call's exit and output below → one line naming which and telling the human to check the session list before opening a session there, then, on a hand-off launch, one line by `SendMessage` to the same hub session, `BLOCKED - <branch>; lane: <lane>; launch failed`, `<branch>` and `<lane>` as HANDOFF's; then the paste line; the tree is kept.
5. **LAST ACT** — where the target is this session's project root — its own tree, or the project root where `trees` reads absent: the launch, confirmed or not, ends this session's work, and it takes no further step, so one writer per tree holds. It sends nothing and stays listed until the hub session stops it, when the successor's `STARTED` names it, as `close-tree` `## A handed-off session` says, or the human closes it, or the tree's close stops every session there.

The one call, whole, `<record>` the record directory `handoff` `## The dated note` names, which the drafts' Writes made where `trees` is filled — where `trees` is absent, `.scratch/handoff-<slug>-record/` under the project root, `<slug>` as `handoff` `## The dated note` names it, which no draft made, so the call opens with `mkdir -p "<record>" &&` there, the redirect making no directory, the `mkdir` first and the PATH removal after it, so the `mkdir` runs as written and the shown call follows it — and `<root>` this session's project root, every path in the *Path form*:

```
PATH="$(printf '%s:' "$PATH" | awk -v RS=: '!s[$0]++{printf "%s%s",(n++?":":""),$0}')" && py scripts/hub.py sessions-at "<tree>" [--vacant] > "<record>\before.txt" && { <the Launch command>; rc=$?; cd "<root>" && [ "$rc" -eq 0 ] && py scripts/hub.py sessions-at "<tree>" --since "<record>\before.txt" --wait <seconds>; }
```

Its exit and output are read so:

- Exit 3 — BEFORE wrote a session at the target into `<record>\before.txt` under `--vacant`, so neither RUN nor CONFIRM ran → step 2's no-launch line and the paste line. Only BEFORE exits 3: a Launch command's own exit, 3 or any other, ends the group at its status test, which exits 1.
- A non-zero exit with the line `hub.py sessions-at: no new session at <tree> within <n>s` — `--wait` passed the window → step 4's failure line naming the window, then, on a hand-off launch, its `BLOCKED` message, then the paste line; the tree is kept.
- Any other non-zero exit, with no such line — the PATH removal failed, as where `awk` is absent, so nothing after it ran, or the Launch command errored, CONFIRM not run, or, where a `hub.py sessions-at:` line names a List read that failed, BEFORE or CONFIRM could not read the list → step 4's failure line naming the PATH removal, the launch error, or that read, then, on a hand-off launch, its `BLOCKED` message, then the paste line; the tree is kept.
- Exit 0 — `--wait` printed the new session's line → step 4's one line.

So, where `trees` is filled, a hand-off into its own tree takes the first act, the drafts' Writes, the placing call, the brief's Write, HANDOFF and the launch call, plus `BLOCKED` on a failure; into another tree, less HANDOFF; the hub session's own, the first act, the drafts' Writes, the placing call, the Grep, the brief's Write and the clear's call, plus `BLOCKED` on a failure, as `handoff` `## The hub's clear` says. Where `trees` is absent: condition 3's read, the first act, the note's re-read and append, the brief's Write, HANDOFF and the launch call; a hub session's own, the same less HANDOFF and the launch call, and nothing is cleared.

## Reporting

The text below, written into the brief in plain ASCII, with `<hub session name>` the target's Hub session name, `<branch>` and `<lane>` the next session's branch and the brief's Lane, written out, and `<predecessor>`, on a hand-off into this session's own root, replaced by a space and `followed by "; predecessor <session id>"`, `<session id>` the id the first act's `session:` line gives, whole, or removed where it gives none; otherwise it is removed as the brief is written; `<EVENT>`, `<detail>` and `<commit>` stay as they stand.

```
Report to the hub session `<hub session name>` by SendMessage, one plain-ASCII line per event, in the form `<EVENT> - <branch>; lane: <lane>; <detail>`. STARTED: your first act, before anything else; detail the skill named in Next steps<predecessor>. BLOCKED: whenever you stop on something only the human or the hub session can clear; detail what blocks you. A refused call, yours or an agent's: report BLOCKED and put your own stop as `.claude/references/core/trees-contract.md` `## A refused act` says; never retry it in another form. FINISHED: at once when the human declines this item at its G0 scope, detail `declined at G0, nothing written`; otherwise after the merge and close-out, detail `merged <commit>`, with what `.claude/references/core/gate-close.md` `### REMOVE` adds - g1-lock, g2-accept and `g2-lite` send it at their REMOVE step, and where your closing skill has none, send it yourself after the close-out. The hub session never replies and never gives you work: do not wait for an answer.
```
