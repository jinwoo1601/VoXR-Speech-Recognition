# handoff — the launch

How `handoff` launches the next session and what the brief's Reporting section carries, where the `session-launch` binding reads filled; "the contract" is `.claude/references/core/trees-contract.md`.

## The launch

After the brief is written into the target's slot, this session launches the next one where all four conditions below hold; where any fails, nothing is launched, and `## What you show me` gives the paste line naming the slot. The target is the tree the next session opens in, as the brief's Context names it: where `trees` is filled, the branch's own tree by its path per the List read, or the hub; where it reads absent, the project root. A staged slot (`handoff` `## Where it goes`, *A staged slot*) launches nothing, whatever the four conditions read. Where `trees` reads absent, a branch session's hand-off made after its branch merged into the main branch — `g2-accept`'s HANDOFF — launches nothing either, whatever the four conditions read: its next session opens on the main branch, the hub's, as the hub is the target where `trees` is filled (condition 3).

1. **A handoff point** — the human invoked this skill or asked for this handoff, or ordered the branch opened for which `g0-open` (for one item or a set) or `tackle-issue` invokes this skill, or this session reached a handoff point of `## When to hand off` and invoked this skill itself; and the human did not say they will open the session themselves. The launch verb's checks are the check, and core's allow rule on it asks nothing: nothing is asked before it.
2. **The slots** — this session's `session-launch` binding reads filled with its Launch command, List command and Confirm window, and the target's with its Hub session name, read as `handoff` `## Bindings` says, each as the contract reads it, and the `verification` binding carries its *Path form*; one missing or `none` is named with the paste line.
3. **Not the hub** — where `trees` is filled, the target is not the hub: a second session there would be a second writer in the hub's one tree; where `trees` reads absent, this is not a hub session's own hand-off: a session whose name, the List command's `name` on the entry whose `sessionId` is its `CLAUDE_CODE_SESSION_ID` (`.claude/references/core/claude-code-cli.md` `## List`), equals this project's Hub session name, invoked for its own next step. A launch brief for a branch `g0-open` or `tackle-issue` has just cut is no hand-off of its own and launches as it does today. A failed read or no such entry reads as not the hub, and LAUNCH's `vacant` check meets the same list.
4. **A plain-ASCII prompt** — the paste line's text, the file's absolute path written in, is plain ASCII.

A launch whose target is this session's own project root — its own tree, or the project root where `trees` reads absent — is a hand-off launch. The steps, in order: LAUNCH, one Bash call; then LAST ACT.

1. **LAUNCH** — one command, alone in its call, run from this session's project root: `py <script> launch "<tree>"`, `<script>` as `.claude/references/core/gate-close.md` `## The clear` gives it, `<tree>` the target's path in the `verification` binding's *Path form*, nothing else passed. The verb checks `read`, `tree`, `brief`, `vacant` and `launch` in that order, acting on none failed, starts a background session in the target by its fixed command (`.claude/references/core/claude-code-cli.md` `## Launch`), with the `trees` binding's paths as `--add-dir` where filled, the branch as `--remote-control` and `-n`, `--permission-mode auto`, the paste line as its prompt, PATH's duplicates dropped and the transcript kept, then re-reads the List command within the `session-launch` binding's *Confirm window* for a session at the target not listed before.
2. **LAST ACT** — where the target is this session's project root — its own tree, or the project root where `trees` reads absent: the launch, confirmed or not, ends this session's work, and it takes no further step, so one writer per tree holds. It sends nothing and stays listed until its successor stops it at its start, as the brief's start step (`## Reporting`) says, or the hub session stops it on a bare `STARTED`, from a brief with no start step, as `close-tree` `## A handed-off session` says, or the human closes it, or the tree's close stops every session there.

LAUNCH's exit and output are read so:

- Exit 0, `launch: launched <id> <name> at <tree>` → one line: the branch launched, and its tree.
- `hub.py launch: vacant: …` → no launch: one line saying that tree has a session running, then the paste line.
- `hub.py launch: confirm: …` → one line saying no new session was seen within the window and telling the human to check the session list before opening a session there.
- Any other exit or refusal line → one line relaying the `hub.py launch:` line and the lines after it, Claude Code's own among them (`Workspace not trusted …` for a repository's main checkout never opened by `claude`, or a linked worktree of it, under trusted ancestors, and for a folder in no repository with no trusted ancestor, `.claude/references/core/claude-code-cli.md` `## Launch`), and telling the human to check the session list.
- Every non-zero exit but `vacant`'s → that line, then, on a hand-off launch, one line by `SendMessage` to the same hub session, `BLOCKED - <branch>; lane: <lane>; launch failed`, `<branch>` this session's branch and `<lane>` the Lane of the brief this session has just written; then the paste line; the tree is kept.

So, where `trees` is filled, a hand-off into its own tree takes the first act, the drafts' Writes, the placing call, the `where` call, the brief's Write and the launch call, plus `BLOCKED` on a failure; into another tree, the same less `BLOCKED`; the hub session's own, the first act, the drafts' Writes, the placing call, the `where` call, the clear's call and the brief's Write, plus `BLOCKED` on a failure, as `handoff` `## The hub's clear` says. Where `trees` is absent: condition 3's read, the first act, the note's re-read and append, the brief's Write and the launch call; a hub session's own, or a branch session's after its merge, the same less the launch call, and nothing is cleared.

## Reporting

The first text below, the Report text, is written into the brief in plain ASCII, with `<hub session name>` the target's Hub session name and `<branch>` and `<lane>` the next session's branch and the brief's Lane, written out; `<EVENT>`, `<detail>` and `<commit>` stay as they stand. On a hand-off into this session's own root where the first act's `session:` line gives an id, the Report text's `<predecessor>` token is replaced by a space and the second text below, the start step, with `<session id>` that id, whole, `<tree>` the target's path as LAUNCH writes it, in the `verification` binding's *Path form*, or as the Bash tool takes it where the binding carries none, and `<script>` as `.claude/references/core/gate-close.md` `## The clear` gives it, read in this session's project root; its `<id>` and `<the verb's case or refusal line>` stay as they stand, for the next session. Where no manifest gives `<script>`, `<predecessor>` is instead replaced by ` STARTED: your first act, before anything else; detail the skill named in Next steps followed by "; predecessor <session id>".`, with its leading space, `<session id>` that id, and no start step is written. Otherwise `<predecessor>` is removed as the brief is written, and no start step is written: a session started fresh sends nothing at its start.

```
Report to the hub session `<hub session name>` by SendMessage, one plain-ASCII line per event, in the form `<EVENT> - <branch>; lane: <lane>; <detail>`.<predecessor> BLOCKED: whenever you stop on something only the human or the hub session can clear; detail what blocks you. FINISHED: at once when the human declines this item at its G0 scope, detail `declined at G0, nothing written`, or rules that it wait, detail `waits at G0, nothing written`; at once when the human halts this branch, after the halt's write and as your last act, its detail as `.claude/references/core/halt.md` `## The branch's halt` gives it; otherwise after the merge and close-out, detail `merged <commit>`, with what `.claude/references/core/gate-close.md` `### REMOVE` adds - g1-lock, g2-accept and `g2-lite` send it at their REMOVE step, and where your closing skill has none, send it yourself after the close-out. The hub session never replies and never gives you work: do not wait for an answer.
```

```
Your first act, before anything else: run `py <script> predecessor "<tree>" <session id> --stop`, alone in its call, its Bash call given the same `timeout`, 600000 ms, as the stop call below, since it runs that stop itself and may wait as long. Where it prints a line opening `suffix: `, whatever its exit: where the rest of that line after `suffix: ` is `; predecessor <session id> stopped`, send nothing; otherwise report BLOCKED, detail that rest without its leading `; `, as printed. Where it prints `manual: Path form` instead, it read and stopped nothing, and the case is decided by that Path form, as `.claude/references/core/trees-contract.md` `## The hub and the comparison of paths` says: run `py <script> predecessor "<tree>" <session id>` and, only where it prints `stop <id>`, `py <script> stop <id>`, its Bash call given a `timeout` of 600000 ms, each alone in its call; then send nothing where the stop exited 0 or the read printed `gone`, else report BLOCKED, detail `predecessor <session id> not stopped - <the verb's case or refusal line>`: the case the read printed, or the first error line of either call's non-zero exit, with its `next:` line where it prints one, as printed, any character outside ASCII written as `?`. Either way, go on with Next steps: a BLOCKED for a predecessor not stopped tells the human, and does not stop this session. Output with neither line, from a usage error or a crash, is read as a refused call. Either call refused by permission or policy: report BLOCKED naming it, never retry it in another form, leave the predecessor, and stop.
```
