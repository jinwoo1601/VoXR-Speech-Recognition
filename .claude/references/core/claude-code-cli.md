# Claude Code CLI — session commands

The behaviour of the Claude Code CLI that the `session-launch` binding's commands rely on — the same for every project; the binding holds only the commands and the project's own facts.

## Launch

- `claude --bg "<prompt>"` starts a session in the background, with no window, in the current working directory, `<prompt>` its first message.
- `--background` is the same flag as `--bg`: `claude --help` lists them together as `--bg, --background` (Claude Code 2.1.296).
- A background session meets Claude Code's background-session guard: Edit, Write and NotebookEdit on a file inside the session's current working directory are refused ("This background session hasn't isolated its changes yet. Call EnterWorktree first …") where that directory is a repository's main checkout rather than a linked worktree, or lies outside any repository while the settings register a `WorktreeCreate` hook. The vc packs' settings templates register none while writer trees are parked, so a background session outside any repository, whatever the vc pack, meets no such refusal while the hook is parked: that edit refusal is lost until a template registers the hook again. Bash is not gated. An edit is not refused where the current directory or the file is inside a linked worktree, or the file is outside the current directory, so a session launched into its own tree that does not `cd` out of it meets no refusal.
- The guard's opt-outs are the setting `worktree.bgIsolation: "none"` and the environment variable `CLAUDE_BG_ISOLATION=none`. The harness keeps the guard on and sets neither in its tracked settings. As observed on Claude Code 2.1.295.
- `--remote-control <name>` makes the session reachable remotely, from the phone; it must be given its name, or it takes the next argument — the prompt — as one.
- `-n <name>` names the session: the name it carries in the session list, and its messaging address.
- `--permission-mode <mode>` sets the permission mode the session runs in.
- `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1` in the session's environment keeps its transcript.
- A background launch prints `backgrounded · <id> · <name>`.
- An interactive session opened with `claude --remote-control <name> -n <name>` is reachable and addressed under `<name>` the same way.
- `--add-dir <dir>...` adds working directories and is variadic: `--add-dir <hub> <location> --remote-control <name> -n <name> --permission-mode auto "<prompt>"` started the session with the prompt as its first message; under the block, writes into the added directories passed and one outside them was refused, ending `the permissions.blockWritesOutsideWorkingDirectories setting blocks writes outside the working directories. Ask the user to add the directory with /add-dir, or to remove that setting.` As observed on Claude Code 2.1.318, 2026-11-05.
- A bare revive (`## List`) wakes the session with its saved options, printing `note: woke session <id> with its saved options (--add-dir, --remote-control, -n, --permission-mode, --model).`, and writes into its added directories passed after it. As observed on Claude Code 2.1.318, 2026-11-05.
- `claude --bg` in a folder with no trust entry of its own in the user's `.claude.json`, under ancestor directories whose entries hold `hasTrustDialogAccepted: true`, as observed on Claude Code 2.1.325, 2026-11-16: a repository's main checkout never opened by `claude`, and a linked worktree of it, each refused before launch, exit 1: `Workspace not trusted. Run claude in <dir> once and accept the trust prompt, then retry.`, and no entry was written; a folder that is no repository's root, inside a trusted repository's work tree, launched, and no entry was written; a folder in no repository, a workspace of another version-control system, launched, and Claude Code wrote its entry with `hasTrustDialogAccepted: false`; such a folder with no trusted ancestor was refused with the same `Workspace not trusted` line.
- On Claude Code 2.1.318, 2026-11-05, a worktree of a repository never opened interactively was refused the same way under a trusted ancestor, and linked worktrees of a trusted main checkout launched with no entry of their own, not probed singly.
- Windows PowerShell 5.1 rejects `&&` (`The token '&&' is not a valid statement separator in this version.`) and cmd rejects a single-quoted `cd`, so `scripts/hub.py launch`'s `trust` refusal prints its launch twice: once for a POSIX shell, `cd '<tree>' && ...`, and once labelled `command (PowerShell):`, `Set-Location -LiteralPath '<tree>' -ErrorAction Stop; $env:CLAUDE_CODE_FORCE_SESSION_PERSISTENCE='1'; claude ...`. As observed by the human, 2026-11-16.

## List

- `claude agents --json` prints one object per running session on the machine, interactive and background alike, and one per background session listed with no `pid`, as below; each object has its `cwd`. A background session's object carries an `id`; an interactive session's carries none, and it is not stopped from the command line.
- Each object also carries `name`, the `-n` name the session was launched or opened under. An object with a `pid` also carries `status`: `idle` for a session waiting on nothing, otherwise another value, such as `busy` or `waiting`. A background session's object also carries `state`, which is not always the `state` in its `.claude/jobs/<id>/state.json`; as observed on Claude Code 2.1.314.
- A background object with no `pid` carries no `status`, and its `state` does not show a turn running. As observed on Claude Code 2.1.314, 2026-10-31: `2a0f3754`, listed `working`, had no file under `.claude/sessions/`, where each object with a `pid` has one; no process on the machine carried its id on its command line, where a running background session's id is on two, its `--bg-pty-host` and the session itself; and its `.claude/jobs/2a0f3754/state.json`, `timeline.jsonl` and transcript were last written on 2026-10-25, the file and the timeline reading `done`, the file holding an `inFlight` `session_cron`, a `ScheduleWakeup` the session ended before, and its `createdAt` the listed `startedAt`. `claude stop` of it printed `stopped`, exit 0, and it stayed listed; as observed on 2026-10-26, its Claude Code version not recorded. `65d226e6`, its job `blocked`, listed the same way on 2026-10-28, its Claude Code version not recorded. What rule keeps such an object listed and sets its `state` is not observed.
- An interactive `claude --resume <full id>` given the flags of the `session-launch` binding's Hub session name command — `claude --resume <id> --add-dir "<dir>" --remote-control <name> -n <name> --autocompact 250k`, with one `--add-dir` directory — reopened the session itself, not a copy, for a session opened as `claude -n <name>` and exited by `/exit`: it answered from its earlier turns; `/remote-control is active` showed; `/context` printed `Auto-compact window: 250k tokens`; `claude agents --json` listed it `"kind": "interactive"`, `"name": "<name>"`, with the same `sessionId`; and its one transcript, `<sessionId>.jsonl`, carried both runs' turns. As observed by the human in PowerShell on 2026-11-16, its Claude Code version not recorded.
- Every object carries `sessionId`, the session's full id, the value its own `CLAUDE_CODE_SESSION_ID` holds, a background session's `id` its first 8 characters, and `startedAt`, the session's start in integer milliseconds since the epoch; both as observed on Claude Code 2.1.288, not in the CLI's own documentation.
- After `claude respawn <id>` of an idle background session, its object keeps `sessionId` and `id`, carries a new `pid` and a `startedAt` reset to the respawn time, and its transcript keeps its first timestamp; as observed on Claude Code 2.1.311. A respawn mid first turn, observed once, kept the `id` but changed the `sessionId`, and no transcript file existed for the new `sessionId`; as observed on 2026-10-22, its Claude Code version not recorded.
- A bare `claude --bg --resume <full id>`, run from the session's `cwd`, revives a background session whose process is gone, and its object then reads as after an idle session's respawn: `sessionId` and `id` kept, a new `pid`, `startedAt` reset to the revive time, its transcript's first timestamp kept. As observed on Claude Code 2.1.308, with the process killed; on 2.1.312, for `8f1fc67c`, launched on 2.1.311 and revived after a night, about 8.5 h later; and without the transcript read, on 2.1.314, for `65d226e6`, listed with no `pid` beforehand, its `state` `blocked` kept. Before its revive, a session whose job reads `done` with nothing in flight was not listed (`8f1fc67c`); a session with no `pid` can be listed, as above.
- `claude --bg --resume <full id>` run with any flag besides `--bg` and `--resume` starts a new session with an id of its own and leaves the dormant session unrevived — a copy; a revive is the bare form above, nothing added. As observed on 2026-10-22 (`feat-automode-command` 140678ab, copy e27f6677), its Claude Code version not recorded.
- A session's transcript is one file per full session id, `.claude/projects/<directory>/<sessionId>.jsonl` under the user's home directory, one directory level under `projects`, and the `.jsonl` files under `<directory>/<sessionId>/subagents/` are named by no session id; its leading entries can carry no top-level `timestamp`, and its first timestamped entry is not always its earliest. The `session-launch` binding's Context read and the trees contract's `predecessor` verb rely on this layout; as observed on Claude Code 2.1.311, not in the CLI's own documentation.

## Stop

- `claude stop <id>` ends one background session, by the `id` the list shows — never by its `-n` name. Its conversation is kept and can be resumed.
