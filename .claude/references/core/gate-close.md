# Gate close

The close steps the three gate skills share word for word — `g1-lock`, `g2-accept` and `g2-lite` — each loaded where the calling skill names it: the session's dated note, the record as one hub operation, and the tree-path steps. Each skill's CLEAR loads `## The clear` as well, and its KEPT BRIEF `## The kept brief`. In these blocks, `## Workflow` and "the items below" are the calling skill's, and "the contract" is `.claude/references/core/trees-contract.md`. `review-cycle`'s lead runs `### CATCH-UP` as well.

## The dated note

`memory/<YYYY-MM-DD>.md` for today's date, created when absent: re-read it, since concurrent sessions share it, then append one entry at its end and edit nothing above — an H1 naming the date, the branch and this step, then `## Summary`, `## Changes`, `## Decisions` and `## Open issues` in that order, none dropped, an empty one saying so in one line. The closed branch's block moves out of `memory/STATUS.md`'s `## Current` into the entry's `## Changes`, whole and verbatim, opened by one line naming where it came from and this step; gate evidence — commit shas, test counts, exit codes, live-run transcripts — and authorship or provenance confessions go under `## Changes`, and the gate ruling and review-cycle records — angle counts, findings, verdicts, rulings — under `## Decisions`; deferred items and named limitations go to STATUS `## Deferred`, one line each in the entry form, `**<ID>** · <VERDICT> · <route> · v<date> — <title>`, their full text under the entry's `## Open issues`; a deferral the work closes leaves `## Deferred` for the entry's `## Changes`, marked CLOSED and naming this step; backlog candidates go to `memory/backlog-candidates.md`, lessons for future features to `memory/notes-for-future-features.md`, each file appended to and created where absent. Where no branch stays active, `## Current` keeps one headline for the main branch naming the next action. A project root with no `memory/` at all: say so and write no note, inventing no other location.

## The record

Under a filled `trees`, outside the trees contract's exception for a hub session on its own branch (`.claude/references/core/trees-contract.md` `## The hub operation`), the record `## The dated note` describes is one hub operation, made after the merge, once the lock is released: its inputs are drafted into one directory in the tree this session runs in, `.scratch/<skill>-<slug>-record/`, `<skill>` the calling skill's name and `<slug>` the topic, feature, changeset or issue it names — `message.md` the commit message, and one file per entry, note and append — then carried by one `scripts/hub.py write --root <hub> --message <file> …` command, with `--main` as the trees contract says, run from that tree.

Its edits, in this order, are `## The dated note`'s moves: `--remove-entry Current <branch>` for the closed branch's block; where the record changes the main branch's headline, `--entry Current <key> <file>`, `<key>` read from the hub's STATUS as the trees contract says, or, where there is none, the same way from the drafted headline line, and single-quoted for the shell, a headline not opening `- **` stopping before the call, saying so; `--entry Deferred <ID> <file>` per new deferral, its ID read from the hub's STATUS right before drafting; `--remove-entry Deferred <ID>` per deferral the work closes; `--remove-entry Auto-closed <key>` per line the gate's packet showed (`.claude/references/core/gate-packet.md` `## The packet`); where the calling skill closed by class, `--entry Auto-closed <branch> <file>`, its LIST line rewritten as it says; `--note <file>`, the entry, whose `## Changes` holds the moved block verbatim, copied from the hub's `memory/STATUS.md` read by absolute path, and each closed deferral's text; and, where the gate has any, `--append memory/backlog-candidates.md <file>` for its backlog candidates and `--append memory/notes-for-future-features.md <file>` for its lessons. Each `--entry` file holds the one entry line, opening `- **` and its key. The note's re-read and every append are the command's, inside its lock.

Where the calling skill's next step invokes `handoff`, the drafts are named to it and its call carries them; otherwise the call is this step's. A refusal printing a `correct:` line: correct it and re-run; any other refusal, the re-run cap spent, or a lock the command holds on its own failure: BLOCKED and stop — both by the trees contract's rule (`.claude/references/core/trees-contract.md` `## The hub operation`). The directory is kept, the call landed or refused, and REMOVE runs only once the call has landed.

## The clear

A gate's CLEAR empties the project root's `.scratch/` by one command, alone in its call, run from that root: `py <script> scratch-clear --root "<project root>"`. `<project root>` is that root's absolute path as the Bash tool takes it; `<script>` is the base's `scripts/hub.py`, the base being the `base` path in `.claude/harness.json`, relative to the project root, the two joined and normalised, so a base of `.` gives `scripts/hub.py`, as a `./` form matches no allow rule. With no manifest the clear could not run: say so and go on. A gate's clear names no `--keep`; a `kept:` line names a directory whose hub write has not landed, which stays, and is relayed. A non-zero exit or a refused call: one line saying so, no retry in another form; what ran before it stands, what follows still runs, and the next clear takes what is left.

## The kept brief

A gate's KEPT BRIEF deletes a brief the closed branch's block cited, only while one remains, after the record has landed and before REMOVE. `<hub>` is the Hub path, or the project root where `trees` reads absent, as the contract reads it.

The command refuses a `memory/` that is not clean, so the record is checked in first: a hub operation's call has done so; otherwise any of the close's `memory/` edits still pending is checked in by the `vc` binding's check-in procedure before this step reads anything.

The names come from one place, the close's note entry: in `<hub>`'s `memory/<YYYY-MM-DD>.md`, by absolute path, `<YYYY-MM-DD>` the date the record took, the last entry whose H1 names this branch and whose `## Changes` holds the moved block, opened by its line from `## The dated note`; other sessions' entries and a later entry of this branch's hold no such block. No such entry, or a block holding no `memory/handoffs/`, either separator, any case: no command, so no prompt, and the step is done.

Otherwise the names come from a listing narrowed by the block's own text, since the Glob tool shows only part of a large folder: for each occurrence of `memory/handoffs/` in the block, each `\` read as `/`, any case, a Glob of the files directly under `<hub>`'s `memory/handoffs/`, its pattern the text following the occurrence, cut before the first `/`, space, quote, backtick, `.` or Glob metacharacter, then `*`; an occurrence with nothing left before its cut, as the folder alone, takes no Glob and cites nothing. A listed `<name>`, directly under the folder, is cited where `memory/handoffs/<name>` occurs in the block, each `\` read as `/`, any case, not followed by a word character, a `-`, or a `.` then a word character: so `memory/handoffs/x.md.` closing a sentence and an absolute path ending there cite `x.md`, `memory/handoffs/x.md.bak` does not, and a bare name cites nothing. A result still saying it shows only part of its matches can be trusted for nothing: one line names that occurrence, and its brief stays, uncited, for a later bare run. A citation in another letter case than the file's, before its cut, is a miss where the listing does not fold case, as it need not even where the file system does: one stale file, as over-keeping costs. None listed and cited: no command, so no prompt.

A cited path below the folder, as `memory/handoffs/sub/x.md`, and a name holding `:`, `"`, `$` or a backtick are never passed: the command takes only a plain name, so it refuses the path and the `:` with a `correct:` line that could not be met, and a shell reads `"`, `$` and a backtick inside the double quotes of the call and of the `!` line. One line names each, and it stays, uncited, for a later bare run, over-keeping costing one stale file.

Otherwise one command, alone in its call, from this session's project root: `py <script> sweep-handoffs --root "<hub>" --only "<name>"`, one `--only` per name as the listing spells it, with `--main <main branch>` after `--root`, where the project's main branch is not the script's default, as the contract says of `write`, `trees` absent included. `<script>` is `## The clear`'s, never another spelling of the script, since only that spelling meets the project's ask rule. The bare form is never this step's: on a project not yet swept it takes the whole pile.

With no manifest there is no `<script>`, so no call and no command for the human: one line saying so, and the brief stays, uncited, for a later bare run. Otherwise two reads decide: the manifest's `base`, from `.claude/harness.json`, and `### ROOT`'s comparison of this session's project root with the Hub path, read as equal where `trees` reads absent. The call is made where `<script>` holds no space and the base is `.`, or absolute, or relative with the two equal. Otherwise no call is made, since a relative base names no sure file from a branch tree and a quoted `<script>` holding a space meets no rule, and the step puts the stop below.

On exit 0 each printed line is relayed and the step is done, no retry: the commit's summary; `kept: <path>`, another block or the headline still citing it, so it waits for that close or a later bare run; `not listed: <path>`, gone since the listing; `nothing to do`.

The session's call meets a permission prompt on every run, in every mode, and the step waits there, a session running unattended included: its process has not started, no lock is held, merge and record stand, and only REMOVE, where it stands, waits, running only once this step has its outcome.

Under a filled `trees`, a denied prompt is the contract's `## A refused act`: `BLOCKED`, the stop, the same command as the `!` line; `Hold` leaves the brief, uncited, for a later bare run, and the tree unremoved. A refusal by the command is the contract's for a `write` (`## The hub operation`), its `re-run:`, `stray:` or `clear:` line carried, and REMOVE does not run.

With `trees` absent, where the contract does not run, a denied prompt or a refusal is one line saying so, with the command's `re-run:` or `clear:` line, no retry in another form; the record stands, what follows still runs, and the brief stays, uncited, for a later bare run.

The stop's command is one line, for the human to run with `!` in the hub terminal, from the hub's working directory: `py "<absolute script>" sweep-handoffs --root "<hub>" --only "<name>"`, one `--only` per name as the listing spells it, with `--main` as above. `<absolute script>` is `<hub>` and a relative base joined with `scripts/hub.py` and normalised, or an absolute base and `scripts/hub.py` as they stand. In this line it and `<hub>` are written with each `\` as `/` and the drive kept, the `verification` binding's *Path form* compared with either separator and never a shell's own form of the drive, so a POSIX shell and PowerShell read the line alike and its effect depends on no working directory. A `<hub>` or base holding `"`, `$` or a backtick has no faithful form: the stop says the act has no command and offers `Done another way`.

That stop is the contract's `## A refused act`'s, taken where no call was refused: one AskUserQuestion naming the act, its target, why no call was made in the words of the two reads, and the command, or that the act has none; its options are `Hold` and, with a command, `Ran it in the hub`, without one, `Done another way`. On `Hold`, or an answer typed in Other, the turn ends `Stop: BLOCKED`, the brief uncited and the tree unremoved: a typed answer never clears the act for a call.

Under a filled `trees`, before that stop, the report to the hub session is one line, with no `refused:`, since nothing was refused and that word would have the hub session log a refusal: `BLOCKED - <branch>; lane: <lane>; kept brief: no call made, the command is at this session's stop`, `<lane>` the lane the calling skill names.

On `Ran it in the hub` or `Done another way` this session reads the effect by absolute path, since the run prints in a terminal it does not see and a printed `kept:` leaves the file standing at exit 0: for each name a new Glob of the files directly under `<hub>`'s `memory/handoffs/`, its pattern the name cut as above, then `*`; each name gone from its result, or still cited in `<hub>`'s `memory/STATUS.md` `## Current` by the match above, is the effect shown, and the step is done. A result still saying it shows only part of its matches shows no effect, whatever else is read. Where the effect is not shown, it says so and puts the same stop, with the same command where it has one, never another form. REMOVE, where it stands, waits on this outcome, as at a prompt.

With `trees` absent, where the contract does not run and only a `<script>` holding a space comes here, that stop is this step's own, by AskUserQuestion, with no `BLOCKED` line, there being no hub session: `<hub>` is the project root, the line runs in this session's own terminal, and the options and the read stand. `Hold`, or an answer typed in Other, is a denied prompt's outcome above: one line saying so, the record stands, what follows still runs, and the brief stays, uncited, for a later bare run.

## Tree-path steps

### ROOT

compare this session's project root with the Hub path, as the trees contract (`.claude/references/core/trees-contract.md`) compares them. Equal → the session is in the hub, on a branch with no tree of its own: the `vc` binding's current-branch read must show the hub on the branch under close, or stop and say so, since a branch with a tree of its own closes in that tree; then `## Workflow` runs as written, merge and all, with nothing to remove and none of the items below, and its `memory/` writes follow the trees contract — as today while the hub is on this branch, under its exception for a hub session on its own branch, and as hub operations once MERGE has returned the hub to the main branch. That merge into the main branch is bracketed as this file's `### HUB READ` and `### MERGE` bracket a tree's, both commands run in the hub: `scripts/hub.py lock take --root <hub>` right before it, a refused take stopping as `### HUB READ` says; `scripts/hub.py lock release --root <hub>` right after it, merged or not, a failed merge or a refused release stopping as `### MERGE` says. Between that take and that merge, the hub is put on the main branch by the switch command the `vc` binding's *Branch procedure* shows for another use, given the main branch's name, and the session runs `### HUB READ`'s version check there, with that step's outcomes, its re-run from this take; on a failure that same command first returns the hub to the branch under close, the lock still held. A binding showing no such command, or barring a switch of the hub, and a switch that fails each stop as a read failing in `### HUB READ` does, saying which branch the hub is on. The hub session's `memory/` record made after that merge, where `## Workflow` makes one, is made as this file's `## The record` says. Not equal → the List read must name this root as a tree on the branch under close, or stop and say which tree the session is in; the items below then run in this tree.

### CATCH-UP

A Catch-up procedure slot still saying a conflict stops gives way to this step. ### HUB READ

first `scripts/hub.py lock take --root <hub>`, run from this tree; refused → BLOCKED by the trees contract's rule for a refusal with nothing written (`.claude/references/core/trees-contract.md` `## The hub operation`), and nothing merges. Then the hub on the main branch, by the `vc` binding's current-branch read, and clean, by the Clean read, both run in the hub by the Hub slot's idiom; then `### DELTA`'s read again: anything new outside `memory/` → `scripts/hub.py lock release --root <hub>`, `### DELTA`, then, nothing sent back, this read again, from its take. The current-branch read, the Clean read or `### DELTA`'s read failing → `scripts/hub.py lock release --root <hub>`, then stop, saying which and that the lock is released, and nothing merges. A release here refused → BLOCKED, naming its reason and `scripts/hub.py clear --root <hub>`; nothing runs after it. Only a merge into the main branch takes the lock: a merge into another branch — a re-lock's merge-back into its feature branch — takes none.

Last, the lock still held: `scripts/hub.py version-check --root <hub> --branch <branch>`, with `--main` as the trees contract says, run from this tree, `<branch>` the branch under close. Exit 0 → MERGE. Any other exit → `scripts/hub.py lock release --root <hub>` first, a release refused → BLOCKED as above; nothing merges, and every stop below says which and that the lock is released. Then `### RE-BUMP AND UPGRADE`; then, nothing sent back, show the human the changed-file list from the head this check read to the branch's new head; then this read again, from its take.

### MERGE

the `vc` binding's merge procedure, the branch into the main branch, run in the hub by the Hub slot's idiom, with nothing else run in the hub since HUB READ; then `scripts/hub.py lock release --root <hub>`, run from this tree, merged or not. A failed merge stops, saying so and that the lock is released. A refused release → BLOCKED, naming its reason, the merge's commit, where there is one, and `scripts/hub.py clear --root <hub>`; nothing runs after it.

### REMOVE
