# Trees contract

What a filled `trees` binding means — the hub, the comparison of paths, the hub clause, the hub operation and the release files — the form of a report to the hub session, and who does what; whether `trees` or `session-launch` reads filled is `## Reading the optional keys`'s.

## Reading the optional keys

`trees` and `session-launch` are optional, and the two exceptions to `none` as a filled value: each is read as absent when its section is absent, empty, carries `TODO` anywhere, or answers `none` alone — bare, or followed by a space or an em dash and a reason, in lowercase — and filled otherwise. Read as absent, neither is ever a stop: the skill runs its path for that case — for `trees`, today's path: one tree, writers serial, one active branch at a time. Filled, a `trees` section that lacks a slot the step in hand needs, save the Release files slot, which `## The release files` reads and which never stops a step, stops that step and names the slot; a `session-launch` section that lacks a slot the step in hand needs, or answers it `none`, sends that step to its degraded path, naming the slot — never a stop.

## The hub and the comparison of paths

Where `trees` is filled, the hub is the path its Hub slot names, `memory/` means the hub's `memory/`, and a session whose project root is not the hub path — compared in the Path form the `verification` binding names — is in a branch tree; a path lies under another when it is that path followed by a separator and further components, compared the same way, so a sibling that merely shares its prefix does not; where the `verification` binding carries no *Path form*, or is a single `none`, a step that needs this comparison stops and says so, naming the slot.

The base's `scripts/hub.py sessions-at "<path>"`, run from the project root, compares in Windows form, case-insensitively and with either separator, so it applies this comparison to the `session-launch` List command's output where the Path form is Windows form, and a step that asks which sessions are at a tree runs it rather than comparing by eye; under another Path form the step compares by that Path form itself. The base's `scripts/hub.py predecessor "<path>" <session id>`, run from the project root, applies the same comparison where the Path form is Windows form and prints one of `gone`, `elsewhere <cwd>`, `alone`, `no-id` and `stop <id>`, on which `close-tree` `## A handed-off session` acts on its `manual: Path form` row. With `--stop` the same verb runs `scripts/hub.py stop <id>` itself on `stop <id>`, with every check of that verb, and ends with the start step's `suffix:` line, and with `--stop --relay <branch>` it ends instead with the `relay:` or `silent:` line close-tree PREDECESSOR reads; where the Path form is not Windows form it prints `manual: Path form` and stops nothing. The base's `scripts/hub.py stop <id>` reads child processes as its last check, which a stop reaches only once every other check passes and which `--check` reads once, without waiting, whatever the other checks printed: where the entry of the session `<id>` names carries an integer `pid`, it reads that pid's direct child processes and, while one is live, re-reads the list and the children every `WAIT_POLL` seconds for at most `CHILD_WAIT` seconds, then stops the session once none is live, or, where the session has left the list during the wait and none of its children is live, prints `stop: gone <id> at <tree>` and exits 0 without a stop, or, once the bound passes, refuses `children`, naming each live child's pid and name, with no `!` line and nothing stopped; a list or children read that fails refuses `read`, nothing stopped, and an entry with no integer `pid` is stopped unread; the predecessor verb itself reads no child process. The verb orders the sessions at the tree by first start: a session's first start is the earlier of the first timestamp in its own transcript on this machine, found by its full session id, and its `startedAt` in the `session-launch` List command's output; where no transcript timestamp is found, its `startedAt` (`adr-0113`, decision 1 as amended 2026-10-27). Where the named session is listed at the tree, it prints `stop <id>`, or `no-id` where that session shows no stop id, if another session at the tree, listed with an integer `pid`, first started after it, and `alone` where none did; the transcript's layout is `claude-code-cli.md` `## List`'s.

## The hub clause

The hub clause: where `trees` is filled, a command a step runs in the hub runs there as the binding writes it when the session's project root is the hub, and by the Hub slot's idiom from any other session. A slot whose command the binding says runs as written from any tree is run that way wherever a step names the hub clause or the Hub slot's idiom.

## The hub operation

Under a filled `trees`, every write to `memory/`, by any skill — a STATUS update made through the `board` binding's default included — is one hub operation: one `scripts/hub.py write --root <hub>` command, run by the writing session from its own tree, which takes the hub's lock, reads that the hub is on the main branch (`--main <branch>`, where the project's main branch is not the script's default) and clean, its own `.scratch/` aside, makes the write, checks in exactly the paths it edited as one commit, pins that commit to the bytes it wrote, and releases the lock. Its edits and their order are `scripts/hub.py write --help`'s — `--entry`, `--remove-entry`, `--section`, `--note`, `--append`, `--record`, `--halt`, `--item`, `--replace-record`, `--take-item`, `--release-item`, `--release-item-append`, `--move-current`, `--ruling`, `--auto-closed`, `--late-overlap`, `--late-overlap-failed`, `--close-item`, `--remove-record` and `--remove-section`, applied in command-line order, `--message <file>` the commit and `--tree <its own tree>` where an `--auto-closed` reads the late overlap — so a gate's whole record is one command; `--section` replaces whatever another session wrote in that section since, so it is kept for a rewrite no single entry carries. An entry edit, `--entry` or `--remove-entry`, in STATUS `## Current` touches only the session's own branch's block there, save the block of a branch the session has just cut, which the launch's hub write carrying that branch's STATUS entry adds, save the block of a branch the hub session halts on the human's word by `.claude/references/core/halt.md` `## The hub's halt`, which that halt's one write removes, and save the main branch's headline at a gate's close whose record changes it: `--entry Current <key> <file>`, `<key>` read from the hub's STATUS as the headline's text from after its `- **` to its first space, replaces it in place, or adds one where there is none. The own-block rule admits one block more at a prototype's carry: the prototype branch's, which the carry's one write removes by `--remove-entry` before its `--entry` adds the carry branch's block, the session by then on the carry branch. On a `write` refusal that prints a `correct:` line — the session's own input or edit refused, nothing written, no lock held — the session corrects the part that line names and re-runs the same record, no edit added, dropped or retargeted and the own-block rule above still binding, at most 2 re-runs per record (provisional → the tuning pass), and lists each corrected retry, the refusal's reason and the correction made, at its next human stop, with no new report event. On every other refusal with nothing written, exit 1, whatever its cause — a hub off the main branch or not clean, a lock still held after a brief wait, an input or an edit the command refuses without a `correct:` line, a failed check-in it restored, and a correctable refusal once its re-runs are spent, among them — the session reports BLOCKED, carrying the reason and the `re-run:` line the command prints, its input files left under the session's scratch area, and stops: no other hub write, and no retry in another form. Where the hub is not clean under `memory/`, the command prints after the `re-run:` line a `stray:` line naming those paths as changed outside `hub.py write`, with the `clear:` command, and the BLOCKED report carries that line too. A lock the command holds on its own failure stays held until the hub session clears it on the human's word (`adr-0156`), and the session reports BLOCKED, naming the kept commit, where there is one, and the `clear:` line the command prints, and stops as on a refusal without a `correct:` line: no other hub write, and no retry in another form. `scripts/hub.py clear --root <hub>` shows the lock's record and the dirty paths, `--release` frees the lock, and `--check-in` checks in the dirty `memory/` paths. A merge into the main branch is one `scripts/hub.py merge --root <hub> --branch <branch>`, run by the closing session from its own tree with `--tree`, or in the hub on `gate-close` `### ROOT`'s route, taking the hub's lock after a brief wait, as `write` does, and releasing it, or holding it with a `clear:` line where undoing a failed merge, or restoring a failed version raise, fails, with `--main` as `write` takes it, its outcomes as `gate-close` `### HUB READ` and `### MERGE` say. `scripts/hub.py lock take --root <hub>` and `scripts/hub.py lock release --root <hub>` stay in `scripts/hub.py`, and no step brackets a merge by them; a merge into another branch — a re-lock's merge-back — takes no lock. The closing session takes the merge ticket by `scripts/hub.py ticket take merge --wait --root <tree> --branch <branch>`, run from its own tree as a background command at the start of `gate-close` `### CATCH-UP`, and releases it by `scripts/hub.py ticket release merge --root <tree> --branch <branch>` before every stop from that take until the merge, as `gate-close` `### CATCH-UP` **The ticket.** says; where the hub's `tickets` binding says Merge ticket `yes`, `scripts/hub.py merge` and its `--check` read a last check, `ticket`, which refuses a branch holding no merge ticket, nothing merged and the lock freed, and a merge made or already merged releases the branch's merge ticket after `merge: merged`, a refused or undone merge keeping it; a merge into another branch takes and releases no ticket. The older verbs `status line`, `status set`, `note append` and `commit` stay in `scripts/hub.py`, each with `--root <hub>`, and no step makes a hub write by them. The hub operation's other form is `scripts/hub.py sweep-handoffs --root <hub>`, which deletes files under `memory/handoffs/` that `memory/STATUS.md`'s `## Current` does not cite, as one commit under the same lock, takes `--main` as `write` does and refuses as `write` does; with `--branch <branch> --date <YYYY-MM-DD>` it deletes only those the closed branch's moved block in that day's dated note cites, reading the names itself. `.claude/references/core/gate-close.md` `## The kept brief` runs it at a branch's close, by a call in that form or, where the call could not reach the script, by a line the human runs.

One case is excepted: a session whose project root is the hub, while the hub is checked out on that session's own branch — a branch with no tree of its own — writes `memory/` as it would with `trees` absent, committed on that branch, and hub operations resume for the hub once that branch's merge returns it to the main branch; a session in a branch tree that finds the hub off the main branch still stops, as above.

`upgrade`'s STATUS rewrite is a hub operation too: where its report lists `status rewrite:` lines, `harness.py upgrade`'s apply lands the hub's `memory/STATUS.md` itself by `scripts/hub.py` `land_status`, never by `write` — taking the hub's lock for `upgrade`, reading that the hub is on the `vc` binding's main branch and clean (`refuse_dirty`, its `stray:` line as `write`'s), reading the file's digest again, writing the rewritten bytes and checking in that one file as one commit, `memory: upgrade rewrites <m> STATUS lines into the path forms`, the lock released as for every hub write. Where the hub is the project's own root checked out on a branch other than its main branch, the rewrite is written in place and committed by that branch's own ceremony, never by `land_status`.

## The release files

A release file is a file a branch changes because it is being shipped, not because of what the feature does; so release files overlap between concurrent branches, each overlap resolved by the file's rule. The Release files slot names them: the `trees` binding's one `- Release files:` line, its entries split by `; `, each its backticked paths or globs, optionally the part meant (as the `version:` line only), then ` — ` and its resolution rule. Within an entry, `save` before backticked paths or globs excludes them: those files are outside the release class. Where an entry names the part meant, only that part is in the release class; an overlap elsewhere in the same file is outside it, ruled as any other overlap. The slot lacking, answered `none` with or without a reason, or naming no backticked path means no release class — today's behaviour: the binding still reads filled, and it is never a stop. An entry with no rule is outside the release class, its overlap ruled as any other overlap. No script or hook reads the slot's entries; `upgrade`'s `slots missing:` report notes only a `trees` section lacking the line.

## A report to the hub session

A report to the hub session is one plain-ASCII line, `<EVENT> - <branch>; lane: <lane>; <detail>`, the event `STARTED`, `FINISHED` or `BLOCKED`, sent to the Hub session name of the project the sending session's tree belongs to — the one its brief's Reporting names, or, for a session sending on its own account, its own `session-launch` binding's — and never answered. On a hand-off launch the outgoing session sends `BLOCKED - <branch>; lane: <lane>; launch failed` when that launch fails; a session sends nothing at its start, save that a session whose brief carries a predecessor and a start step stops it at its start, as that step says, and sends nothing where the stop exited 0 or the read printed `gone`, else `BLOCKED - <branch>; lane: <lane>; predecessor <session id> not stopped - <the verb's case or refusal line>`; and a session whose brief carries a predecessor and no start step sends the bare `STARTED - <branch>; lane: <lane>; <skill>; predecessor <session id>`, on which the hub session stops the predecessor, as `close-tree` `## A handed-off session` says; in each form the id in full.

**The act 4 duty.** Under a filled `trees`, the hub session relays a BLOCKED line as one line to the human pointing at the session, never rules or answers it, with no push; the hub session never replies to a branch save `adr-0154`'s one information-only exception.

**The act 6 duty.** Under a filled `trees`, the branch session keeps its own STATUS block and dated-note entries current at every stage change.

**The act 7 duty.** Under a filled `trees`, shared hub memory — the master headline's upkeep, the STATUS budget, moving closed history, `automode-refusals.md` and the triage of open items in `memory/items/`, deferrals among them — is the hub session's, where triage is routing an `untriaged` item, closing a duplicate `superseded by <slug>` and closing a stale one `withdrawn`; the closing branch still writes its own records (its block move, its `## Auto-closed` line, the headline change its gate record makes), and a branch session, closing or not, files and closes its own items by hub operation.
Before re-running a draft directory, read its `.hub-write` mark, which `hub.py write` writes in that directory beside the message file, as `<message file>.hub-write`: a first line `landed` is done, so a landed write is not run twice.

**The act 13 duty.** Under a filled `trees`, on the human's word the hub session revives a dormant, stuck or ghost session by the base's `scripts/hub.py launch --resume <full id>`, run from the project root, which runs the bare `claude --bg --resume <full id>` from the session's tree, any flag starting a copy, and stops a non-predecessor by the base's `scripts/hub.py stop <id>`, its Bash call given a `timeout` of 600000 ms, or, where that refuses `merged`, by the `!` line it prints, handed with its `children:` line where it prints one, which the human runs; where it refuses `children`, the session's live child processes past its wait, one line to the human names them, and nothing is stopped.
