# Trees contract

What a filled `trees` binding means — the hub, the comparison of paths, the hub clause, the hub operation and the release files — and the route of a refused act, the form of a report to the hub session, and who does what; whether `trees` or `session-launch` reads filled is `## Reading the optional keys`'s.

## Reading the optional keys

`trees` and `session-launch` are optional, and the two exceptions to `none` as a filled value: each is read as absent when its section is absent, empty, carries `TODO` anywhere, or answers `none` alone — bare, or followed by a space or an em dash and a reason, in lowercase — and filled otherwise. Read as absent, neither is ever a stop: the skill runs its path for that case — for `trees`, today's path: one tree, writers serial, one active branch at a time. Filled, a `trees` section that lacks a slot the step in hand needs, save the Release files slot, which `## The release files` reads and which never stops a step, stops that step and names the slot; a `session-launch` section that lacks a slot the step in hand needs, or answers it `none`, sends that step to its degraded path, naming the slot — never a stop.

## The hub and the comparison of paths

Where `trees` is filled, the hub is the path its Hub slot names, `memory/` means the hub's `memory/`, and a session whose project root is not the hub path — compared in the Path form the `verification` binding names — is in a branch tree; a path lies under another when it is that path followed by a separator and further components, compared the same way, so a sibling that merely shares its prefix does not; where the `verification` binding carries no *Path form*, or is a single `none`, a step that needs this comparison stops and says so, naming the slot.

The base's `scripts/hub.py sessions-at "<path>"`, run from the project root, compares in Windows form, case-insensitively and with either separator, so it applies this comparison to the `session-launch` List command's output where the Path form is Windows form, and a step that asks which sessions are at a tree runs it rather than comparing by eye; under another Path form the step compares by that Path form itself. The base's `scripts/hub.py predecessor "<path>" <session id>`, run from the project root, applies the same comparison where the Path form is Windows form and prints one of `gone`, `elsewhere <cwd>`, `alone`, `no-id`, `stop <id>` and `children <pid> <name>, ...`, on which `close-tree` `## A handed-off session` acts. Where it would print `stop <id>` and that session's entry carries an integer `pid`, it first reads that pid's direct child processes and, while one is live, re-reads the list and the children every `WAIT_POLL` seconds for at most `--wait SECONDS`, `CHILD_WAIT` by default, printing the last read's case: `stop <id>` once none is live, or `children <pid> <name>, ...`, each live child's pid and name, once the bound passes; a list or children read that fails exits 1, and an entry with no integer `pid` prints `stop <id>` unread. The verb orders the sessions at the tree by first start: a session's first start is the earlier of the first timestamp in its own transcript on this machine, found by its full session id, and its `startedAt` in the `session-launch` List command's output; where no transcript timestamp is found, its `startedAt` (`adr-0113`, decision 1 as amended 2026-10-27). Where the named session is listed at the tree, it prints `stop <id>`, or `no-id` where that session shows no stop id, if another session at the tree first started after it, and `alone` where none did; the transcript's layout is `claude-code-cli.md` `## List`'s.

## The hub clause

The hub clause: where `trees` is filled, a command a step runs in the hub runs there as the binding writes it when the session's project root is the hub, and by the Hub slot's idiom from any other session. A slot whose command the binding says runs as written from any tree is run that way wherever a step names the hub clause or the Hub slot's idiom.

## The hub operation

Under a filled `trees`, every write to `memory/`, by any skill — a STATUS update made through the `board` binding's default included — is one hub operation: one `scripts/hub.py write --root <hub>` command, run by the writing session from its own tree, which takes the hub's lock, reads that the hub is on the main branch (`--main <branch>`, where the project's main branch is not the script's default) and clean, makes the write, checks in exactly the paths it edited as one commit, pins that commit to the bytes it wrote, and releases the lock. Its edits and their order are `scripts/hub.py write --help`'s — `--entry`, `--remove-entry`, `--section`, `--note`, `--brief`, `--append` and `--record`, applied in command-line order, `--message <file>` the commit — so a gate's whole record is one command; `--section` replaces whatever another session wrote in that section since, so it is kept for a rewrite no single entry carries. An entry edit, `--entry` or `--remove-entry`, in STATUS `## Current` touches only the session's own branch's block there, save the block of a branch the session has just cut, which the one call landing that branch's launch brief adds, and save the main branch's headline at a gate's close whose record changes it: `--entry Current <key> <file>`, `<key>` read from the hub's STATUS as the headline's text from after its `- **` to its first space, replaces it in place, or adds one where there is none. On a `write` refusal that prints a `correct:` line — the session's own input or edit refused, nothing written, no lock held — the session corrects the part that line names and re-runs the same record, no edit added, dropped or retargeted and the own-block rule above still binding, at most 2 re-runs per record (provisional → the tuning pass), and lists each corrected retry, the refusal's reason and the correction made, at its next human stop, with no new report event. On every other refusal with nothing written, exit 1, whatever its cause — a hub off the main branch or not clean, a lock still held after a brief wait, an input or an edit the command refuses without a `correct:` line, a failed check-in it restored, and a correctable refusal once its re-runs are spent, among them — the session reports BLOCKED, carrying the reason and the `re-run:` line the command prints, its input files left under the session's scratch area, and stops: no other hub write, and no retry in another form. Where the hub is not clean under `memory/`, the command prints after the `re-run:` line a `stray:` line naming those paths as changed outside `hub.py write`, with the `clear:` command, and the BLOCKED report carries that line too. A lock the command holds on its own failure stays held until the human clears it, and the session reports BLOCKED, naming the kept commit, where there is one, and the `clear:` line the command prints, and stops as on a refusal without a `correct:` line: no other hub write, and no retry in another form. `scripts/hub.py clear --root <hub>` shows the lock's record and the dirty paths, `--release` frees the lock, and `--check-in` checks in the dirty `memory/` paths. A merge into the main branch is bracketed by `scripts/hub.py lock take --root <hub>` and `scripts/hub.py lock release --root <hub>`. The older verbs `status line`, `status set`, `note append` and `commit` stay in `scripts/hub.py`, each with `--root <hub>`, and no step makes a hub write by them.

One case is excepted: a session whose project root is the hub, while the hub is checked out on that session's own branch — a branch with no tree of its own — writes `memory/` as it would with `trees` absent, committed on that branch, and hub operations resume for the hub once that branch's merge returns it to the main branch; a session in a branch tree that finds the hub off the main branch still stops, as above.

## The release files

A release file is a file a branch changes because it is being shipped, not because of what the feature does; so release files overlap between concurrent branches, each overlap resolved by the file's rule. The Release files slot names them: the `trees` binding's one `- Release files:` line, its entries split by `; `, each its backticked paths or globs, optionally the part meant (as the `version:` line only), then ` — ` and its resolution rule. Within an entry, `save` before backticked paths or globs excludes them: those files are outside the release class. Where an entry names the part meant, only that part is in the release class; an overlap elsewhere in the same file is outside it, ruled as any other overlap. The slot lacking, answered `none` with or without a reason, or naming no backticked path means no release class — today's behaviour: the binding still reads filled, and it is never a stop. An entry with no rule is outside the release class, its overlap ruled as any other overlap. No script or hook reads the slot's entries; `upgrade`'s `slots missing:` report notes only a `trees` section lacking the line.

## A report to the hub session

A report to the hub session is one plain-ASCII line, `<EVENT> - <branch>; lane: <lane>; <detail>`, the event `STARTED`, `FINISHED`, `BLOCKED` or `HANDOFF`, sent to the Hub session name of the project the sending session's tree belongs to — the one its brief's Reporting names, or, for a session sending on its own account, its own `session-launch` binding's — and never answered. On a hand-off launch the outgoing session sends `HANDOFF - <branch>; lane: <lane>; brief <file name>` after the brief and before the launch, `<file name>` the brief's file name, not its path, and `BLOCKED - <branch>; lane: <lane>; launch failed` when that launch fails; a session whose brief carries a predecessor sends `STARTED - <branch>; lane: <lane>; <skill>; predecessor <session id>`, the id in full. A session whose call, or whose agent's, is refused sends ``BLOCKED - <branch>; lane: <lane>; refused: <date>; <tree>; sub; <tool>; `<call>`; [<tag>]``, `sub; ` only for an agent's call, its fields as `## A refused act` reads them.

## A refused act

Under a filled `trees`, a call refused in a branch session, or to one of its agents, by the auto-mode classifier, a guard or the human at a prompt, is never retried in another form: the session reports `BLOCKED` and puts its own stop, save where a guard names its sanctioned route, below. The detail's fields are a `memory/automode-refusals.md` line's, in its order, ` · ` written `; `: `<date>` UTC; `<tree>` as that file writes it; `sub` only for an agent's call; `<call>` on one line, each run of whitespace one space, a Write or Edit as `<path> :: <its content, or the Edit's new_string>`, cut to 140 characters, `...` where cut, non-ASCII as `?`; `<tag>` the classifier's, the guard's file name, or `denied` for a denied prompt, for an agent's call read from its `refused` line's words, `unknown` where they carry none. `refused:` is detail, not an event word.

A guard refusal whose reason names its sanctioned route (`hooks.md`: the hub memory rule's `scripts/hub.py write`, the handoff rule's `handoff`) takes that route, no retry in another form, never a command around the guard: no `BLOCKED`, so no log line, and no stop. Any other stop's command is one line for the human to run with `!` in the hub terminal, from the hub's working directory, alike in a POSIX shell and PowerShell: no heredoc; no `;`, `&&`, `||` or `|` outside quotes; absolute paths quoted as the Hub slot's idiom quotes them; a version-control command by the Hub slot's idiom. Only a shell call and a Write or Edit (below) have one: the shell call's effect-bearing command kept, its paths made absolute against the tree, a leading `cd <dir> &&` turned into that idiom or absolute paths, a trailing status print dropped. Any other call (`Agent`, `SendMessage`, `NotebookEdit`, `Read`) has no faithful form, said in the stop; so has a shell call whose line would hold two effect-bearing commands, whose effect depends on its working directory beyond the paths it names, or that names a path holding `"`, `$` or a backtick.

For a refused Write or Edit, the session places the file as the call would leave it at `.scratch/refused/<slug>/<file name>` in its tree, `<slug>` a new kebab-case name, by a command that writes it from the call's input in the transcript without printing it, as `delegation-contract.md` `## Filing` extracts a recon report: an agent's call from its transcript, a main-thread call from the session's own (`claude-code-cli.md` `## List`); for an Edit, it reads the target and replaces `old_string` with `new_string`, each occurrence where `replace_all` is set; never by a Write or Edit, which the classifier can refuse like the call. The command is `cp "<placed file>" "<target>"`, `<placed file>` the placed file's absolute path, both paths written in the `verification` binding's *Path form*, replacing the whole target. Where the placing command is refused too, where an Edit's `old_string` is absent from the target or, without `replace_all`, found in it more than once, or where a Write's target directory is absent, the act has no command.

The stop, one AskUserQuestion after `BLOCKED`, names the act, its target, the refusal's words and the command, or that the act has none; its options are `Hold` and, with a command, `Ran it in the hub`, without one, `Done another way`. On `Ran it in the hub` or `Done another way` the session reads the effect from evidence, the file or the tree's state by the `vc` binding's working-tree read: where the effect shows, it goes on; where not, it says so and puts the same stop, with the same command where it has one, never another form. On `Hold`, or an answer typed in Other, the act stays refused and the turn ends `Stop: BLOCKED`: a typed answer never clears the act for a retry. For an agent's call, named by its `refused` line (`brief-fields.md` `## The report (up)`), the delegator puts the stop and does not re-run the agent for it.

The hub session relays the line (the act 4 duty) and logs it in `automode-refusals.md` by one hub operation (the act 7 duty), acting on no output its terminal shows. After 3 blocks in a row or 20 in all, auto mode prompts instead (`adr-0152`); a denied prompt takes this route. A failed `SendMessage` or an absent hub session stops nothing: the stop stands in the branch, which awaits no reply.

**The act 4 duty.** Under a filled `trees`, the hub session relays a BLOCKED line as one line to the human pointing at the session, never rules or answers it, with no push; the hub session never replies to a branch save `adr-0154`'s one information-only exception.

**The act 6 duty.** Under a filled `trees`, the branch session keeps its own STATUS block and dated-note entries current at every stage change.

**The act 7 duty.** Under a filled `trees`, shared hub memory — the master headline's upkeep, the STATUS budget, Deferred trims, moving closed history, `automode-refusals.md`, backlog candidates — is the hub session's; the closing branch still writes its own records (its block move, its `## Auto-closed` line, the headline change its gate record makes).

**The act 13 duty.** Under a filled `trees`, on the human's word the hub session revives a dormant, stuck or ghost session by a bare `claude --bg --resume <full id>` from the session's tree, any flag starting a copy, and stops a non-predecessor.

**The act 14 duty.** Under a filled `trees`, a branch session whose call, or whose agent's, is refused reports `BLOCKED` and puts its own stop as `## A refused act` says, save where a guard names its sanctioned route; the human runs the act; the branch verifies its effect from evidence; the hub session's Claude only logs the refusal and takes no branch act.
