# Halt

What a halt is, how a branch's own session and the hub session write one, and how it runs where `trees` reads absent. The halt record's layout and its refusals are `scripts/hub.py write --help`'s for `--halt`; the close of a halted tree is `close-tree`'s `## Workflow`; a hub write is `.claude/references/core/trees-contract.md` `## The hub operation`.

## The halt

A halt drops a branch's work unmerged and keeps the branch: a design scratched, a feature dropped or a light-lane changeset abandoned, at any stop of any lane. A branch is halted only on the human's ruling, never on the PM's judgement, and its halt record carries the human's halt words verbatim; no check tells a ruled halt from an invented one, so this rule is advice. The record, `memory/halts/<name>.md` in the hub's `memory/`, `<name>` the branch with each `/` written `~`, pins the branch, and each writer branch it names on a `unit:` line, to its head as the write read it: `scripts/hub.py stop` and the `trees` binding's Remove procedure pass, beside a merged branch, a branch a halt record names at its current head, so a later commit or changeset on it voids the halt. Nothing deletes a halted branch. Once a halt's write lands, where the `tickets` binding at the write's `--root` says Merge ticket `yes`, `scripts/hub.py write` drops the halted branch's merge ticket and merge queue place, promoting the next queued branch and printing a line for each drop after the commit line; a write that refuses drops nothing.

## The branch's halt

On the human's halt ruling, the branch's own session, in its own tree, first checks in its pending work on the branch by the `vc` binding's *Check-in procedure*: the record pins the head read at the write, so a check-in after it would void the halt.

It drafts the write's inputs into `.scratch/halt-<slug>-record/`, `<slug>` the topic, feature or changeset the branch names: `message.md` the commit message, the halt file and, where the item is `taken` and its fate `open`, the release text, the halt and any revisit condition, for the item's body. The item is the one the base's `scripts/hub.py items --root <hub> --status taken` shows `taken <branch>`, else the one the human's words name, else none. Where that read shows more than one item `taken <branch>` — a batch's items, or a feature's with its row's `Sites:` items — the item is the first it shows, and each other one is returned to `open` by the write's `--release-item <slug>`, whatever the fate. Its fate is `declined` only where the human's halt words decline the item itself, as the PM reads them; `open` otherwise, the item returned to `open` with the halt and any revisit condition written into its body, or left as it is where it is already `open`; and `none` where there is no item.

The halt file is the record less its heads, one line each, in this order: `---`; `branch: <branch>`, the branch as the `vc` binding's current-branch read gives it, without a leading `/`; `date: <date>`, the day of the ruling, `YYYY-MM-DD`; `stage: <step>`, the step the branch halted at; `item: <slug>` or `item: none`; `fate: open`, `fate: declined` or `fate: none`; `writer: branch`; then one `unit: <writer branch>` line per writer tree the `trees` binding's List read shows on a branch the Writer-branch naming slot gives for this branch, naming that branch alone; then `---`; then the human's halt words, verbatim and never blank. It carries no `head:` line and no head on a `unit:` line: the write reads every head itself.

Then one `scripts/hub.py write --root <hub> --message <file>` command, with `--main` as the trees contract says, `<hub>` the Hub path, run from this tree, carries in this order: `--remove-entry Current <branch>`, where the branch's block is in the hub's `memory/STATUS.md` `## Current`; then the item edit the fate needs: for the fate `open`, `--release-item-append <slug> <file>` where the item is `taken`, `<file>` the release text, which the write appends to the item's body as it returns the item to `open`, and no item edit where it is already `open`; for the fate `declined`, whether the item is `taken` or already `open`, `--note <file>`, an entry in `.claude/references/core/gate-close.md` `## The dated note`'s form, then `--close-item <slug> declined`; no item edit for `item: none` or for a `declined` item already closed; then `--release-item <slug>` per other item that read shows `taken <branch>`; then `--halt <file>`, last. The table below reads what it prints, its refusals taken as `.claude/references/core/trees-contract.md` `## The hub operation` says.

| `write` prints | The halt |
|---|---|
| the commit line, exit 0, and any merge ticket line `## The halt` names after it | the halt landed: the next paragraph's report here, `close-tree` in `## The hub's halt`, nothing more where `trees` reads absent |
| `hub.py write:` with a `correct:` line, exit 1 | correct the part it names and re-run the same write, as the trees contract says |
| `hub.py write:` with a `clear:` line, exit 3 | the lock held: BLOCKED and stop, naming the `clear:` line, as the trees contract says |
| `hub.py write:` with no `correct:` line, exit 1 — the item absent or malformed among them — or any other output | BLOCKED and stop, the drafts kept, nothing written, as the trees contract says |

Then, where the `session-launch` binding reads filled with its Hub session name, as the trees contract reads it, the session reads the `head:` line of the landed record, `memory/halts/<name>.md` in the hub, says the report line `FINISHED - <branch>; lane: <lane>; halted at <step>, branch kept at <head>`, `<lane>` the brief's Lane, `<step>` the record's `stage` and `<head>` its `head`, and sends it by `SendMessage` to the Hub session name as this session's last act, since the hub session may stop this session within seconds and closes the tree, and each writer tree the record names, by `close-tree`. Otherwise nothing is sent, and the tree stays until the human's word closes it. Either way this session does no further work.

## The hub's halt

On the human's word to halt a branch whose session is dead or idle, never one still at work, the hub session makes `## The branch's halt`'s write itself, run in the hub with `--root <hub>`, its drafts in the hub's own `.scratch/halt-<slug>-record/`, the halt file's `writer: hub`, each edit only where still needed: a block already gone takes no `--remove-entry`, and the item takes that section's route by its fate, `--release-item-append` for a `taken` item whose fate is `open` and no item edit for one already `open`, `--note` then `--close-item <slug> declined` for a `declined` item whether `taken` or already `open`, and no item edit for `item: none` or a `declined` item already closed, and `--release-item <slug>` per other item shown `taken <branch>`, as that section says, so the write may be `--halt` alone, what it prints read by that section's table. Nothing is checked in in the branch's tree, so a tree with pending changes is kept at `close-tree` CLEAN with R3's line (`.claude/skills/close-tree/references/outcomes.md`), the halt standing for a later close. No report line is sent. Then the hub session runs `close-tree` `## Workflow` for the branch, as its `## When it runs` says.

## Where trees reads absent

Where `trees` reads absent, the halt is the write alone: no stop, no removal and no report line, the one checkout being the branch's tree. Since `scripts/hub.py write` writes only on the main branch, the session works in this order: it checks in its pending work on the branch by the `vc` binding's *Check-in procedure* and reads the branch's name by the `vc` binding's current-branch read; it puts the one checkout on the *Main branch* by the switch the `vc` binding's *Branch procedure* shows, that idiom with the *Main branch* named as the branch switched to; then, on the main branch, it reads the item as `## The branch's halt` says, by `scripts/hub.py items --root <project root>`, and drafts that section's inputs, the halt file's `branch:` the name read before the switch, the halt file holding no `unit:` line; then it makes that section's write with `--root <project root>`, what it prints read by that section's table. The branch is kept.
