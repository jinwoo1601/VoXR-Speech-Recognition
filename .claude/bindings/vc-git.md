# vc-git bindings

## vc
<!-- Interview: Which version-control system does this project use, and how are branches created, changes checked in, base revisions read, branches merged, the working tree recorded before an upgrade, and pull requests read, diffed and commented on? -->
- System: git; GitHub, remote `origin` `https://github.com/jinwoo1601/VoXR-Speech-Recognition.git`, public; `gh` on the Windows PATH (`C:\Program Files\GitHub CLI\gh.exe`), authenticated as `jinwoo1601`
- Main branch: `main`
- Auto-mode entries: excluded
- Branch procedure: a re-lock — a `design-<topic>` branch cut from the feature branch's head in the feature's own tree, declared on its STATUS line `re-lock of <feature-branch>`, merged back into that feature branch after G1 — is cut by `git switch -c design-<topic>` in the feature's tree and merged back by `git switch <feature-branch>`, then `git merge design-<topic>`, in that tree; a carry — a `design-<topic>` branch cut from the main branch in a prototype's own tree, the one checkout where `trees` is absent, declared on its STATUS line `carry of <prototype-branch>`, which takes only the topic's design directory from the prototype branch — is cut and switched to by `git switch -c design-<topic> <main-branch>` in that tree; branches are `design-<topic>`, `feat-<feature>`, `light-<topic>` (an issue's `light-<n>-<slug>`), `lab-<topic>`, which merges nothing, and the release prep `chore/release-X.Y.Z`; each is cut from an up-to-date `main` — `git fetch origin`, then on `main` `git merge --ff-only origin/main`, both run in the hub — together with its own tree, from the hub, by the Create procedure of `## trees` below, and runs in that tree
- Check-in procedure: inline on the main thread — `git add -- <paths>`, then `git commit -F <message file> -- <paths>`, each one command, never a heredoc or a chain, never `git add -A` — a hub operation's `memory/` check-in by the base's `scripts/hub.py write --root D:\Workspace\VoXR-Speech-Recognition --main main`, which writes and checks in exactly the paths it edits under `memory/`, as one commit; then `git push -u origin <branch>` on a branch's first push and `git push` after; the commit sha is the receipt; every hub write — a `hub.py write` in the hub on `main` — is preceded by `git pull --no-rebase origin main` in the hub and followed by `git push` there, `hub.py write` neither pulling nor pushing; a failed pull or push is reported, never retried in another form, and the local write stands; a session's `memory/` commits in the hub while the hub is on that session's own branch are plain check-ins on that branch, outside the sync, `main` never pulled into it; pull requests still merge on GitHub, by the human
- Base-revision reads: `git show <revision>:<repo-relative-path>`; `git diff --name-status <base>..<head>` for the changed-file list; `git diff <base>..<head> -- <path>`; `git log --oneline <base>..<head>`; `git status --short` for the working-tree read; `git branch --show-current` for the current branch; `git diff --numstat --no-renames <base>..<head>` for the per-file line-count read
- Merge procedure: a pull request against `main`, opened by `gh pr create --base main --title "<title>" --body-file <file>` after the push, merged by the human on GitHub behind the gate's stop; Claude never merges
- Snapshot procedure: `git stash create "harness pre-upgrade <date>"`, then, where it prints a sha, `git update-ref refs/harness/pre-upgrade/<sha> <sha>` — a ref of its own keeps the snapshot from garbage collection without touching the stash stack, which every worktree shares, so no parked stash moves; the working tree and the index are left as they are; where it prints nothing, the snapshot is `git rev-parse HEAD`; confirmed by `git rev-parse --verify <sha>^{commit}`; restored by the human from that sha — `git stash apply <sha>` — and the ref then dropped by `git update-ref -d refs/harness/pre-upgrade/<sha>`; `.claude/` and `CLAUDE.md` are tracked from `light-harness-adopt` on, so the record covers them — `.claude/settings.local.json` and `.scratch/` stay ignored and are not covered
- PR read: `gh pr view <n> --json number,title,body,url,state,isDraft,headRefName,headRefOid,baseRefName,files,labels` and `gh pr list --head "<branch>" --json number`; `gh` has no `baseRefOid` and no `closingIssuesReferences` field, and `--json` never goes without an explicit field list
- PR diff: `gh pr diff <n> > <file>`
- PR comment: `gh pr review <n> --comment --body-file <file>`, falling back to `gh pr comment <n> --body-file <file>`; never `--approve` or `--request-changes`, which GitHub refuses on one's own pull request; `gh pr edit` fails on the Projects-classic `projectCards` deprecation, so a PR body is patched by `gh api repos/jinwoo1601/VoXR-Speech-Recognition/pulls/<n> -X PATCH -F body=@<file>`

## trees
<!-- Interview: Does this project run branches in their own working trees — where the main checkout and the trees live and how trees are named, how a branch and its tree are cut, listed, read clean, caught up with the main branch and removed, how writer branches are named, and whether writer trees are pooled — or a single `none` where every branch runs in the one checkout? -->
- Hub: a command runs in another tree by the idiom `git -C "<path>" <command>`, the path quoted, and only there — a command in the session's own tree runs bare from its root; the main checkout is `D:\Workspace\VoXR-Speech-Recognition` — it stays on `main` and holds `memory/`; every hub write while the hub is on `main` — `scripts/hub.py write --root D:\Workspace\VoXR-Speech-Recognition --main main`, from the hub or from any tree — is preceded by `git pull --no-rebase origin main` in the hub and followed by `git push` there, each run from a tree by this idiom, as the vc Check-in procedure states
- Location: trees live beside the hub in the directory `D:\Workspace\VoXR-Speech-Recognition.trees`; a branch tree is `D:\Workspace\VoXR-Speech-Recognition.trees\<branch>`, and a writer tree is `D:\Workspace\VoXR-Speech-Recognition.trees\<branch>--<unit>`
- Create procedure: in the hub, `git show-ref --verify --quiet refs/heads/<branch>` finding nothing, then `git worktree add -b <branch> "<path>" main`
- List read: `git worktree list` — one line per tree, the hub's first
- Clean read: `git status --short` in the tree — empty is clean
- Catch-up procedure: in the branch tree, `git -c core.attributesFile=.claude/references/vc-git/merge-attributes.txt merge main`; a conflict leaves the merge open: `git diff --name-only --diff-filter=U` lists its paths, `git add -- <paths>` marks each resolved, `git commit -F <message file>`, with no pathspec, concludes it, and `git merge --abort` undoes it
- Remove procedure: `py .claude/references/vc-git/tree-remove.py "<path>"`, run as written from the hub or any tree of the repository — one command, never wrapped in the Hub slot's idiom: it waits for the directory's release, runs `git worktree remove "<path>"` (never forced, so a tree with a pending change is refused), reads back, and prints `removed`, `refused`, `absent`, `held` or `half-removed`; the branch is kept
- Writer-branch naming: `<branch>--<unit>`, cut from the branch's tip
- Pool: `none`
- Release files: `CHANGELOG.md` — keep both sides' `## [Unreleased]` entries, this branch's first; `.claude/`, `.claude/harness.json` included, save `.claude/bindings/*.md` — regenerated by `upgrade`, never hand-merged
